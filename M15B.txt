## 1. Mission

Implement an integrated, usable workflow rather than more isolated security helpers:

1. Current actively assigned **DRIVER** selects the canonical deployed vehicle in a REAL incident.
2. Driver explicitly enrolls the phone via P-256 device proof and one-time server challenge.
3. Driver reads an **approved, versioned** sharing notice, consents and manually presses START.
4. Server confirms a **bounded** sharing session; only then may Android start its visible location foreground service.
5. Real Android OS GPS observations are signed, validated and uploaded as latest-only vehicle position; no route/history.
6. Independently authorized Web and Android readers see fresh (green), approved stale (amber), or unavailable (grey/no marker) position on existing maps.
7. STOP / “I left the vehicle” halts acquisition immediately; server authorization/reader visibility ends on confirmed revocation, or lease expires when offline.
8. A separately approved retention worker physically deletes expired coordinates without requiring more reads or traffic.

Make genuine implementation code, not just another architecture-only milestone. Clearly distinguish `IMPLEMENTED_BUT_DISABLED`, `IMPLEMENTED_SAFE`, `BLOCKED_BY_POLICY`, `BLOCKED_BY_INFRASTRUCTURE`, and `NOT_IMPLEMENTED`. There are important design decisions here, not assumptions:

1. If `incident_units` deployment changes vehicle, the prior binding and session must fail authorization; never silently reassign to a new canonical vehicle ID.
2. Use a unique partial index for active binding/session ownership per canonical incident deployment and vehicle **only after evaluating lease-expiration mechanics**. A stale SHARING row might remain after wall-clock expiry; enforce transition under lock before granting a new slot rather than assuming a partial index with `now()` predicate is valid.
3. Do not automatically create an `APPROVED` policy row as part of the migration. All new rows are default DRAFT and no session can start until source-verified, owner-approved activation exists.
4. Store latest observation per active canonical vehicle; use `INSERT ... ON CONFLICT DO UPDATE` with monotonic sequence and trusted time checks, not append-only trip-history tables. Prevent `RETURNING` from leaking raw data through an untrusted wrapper.
5. Stop/revoke must remove the latest coordinate **or immediately forbid its read even when deleted physically later**; never leave a visible last-known marker after a deliberate STOP.
6. Do not insert raw coordinates into existing incident audit/events/snapshot/receipts/FCM/Realtime or generic analytics records. Exact receipts may store hashes/outcomes, **not locations**.
7. Use appropriate `CHECK` constraints for E7 coordinates and accuracy, relational cardinality, timestamp order, policy state and protocol version. Reject NaN/Infinity at the API boundary before integer encoding.
8. If policy approval/data controller/retention ownership is not defined, implement schema and procedures that are genuinely disabled from production entrypoints. Do not manufacture approval values or a server status PASS.
9. Provide an explicit deletion-retention lifecycle for policy/consent/security metadata separately from raw precise coordinates. No blind permanent storage just because the table is `private`.
10. Use `LOCK_TIMEOUT` and bounded transaction times appropriate for the existing project; do not hold PostgreSQL transactions open during network/WebCrypto awaits.

### 12A.4 Proposed function and HTTP API contracts

Resolve exact naming conventions from repository source. Proposed shapes follow; **do not claim these signatures already exist**. Implement typed request/response schemas in TS/Kotlin and exact SQL signatures for the chosen real architecture. Every mutable request carries an original client-generated UUID, an immutable normalized payload hash and a context identity tuple.

**Credential ceremony (distinct from GPS permission)**

- `POST /functions/v1/vehicle-location/device/register` — explicit user action. Body: original registration operation UUID, acting organization, REAL incident, deployment, vehicle, public P-256 SPKI, credential UUID. The server verifies current DRIVER scope and records only an inactive candidate public key; **registration alone is not evidence of possession**. Where policy gate not approved, return a disabled code rather than accept a production binding.
- `POST .../device/challenge` — original issue and confirm operation UUID, credential ID and frozen scope. Server allocates nonce, challenge row and actual bound 27-line transcript, with 120-second lifetime. Retry of original UUID must retrieve same challenge and nonce, not issue a fresh one.
- `POST .../device/confirm` — original confirm UUID, raw64 proof and challenge ID. Trusted CLAIM -> WebCrypto -> FINALIZE; return authoritative `PROOF_VALIDATED_INACTIVE` receipt with no sharing authority. Fail closed on JWT, challenge, credential or episode mismatch.
- `POST .../device/revoke` — owner/actor-scoped immutable revoke, explicit local status; server revocation wins over late confirm, old receipts cannot restore it.

**Consent & sharing (separate policy-gated paths)**

- `POST .../consent` — exact policy ID and immutable version/document/audience hashes, driver-visible notice presentation evidence, explicit user action, original UUID. Never consent via a background refresh.
- `POST .../sessions/start` — binding + consent + current active driver + REAL incident + vehicle versions + retention readiness + enabled policy + verifier proof; returns server-generated session ID, bounded lease and server time. The client must not start GPS collection if the server refuses.
- `POST .../sessions/renew` — authenticated bounded renewal using live actor/credential/session and current authority, with no implicit re-consent across policy changes. The server must limit renewals and overall maximum approved sharing duration.
- `POST .../sessions/stop` — immutable STOP UUID, reason `USER_STOP` / `LEFT_VEHICLE` / `LOGOUT` / `PERMISSION_REVOKED` / `ERROR`; idempotent, revokes live sharing and precise visibility. If the service is offline, stop collection locally immediately and show server outcome as UNKNOWN until acknowledged/lease expires.
- `POST .../positions/latest` (ingest) — JWT + active session + distinct signed GPS sample + bounded coordinate bytes. Accept only one strictly advancing sequence; never persist unapproved offline backlog.
- `GET .../positions` — exact acting organization and incident, authenticated current reader with *narrow precise-reader policy*; only nonexpired and not-revoked positions. Return safe stable view DTOs, never full session/key/driver metadata.

Prefer fewer well-secured Edge paths if matching source conventions, but do not consolidate different operations into a handler that silently confuses auth boundaries. Specify request-size maxima and JSON rejection rules; unrecognized fields, duplicate keys, wrong canonical UUIDs and precision anomalies must be rejected consistently. Signature metadata must not be writable in URLs or logs.

**Mandatory response shape** (adapt to actual project API conventions, retain semantics):

```typescript
type VehicleLocationResult<T> =
  | { ok: true; schemaVersion: 1; result: T; originalOperationId?: string; serverTime: string }
  | { ok: false; schemaVersion: 1; code:
      "CAPABILITY_DISABLED" | "POLICY_UNAPPROVED" | "RETENTION_NOT_READY" |
      "DEVICE_PROOF_REQUIRED" | "NOT_AUTHORIZED" | "SCOPE_CHANGED" |
      "CHALLENGE_EXPIRED" | "PROOF_INVALID" | "CREDENTIAL_REVOKED" |
      "SESSION_EXPIRED" | "OPERATION_CONFLICT" | "OUTCOME_UNKNOWN" |
      "INVALID_LOCATION" | "RATE_LIMITED" | "BACKEND_UNAVAILABLE";
      originalOperationId?: string; retryable: boolean };
```

Do not return whole row objects or opaque SQL exception strings to clients. Correlation IDs must be non-secret and must not contain coordinates. Unknown network outcome stays UNKNOWN; do not translate a timeout into CONFIRMED.

### 12A.5 Registration, challenge and trust bridge: transaction-level procedure

The new handler must be auditable at the boundary between a live user JWT and internal SQL.

**Registration**:

1. Validate actual user JWT and session status using the installed supported Supabase auth pattern; `apikey` is not an actor. Use the official `@supabase/server` documented `auth:'user'` pattern if compatible with checked-in dependencies and project config, or the existing correct JWT pattern. Do not disable gateway JWT validation to bypass 401.
2. Resolve actor from trusted verified JWT, not request JSON. Confirm account active, exact acting org, active REAL incident, exact deployment/vehicle, current ACTIVE DRIVER episode and authority revision. Only use effective leader fallback if separately approved; default to DRIVER only.
3. Validate 91-byte P-256 SPKI DER, curve/point and SHA-256 fingerprint, canonical UUID, size and request identity. Possession cannot be proven until the challenge is signed and accepted.
4. Acquire a consistent row-lock order for relevant credential/generation and binder slot. Do not hold locks across external `await`.
5. Insert inactive credential, original immutable registration operation and **only** the minimum necessary registration metadata. Return no authorization to share. On replay verify exact request equality.
6. Never allow app-level `service_role` or arbitrary admin to enroll on behalf of someone else without independently approved policy and impersonation/audit model.

**Challenge issue**:

1. Recompute the exact domain (`GASILKO-VEHICLE-PHONE-BINDING-V1`), actor/org/incident/deployment/vehicle/authority episode from trusted rows.
2. Determine `audience`, `recoveryEpoch`, `policyVersion`, `policyDocumentSha256`, `preciseAudienceSha256` from *actual approved authoritative records*. If absent, **reject**; do not use fake hashes, zero epochs or a TODO constant to make the transcript compile.
3. Mint 32 bytes of CSPRNG nonce server side and a new challenge UUID, bound to original issue and confirm operation UUIDs. Enforce `expires_at=issued_at+120s`, unique UUIDs, key generation and entity versions.
4. Freeze the transcript bytes; store appropriate hash, nonce, policy reference, immutable request hash and issued/expiry in private DB. Use canonical encoding from the existing v1 library.
5. Idempotent replay of `issue_operation_id` and same normalized request returns the same challenge, not a duplicate. Changed request with reused operation UUID -> OPERATION_CONFLICT. Already expired -> EXPIRED, not silently new nonce for same UUID.
6. Bound outstanding challenges per actor/credential/org, reject abuse and never leak foreign credential existence.

**Confirm**:

1. Validate JWT, raw64 signature length and claim operation UUID; resolve stored canonical credential and challenge. A caller cannot replace SPKI, challenge nonce, current policy, actor, role, authoritative clock or vehicle versions.
2. TX-A attempts `ISSUED -> CLAIMED` through the existing private guarded primitive or a verified successor; use same original request hash and claim lease. Under replay return the same current claim where source permits.
3. Outside TX-A, call `verifyDeviceProofV1` on the exact stored SPKI and stored transcript with raw64. Its only proof is `SIGNATURE_VALID_ONLY`; avoid fresh construction of a transcript from user JSON.
4. TX-B must have **trusted verifier-only authority**; an ordinary authenticated RPC invoker must be structurally incapable of submitting `verified=true` or a chosen digest and advancing state. Choose and document an actual secure bridge (private server secret + limited DB contract, or dedicated restricted trusted invocation) based on verified source. Avoid treating mere service_role use as evidence of role/actor authorization.
5. Within TX-B lock/validate claim, current credential generation, revocation, current DRIVER, incident mode/lifecycle, deployment vehicle, unchanged versions, current policy and challenge expiry. On match commit `PROOF_VALIDATED_INACTIVE` and immutable receipt; on revocation/staleness fail without resurrection. No GPS status changes.
6. A duplicate confirm returns original committed receipt only if immutable args match; changed args with same UUID rejected. A claim timeout may be UNKNOWN, never artificial acceptance.

Document specific failure injection states even though no code execution is authorized: handler crashes before CLAIM, after CLAIM, after verification, during TX-B, after commit and before HTTP response; what exact row/receipt is expected and how a later identical operation recovers.

### 12A.6 GPS sharing lifecycle and safe state transitions

Implement a **real** state machine for operational sharing independent from the proof lifecycle. Suggested states and allowed edges:

```text
NO_BINDING
  -> PROOF_VERIFIED_INACTIVE
  -> AWAITING_CONSENT
  -> READY_TO_START  [all server policy + retention + authority gates]
  -> STARTING        [original START UUID frozen]
  -> SHARING         [server confirms bounded lease]
  -> STOP_REQUESTED  [local acquisition stops FIRST]
  -> STOPPED         [server confirms revoke]
SHARING -> LEASE_EXPIRED / REVOKED / ERROR_UNKNOWN
STARTING -> ERROR_UNKNOWN / STOPPED / SHARING only on authoritative receipt
STOP_REQUESTED -> STOPPED or UNKNOWN_REMOTE_STOP (never resume samples)
```

**No shortcut transitions** from signature verified to SHARING. Consent cannot be inferred from proof, possession, driver role, map visibility, or prior login. A policy version change invalidates previous readiness, never auto-upgrades consent.

For every state define, in the milestone doc:

- server-owned state and any canonical DB `CHECK`/unique constraints;
- Android UI copy and permitted controls;
- authoritative original operation UUID and immutable request;
- terminal transitions and recovery after process death;
- exact server lease and local acquisition deadline;
- which authority conditions are re-evaluated;
- whether a position reader may receive precise coordinates;
- denial code and cleanup of local mutable references;
- what a stale Android ViewModel after org switch may display;
- how it behaves if old server migrations are absent.

**Lease design**: propose an initial short time (for example 90 seconds) subject to P10/P11 owner approval. Sample receipt may or may not renew the lease; make that explicit and ensure renewal cannot continue indefinitely without the approved maximum duration. A server lease is not a substitute for STOP: local GPS acquisition must stop synchronously with STOP, and stale already-issued observations must be rejected by authority/generation/session checks.

**Single device / handover**: enforce exactly one accepted owner for a canonical deployed vehicle at a time using DB locks + unique active-row constraint. When prior lease has expired but row still says SHARING, explicitly retire it under lock before another start; no `now()` in partial unique index. Handover requires an approved owner-visible flow; do not silently transfer on a second phone request.

**Vehicle release or incident close**: even without a proactive trigger, every ingest/read/renew must re-check current authority; service must stop locally on next rejected heartbeat and old latest position must be hidden immediately. Design a server-side invalidation mechanism where possible, but do not claim client push delivery is guaranteed.

**Offline STOP**: on tap, revoke local collection permission inside app first, kill callbacks/service, clear in-memory coordinate, freeze STOP request UUID and attempt server cancel when network exists. No GPS queue or stored trip replay. Remote STOP can remain UNKNOWN until reconnect or server lease expiry; disclose this plainly, do not assert that distant server instantaneously acknowledged an offline action.

### 12A.7 Idempotency model for START, STOP, consent and each sample

Design an explicit immutable request envelope rather than relying on HTTP retries:

```typescript
type FrozenCommand = {
  originalOperationId: string; // UUID, never reissued on retry
  scope: {
    accountId: string;
    actingOrganizationId: string;
    incidentId: string;
    deploymentId: string;
    vehicleId: string;
  };
  canonicalPayloadHash: string; // hash of immutable normalized fields
  command: "CONSENT" | "START" | "RENEW" | "STOP" | "LEAVE_VEHICLE" | "SAMPLE";
};
```

Scope/model may be adjusted to actual source, but operation identity cannot silently retarget after an organization or selected vehicle changes. Store per-operation receipts with bounded nonlocation metadata. Do **not** store raw lat/lon in receipt JSON, command log or incident audit.

- Duplicate START same original UUID+hash returns the same server-created session and state, **not** a second active session.
- Same UUID different vehicle, policy hash, consent fields or coordinates -> OPERATION_CONFLICT.
- STOP can be idempotently repeated even if session expired; do not resurrect it.
- STOP and SAMPLE racing: lock session row and compare sample lease/generation/sequence; STOP commit must make subsequent or delayed sample reject, never override STOP.
- SAMPLE unknown result is tricky: if the client did not receive ack and later GPS moved, never reuse original sample UUID to sign new coordinates. Do not queue old samples as an offline trip. Optionally retry a single same frozen in-flight payload **only while live and lease-valid**, with hard bounded delay, or drop it; document exact choice.
- Keep out-of-order/duplicate sequence from replacing a more recent observation; repeated accepted sample yields same receipt/ack metadata, not another row.
- If crypto fails after server CLAIM, never finalize an `approved` state. If a network timeout occurs after a successful write, eventual original receipt can confirm exactly what was accepted, not a newly constructed request.
- Do not change B1 cursor/projection atomicity, D1/D2 command queues or M10 notification payloads. GPS samples must use a dedicated ephemeral, privacy-aware path, **not** the existing durable incident operation queue.

### 12A.8 Signed sample V1: canonical byte-level contract

Add a **new** domain, separate from the 27-line enrollment transcript. Publish the exact byte layout in both Kotlin and TypeScript, preferably as a versioned common contract document. This is an implementation specification; choices below are defaults to be source-reviewed and accepted by owner before activation.

```text
Domain: GASILKO-REAL-VEHICLE-LOCATION-SAMPLE-V1
Canonical encoding: UTF-8 LF-delimited ASCII fields, one final LF
OR a documented binary schema with exact offsets and endian order.
Do not use JSON.stringify as signed bytes.
Fields in the EXACT same order:
  01 domain
  02 protocol version "1"
  03 original sample operation UUID
  04 sharing session UUID
  05 actor user UUID
  06 acting organization UUID
  07 REAL incident UUID
  08 incident deployment UUID
  09 canonical vehicle UUID
  10 credential UUID
  11 credential generation as positive decimal integer
  12 policy version
  13 binding generation
  14 monotonic per-session sample sequence
  15 provider observed-at Unix milliseconds (decimal integer)
  16 latitude_e7 signed integer
  17 longitude_e7 signed integer
  18 horizontal_accuracy_cm positive integer
  19 provider/source code
  20 session-issued anti-replay context/nonce/version
```

The server must decide and enforce the final 20-field format exactly. Use lowercase canonical UUIDs; no floating decimals, locale, whitespace, exponent notation or timezone strings. Bound integer ranges in both languages and PostgreSQL; E7 resolution is ~1.1cm at equator and must not be misrepresented as physical GPS accuracy. A provider location with no reliable observation timestamp or accuracy is not suitable for a green live marker.

**Android**: immutable sample UUID, strictly increasing sequence, source GPS observation metadata from platform; use P-256 Keystore key or an equally strong approved session-bound proof; sign the exact canonical bytes (ECDSA SHA-256), DER JCA->raw64 for server. Do not sign a GPS sample with the enrollment challenge domain.

**Server**: reject malformed input early; enforce request body size; authenticated actor and allowed session/credential; reconstruct bytes from normalized scalars, do not blindly trust submitted `transcript` bytes; verify raw64 with stored SPKI, current revoked/generation state and server lease. Recheck exact unit/deployment/vehicle authority on ingest. No signature verification can authorize expired or stopped session.

**Timestamp skew and provider staleness**: use trusted server `received_at` and bounded provider `observed_at`. A client's wall clock may be wrong; compare observed elapsed-realtime source where Android provides it and detect stale cached positions. Define source-specific skew tolerances and stricter freshness checks; do not accept future-stamped points to lengthen TTL. Use server time for expiry and read-time freshness. If a phone reports mock/suspect location flags, do not label it verified physical movement; reject/flag per documented policy. GPS spoofing cannot be definitively prevented by client software.

**Sequence**: accept only `sample.sequence > session.accepted_sequence` and timestamp is not older than stored latest; transactionally advance both and upsert one latest row. Enforce sample rate and no unrealistic leaps as *quality flags*, not as unreviewed emergency routing logic. Reject >1 simultaneous per-session in-flight buffer if that avoids reordering.

### 12A.9 Sample ingestion: exact atomic algorithm

Implement using an actual trusted server pathway that verifies the signature and then invokes a narrow transactional private ingestion routine. The SQL routine must not accept bare client `signature_valid=true`. Sequence for each sample:

1. Parse body with strict schema and bounded 1 request, not an unbounded array/batch.
2. Authenticate JWT; obtain trusted actor.
3. Resolve session by opaque UUID *without leaking foreign existence*.
4. Check state `SHARING`, lease, absolute maximum, consent/policy version, organization, REAL incident, current DRIVER episode, actual deployed vehicle, credential generation and revocation.
5. Build canonical bytes and verify signature with registered SPKI, using trusted snapshots. Ensure session ID/nonce cannot be taken from an old revoked session.
6. In DB TX lock session then current latest row (consistent lock order across STOP, SAMPLE, RENEW).
7. Revalidate all current authority/time and the proof result's claim binding via a trusted server-only path. Reject STOPPED/REVOKED/LEASE_EXPIRED and out-of-order sequence.
8. Reject invalid quality, lat/lon bounds, impossible observed timestamp, stale cached provider fix and samples from SIM/manual NAV. Do not accept user-supplied `source=GPS` as its own proof; store what can be truthfully known.
9. Update `accepted_sequence` and `last_sample_at` and upsert exactly one latest vehicle location with `received_at` server time and an owner-approved bounded `expires_at`.
10. Commit and return only sequence, server-time, freshness/receipt metadata. **Never echo precise lat/lon in public logs or generic receipts.**
11. On transient retry, exact frozen UUID+hash can recover accepted/nonaccepted result; do not silently accept a new position under the old operation UUID.
12. No history table, no recent-samples query, no trail rendering, no offline backlog or durable GPS queue.

Document performance budget and rate limits (per session, per user, per organization); avoid read/write amplification and uncontrolled Edge costs.

### 12A.10 STOP and revocation: race-free algorithms

Required dedicated STOP/LEAVE semantics:

```text
Android STOP button:
  1. state = STOPPING_LOCAL immediately;
  2. unregister location callback + cancel in-flight sample scheduler;
  3. remove visible sharing state and clear in-memory last observation;
  4. freeze immutable STOP UUID / original session identity;
  5. stopForeground and stopSelf safely, return user-visible stopped;
  6. attempt server STOP with bounded retry, display server ACK or UNKNOWN;
  7. do not resume GPS because retry failed.
```

```text
Server STOP transaction:
  acquire session lock;
  validate actor OR separately reviewed emergency revoker policy;
  accept same original STOP UUID idempotently;
  record state STOPPED/REVOKED and server stop time;
  invalidate active lease and any binder generation as applicable;
  make latest position unreadable immediately and delete current
  raw latest position where legal/possible;
  commit original command receipt without raw coordinates.
```

If the server receives a SAMPLE just before STOP, ordering determines whether it was accepted; if STOP commits first, the late sample must reject. If STOP was initiated offline, server may still see the last accepted point until lease and visibility expire, so client must never claim remote confirmation until it exists. Implement a short server lease as bound on that risk, not a replacement for a valid STOP request.

`LEFT_VEHICLE` must also drop the phone→vehicle binding or invalidate its generation according to approved handover policy; it must not simply stop local location callback while leaving server sharing active. On logout, org switch or missing permissions, prioritize stopping local acquisition immediately and invalidate corresponding session when online. Do not silently restart on boot/process recreation; if the OS kills FGS, server lease expiry must stop accepting positions independent of a STOP packet.

### 12A.17 SQL concurrency, deadlock and deterministic lock order

Codex must document and implement a single consistent lock order, adjusted to actual tables, covering:
`credential -> binding slot -> session -> latest position -> receipt`, or a justified canonical alternative consistent with PR #96 existing CLAIM/revoke locks. If #96's existing order conflicts with the proposal, **adapt to #96** rather than introducing a deadlock cycle.

- A STOP must win against delayed finalize/renew/sample when it commits earlier.
