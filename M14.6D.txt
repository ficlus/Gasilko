## 2. M14.6D objective

Implement deterministic operational effects for SIM training.

The simulator must support:

- explicit action execution;
- resource consumption;
- water supply relationships;
- bounded suppression effects on existing hazard models;
- configurable simulated resource capabilities;
- operational result reporting;
- event/timeline history;
- map visualization;
- safe recovery from interrupted operations.

The user should be able to issue an operational task, observe simulated execution and see its effects.

The software must never treat a movement command alone as a physical action.

**COMMAND INTENT != EXECUTION != PHYSICAL EFFECT**

Conceptual states:

```text

READY
ACTIVE
BLOCKED
COMPLETED
```

- acting resource;
- action type/version;
- target;
- operation UUID;
- simulation clock;
- state;
- start/end information;

Separate the existing recipient assignment state from simulated physical execution state.

Preserve manual recipient acknowledgement requirements where applicable.

## 6. Resource capacity model

Create simulated resource inventory separate from permanent organizational inventory.

Conceptual properties:

```text
resource_id
scenario_id
water_capacity_l
water_remaining_l
pump_capacity_lpm
operating_flow_lpm
supply_state
consumption_state
version
```

Not every resource must support every property.

Use capability definitions.

Examples:

- Tanker: stored water capacity.
- Pump: bounded flow capability.
- Hydrant: potential external water source.
- Portable tank: simulated reserve.
- Crew: personnel resource, not automatically a water carrier.

Do not modify permanent resource definitions.

Do not invent physical capacity for a real hydrant.

Instructor-configured exercise capacities must be visibly marked as simulation parameters.

Preserve provenance.

## 7. Water supply graph

Implement explicit directed simulation water connections.

Concept:

```text
HYDRANT / RESERVOIR / TANKER
             |
         SUPPLY EDGE
             |
          PUMP/UNIT
             |
       SUPPRESSION ACTION
             |
         HAZARD MODEL
```

Each active connection should record:

- source;
- consumer;
- source type;
- maximum simulated flow;
- connection state;
- created/ended time;
- actor/operation;
- version.

Avoid creating an unrestricted arbitrary graph.

Prevent:

- invalid self-connections;
- invalid cross-scenario references;
- accidental directed cycles;
- duplicate active connection where prohibited;
- resource use after release;
- phantom unlimited water from finite tanks.

Allow multiple consumers where resource policy permits.

Do not interpret incident hydrant linkage alone as an active physical connection.

## 8. Consumption algorithm

Use deterministic simulation-clock deltas.

For each active bounded action:

```text
requested_liters =
  requested_flow_lpm * delta_seconds / 60
```

Actual delivered quantity is limited by:

- remaining source inventory;
- active connection;
- source/consumer flow capacity;
- resource availability;
- valid execution state;
- remaining action duration;
- configured training constraints.

Prevent negative inventory.

Never consume more water than exists in a finite resource.

For continuous/infinite scenario sources, require an explicitly configured simulation policy.

Do not assume real hydrants have infinite capacity or known delivery pressure.

Record actual delivered quantity, not merely requested quantity.

Use stable numeric precision/rounding rules so replay is deterministic.

The same SIM time step must not consume resources twice.

## 9. Suppression effects

Integrate with existing M14.6C hazard cells.

Create a deterministic, bounded suppression effect.

The effect may depend on:

- actual simulated water delivered;
- configured nozzle/action efficiency;
- target geometry;
- distance/coverage;
- current fire intensity;
- duration.

Do not model exact real firefighting hydraulics.

Do not present training calculations as certified engineering values.

Suppression should reduce or modify existing fire-state values according to documented bounded equations.

Effects must not:

- increase water inventory;
- create negative fire intensity;
- corrupt hazard JSON;
- bypass hazard version/history;
- silently rewrite instructor source templates;
- change real-world hydrant status.

Existing wildfire/structure-fire progression remains authoritative.

Apply operational effects in deterministic order relative to the existing five-second hazard steps.

Explicitly define this ordering in documentation.

## 10. Target and position guards

A resource must not extinguish a fire from an arbitrary location.

Validate the training action's target and source position.

Use authoritative SIM positions and existing navigation state.

No fabricated GPS.

No sector centroid used as physical source location.

No unlimited-distance effects.

A resource must have a valid execution position and supported capability before applying a spatial effect.

If the target is unreachable or conditions are not met, report BLOCKED or an equivalent explicit state.

Movement into an area does not automatically authorize suppression.

## 11. Simulation autonomy

- prepare resources;
- begin a configured effect;
- consume simulated resources;
- report progress;
- report depletion;
- report BLOCKED/UNABLE;
- finish execution when the model's conditions are met.

Avoid infinite retry loops.

Do not bypass existing command roles.
