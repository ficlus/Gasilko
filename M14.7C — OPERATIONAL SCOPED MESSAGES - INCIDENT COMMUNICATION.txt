02. DOMAIN GOALS / MUST HAVE / NON-GOALS
=======================================================================

MUST:
  A. Web commander can compose, scope, send, browse and explicitly correct
     a message within an incident using a confirmed server operation.
  B. Authorized Android responder can read applicable messages and send
     messages using the existing authenticated repository/offline pattern.
  C. INCIDENT / ORGANIZATION / UNIT audiences are represented with exact
     canonical IDs and constrained by current membership/participation/
     command/crew episodes.
  D. All message bodies and revision histories are durable, scoped, ordered,
     append-only, paginated and fully audit attributable.
  E. Exact duplicate requests are idempotent; unknown network responses are
     reconciled using the original operation/message UUID.
  F. Scoped message changes use B1 authoritative refresh protocol and B2
     private hint transport with M10 optional generic notifications; never
     put body text into generic push, broadcast or incident-wide timeline.
  G. Account/org/incident switch, incident lease expiry and confirmed access
     revocation hide protected content while preserving unsent local intent.
  H. Slovenian and German UI with default safe wording, accessible operation,
     and clear distinction between SENT / PENDING / FAILED / UNSENT.
  I. Migrations forward-only, source-only, with documented human rollout.

SHOULD:

     responder read or accepted anything.
  K. Efficient concurrent pagination and modest capped offline caching.
  L. Safety warning: "Operational messages are not command acknowledgments";

MUST NOT:

03. DOMAIN IDENTITIES AND AUTHORIZATION TERMINOLOGY
=======================================================================

Distinguish these UUID identities:
 - incident_id: canonical incidents UUID;
 - actor_user_id: derived from auth.uid(), NEVER trusted from client;
 - acting_organization_id: explicit valid active exact membership;
 - incident_participation_id / participant organization;
 - unit_assignment_id: deployed incident unit episode, NOT inventory unit
   UUID, NOT vehicle UUID, NOT crew person's profile ID;
 - message_id: stable UUID (generated before offline send);
 - operation_id: separate immutable command receipt UUID;
 - supersedes_id: prior message within same incident and same audience
   identity (if correcting);
 - change revision/event sequence: server-created incident aggregate
   revision and timeline sequence, NOT Android timestamps.

No separate "chat members" table or chat roles. Authorization derives
from the EXISTING active membership, incident participation, effective
command hierarchy, unit assignment and crew episodes. Administrative
organization membership alone is not incident command authority.

Server must verify exact actor/org/incident target on BOTH writes and reads,
and recheck under existing command lock/permission conventions for writes.
Use existing private.can_read_incident, private.has_incident_capability,
locked org/profile helpers, incident receipt and participation contracts
after checking their precise signatures.

For FINAL/CLOSED historical read, follow current incident archival rules
and preserve immutable messages, but never broaden archived audience to
anyone who later gains general org membership. If no approved historical
scoped access policy exists, provide a strictly conservative policy and
document the limitation; do not default to full-incident visibility.

04. AUDIENCE AND SEND/READ CAPABILITY MATRIX
=======================================================================

Implement an explicit source- and documentation-backed matrix, adapted
to real domain capability names and role relationships.

INCIDENT audience:
 - target is the specific incident; no audience_org_id/unit_assignment_id;
 - read only by users with active approved incident-wide read capability
   according to canonical incident participation and visibility; avoid
   allowing an unrelated agency to read more than the SPEC authorizes;
 - send conservatively by effective incident commander/deputy or explicitly
   delegated incident-wide communication capability; do not infer authority
   from organization ADMIN/MANAGER or from merely reading incident;
 - if owner approves wider participant posting later, add a deliberate
   capability and spec revision, not an implicit open chat.

ORGANIZATION audience:
 - audience_org_id required; must be an ACTIVE participating organization
   linked to that incident; unit_assignment_id NULL;
 - reader must currently have that exact active org membership AND current
   incident participation/authorized command relationship;
 - sender may address own active participating org if currently authorized
   member/responder; cross-org organization announcements require explicit
   superior incident command capability and still must respect target
   recipient scope and sender privilege;
 - an IC may issue an authorized message to a participant org without
   acquiring that org's general organization records or membership rights;
   validate the relevant command delegation and recipient participation
   before allowing this path.
 - different orgs in the same incident cannot read one another's private
   messages merely because both participate.

UNIT audience:
 - unit_assignment_id required; must belong to same incident; audience_org_id
   NULL or normalized to verified unit owner only if current spec requires;
 - user must be current member of that deployment's crew, effective unit
   leader, or authorized commander over the unit as derived from the REAL
   command tree; unrelated responder and released-episode users denied;
 - sending to the unit requires same validated scope (or an effective
   superior command scope), NEVER any arbitrary unit UUID;
 - a unit leader is not automatically commander over another unit;
 - if a unit is reassigned/released, explicitly determine whether old
   messages remain historically readable by currently authorized actors;
   never allow stale offline scope to override a server revocation.

Send and read rights are distinct. Add a capability matrix to documentation
for current IC, deputy, agency commander, sector commander, unit leader,
crew responder, org admin without incident role, unrelated org member,
SUSPENDED, PENDING_APPROVAL, historical/released participant. Tie every
ALLOW to an existing helper/canonical role predicate, not an invented title.

Default DENY for ambiguous roles or missing command hierarchy information.

05. SQL DATA MODEL — USE CANONICAL ENTITY WHEN AVAILABLE
=======================================================================

Inspect all migrations: if a suitable existing `incident_messages` table is
present, extend it minimally. Otherwise create an additive forward migration
AFTER current merged migrations, conceptually:

public.incident_messages
  id UUID PRIMARY KEY
  incident_id UUID NOT NULL
  sender_user_id UUID NOT NULL
  sender_acting_org_id UUID NOT NULL
  audience_kind TEXT NOT NULL CHECK IN ('INCIDENT','ORGANIZATION','UNIT')
  audience_org_id UUID NULL
  audience_unit_assignment_id UUID NULL
  body TEXT NOT NULL
  supersedes_id UUID NULL
  sent_at TIMESTAMPTZ NOT NULL DEFAULT server_clock
  version BIGINT NOT NULL DEFAULT 1
  changed_revision BIGINT NOT NULL
  operation_id UUID NOT NULL
  status_code TEXT (only if needed for append-only correction/retraction
                    projection; not a second mutable message lifecycle)

Constraints/invariants:
  - INCIDENT: both target columns NULL;
  - ORGANIZATION: exactly org target, unit target NULL;
  - UNIT: exactly unit assignment target, org target NULL;
  - trim(body) nonempty and char_length(body) <= 4000;
  - optionally a conservative byte cap as defense against abuse, WITHOUT
    accidentally reducing the accepted four-thousand-character contract
    for normal Unicode text;
  - FK target must belong to same incident: composite FK or locked
    trusted validation, not an unchecked ID equality assumption;
  - sender profile FK, incident FK, organization/participation identity;
  - immutable author/scope/body/created time once committed;
  - supersedes_id same incident and SAME audience identity, and previous
    message is authorized for correction; avoid cycles, double supersession
    and cross-scope laundering;
  - no hard delete; RESTRICT historical FK deletion;
  - stable server revisions and monotonically ordered feed identities.

Suggested indexes:
  (incident_id, sent_at DESC, id DESC)
  (incident_id, audience_kind, audience_org_id, sent_at DESC, id DESC)
  (incident_id, audience_kind, audience_unit_assignment_id,
         sent_at DESC, id DESC)
  (incident_id, supersedes_id) WHERE supersedes_id IS NOT NULL
Avoid premature JSONB GIN indexes or unbounded full-text indexing.
No index for a query not implemented in this milestone.

If existing version/revision schema differs, adapt with an explicit
mapping. Do NOT blindly create a duplicate sent_at/created_at/version
concept or add `incident_id` foreign keys to unrelated hydrant tables.

07. IMMUTABLE OPERATION RECEIPT AND COMMIT PATH
=======================================================================

A message send is a canonical incident mutation, not a direct INSERT
from Web/Android. Use the M14.1 receipt helper and existing lock order.

Conceptual RPC:
  incident_message_send(
    p_incident_id UUID,
    p_acting_organization_id UUID,
    p_operation_id UUID,
    p_message_id UUID,
    p_audience_kind TEXT,
    p_audience_org_id UUID DEFAULT NULL,
    p_audience_unit_assignment_id UUID DEFAULT NULL,
    p_body TEXT,
    p_expected_incident_revision BIGINT DEFAULT NULL
  ) RETURNS permitted message DTO / accepted command receipt

Actual signature MUST follow current repo migration conventions; do not
assume this function already exists, and do not introduce breaking default
arg ordering in PostgreSQL. If existing command framework requires an
expected revision, use it and keep stale conflicts explicit. If normal
chat concurrent writes can safely use incident row lock with snapshot
revision rather than a stale client expected version, document choice
rather than forcing false frequent conflicts.

Successful transaction should, under existing canonical sorted locks:
  1. Read exact existing operation receipt by operation UUID.
  2. If exact same actor/org/action/normalized payload, recheck current
     permitted visibility as canonical replay policy requires and return
     committed result; do not emit duplicate message/notification/change.
  3. If UUID is reused with different payload/scope, OPERATION_REUSED.
  4. Revalidate ACTIVE actor, organization membership, incident active
     participation, legal incident lifecycle and target audience authority
     within the same transaction.
  5. Validate UTF-8 body, normalized line endings, max 4000 characters,
     dangerous control chars, no HTML interpretation in clients.
  6. Validate message ID not already bound to conflicting content;
     no client-supplied created_at or changed_revision authority.
  7. Acquire canonical incident mutation lock and target episode locks.
  8. Allocate one incident revision and appropriate source timeline
     evidence following exact current helpers; do not manually bump
     unrelated task versions.
  9. Insert immutable message row(s), audit provenance, operation receipt
     and authorized change descriptor(s) in SAME DB transaction.
 10. If M10 notification event is applicable, enqueue via existing
     durable notification mechanism in transaction with deterministic
     source ID. Actual push occurs separately AFTER commit.
 11. Return authoritative message ID, scope, server sent time and revision.

No external network requests, Realtime subscription or FCM delivery inside
locked mutation transaction. Atomic rollback must leave no partial
message, revision, audit or receipt.

Preserve canonical timeline sequencing. Do not put confidential text
or target IDs from private audiences into the shared incident timeline.
If the general incident append helper necessarily publishes shared event
metadata, use a safe audience-aware event or a deliberately redacted generic
event with SQL-filtered visibility, not client-side hiding. Explain exactly
what is visible and why.

08. MESSAGE CORRECTION / RETRACTION
=======================================================================

The M14 SPEC requires APPEND-ONLY corrections, not editable chat rows.

Conceptual RPC:
  incident_message_correct(
    p_incident_id UUID,
    p_acting_organization_id UUID,
    p_operation_id UUID,
    p_message_id UUID,
    p_supersedes_id UUID,
    p_body TEXT,
    p_expected_parent_version BIGINT
  ) RETURNS immutable correction message DTO

Required behavior:
  - New UUID, new receipt, new immutable row, supersedes original.
  - Original content remains in restricted audit/history for authorized
    historical readers, not silently overwritten or deleted.
  - Same incident/author or explicit incident command ability to correct;
    commander may need additional reason and auditing when correcting
    another sender's message; by default restrict correction to original
    sender and preserve privilege boundary.
  - Original audience identity is frozen. Cannot "correct" a unit-private
    message into incident-wide broadcast, or vice versa.
  - Normal user UI shows newest authorized revision as current, with
    "corrected" indicator and accessible history for permitted roles.
  - Concurrent corrections to one parent resolve deterministically:
    one succeeds; the other gets STALE_VERSION / ALREADY_SUPERSEDED.
  - Retracting content, if required by approved repo semantics, is
    append-only tombstone/correction with reason and retained audit,
    never an unrestricted SQL DELETE.
  - If corrections are not specified for an archived CLOSED incident,
    prohibit them after terminal status instead of silently editing
    immutable closed history.
  - No automatic post-send editing / "undo" against authoritative server.

If a previous correction is authorized, specify whether the next version
links directly to immediate predecessor and prevent multiple active heads
in the correction chain. Use unique constraints/transaction locks rather
than merely checking client state.

09. READ RPCS, PAGINATION AND PRIVACY-SAFE DTOS
=======================================================================

Proposed endpoints (names only illustrative):
  incident_message_page(
    p_incident_id,
    p_acting_organization_id,
    p_audience_kind OPTIONAL,
    p_audience_scope_id OPTIONAL,
    p_before_sent_at OPTIONAL,
    p_before_id OPTIONAL,
    p_limit DEFAULT 30
  ) -> {messages[],next_cursor,has_more,server_revision,schema_version}

  incident_message_get(
    p_incident_id,
    p_acting_organization_id,
    p_message_id
  ) -> one authorized immutable or corrected projection

ALL responses are filtered in SQL for current actor and exact audience.
A user requesting "ALL" sees only a UNION of the scopes they may read;
never return raw joined hidden messages and count on UI filtering.

Keyset order:
  ORDER BY sent_at DESC, id DESC
Cursor rule:
  (sent_at, id) < (before_sent_at, before_id)
Never OFFSET, never trust a timestamp alone to break ties. Prefer
server-generated sent_at; client observed_at is not message ordering.

Bind range 1..50/page. Snapshot and total-size caps apply as in B1:
avoid loading unlimited messages into one 3MiB incident projection.
If there is a pending local unsent message, keep it separate from server
rows; rendering both does not make the local row server-confirmed.

Separate "current message" (latest correction) and "history" reads:
avoid exposing bodies of superseded/retracted versions to users whose
current audience permission no longer permits them. Do not return
another audience's message in message correction linkage.

Do not allow arbitrary text search across all incident organizations.
Search, if included, must be bounded AND SQL audience-scoped.

For absent/inaccessible messages, use the canonical uniform NOT_FOUND
pattern to avoid message existence enumeration.

17. MESSAGE SAFETY AND CONTENT POLICY IN APPLICATION
=======================================================================

Messages are short operational notes. They may contain personal data,
so minimize exposure:
 - server validates bounded body and strips/rejects forbidden control
   characters; preserve intended normal line breaks;
 - no SQL/string concatenation with user input; parameterized RPC;
 - never render content as unsafe HTML or embedded executable markup;
 - private bodies absent from shared timeline, push, broadcast payloads,
   analytics, crash logs and error response details;
 - do not suggest sensitive medical/patient details in examples;
 - do not expose sender profile records outside the read projection;
 - no data mining/cross-scope full-text search;
 - retraction/correction preserves audit but hides a superseded public
   display appropriately, without erasing retained legal history;
 - prevent extremely rapid spamming using bounded writes and existing
   server-side operational limits if available; avoid creating a
   second rate limiter/service.
 - messages are not an alternative to emergency radio communications.

REAL vs TRAINING: use same permission model but clearly show training
label, prevent SIM-generated messages from appearing as genuine human
communication or from triggering REAL notification recipients.

19. CONCURRENCY / TIMESTAMPS / REVISIONS
=======================================================================

- Server sent_at controls ordering, not phone clock.
- For same timestamp use message UUID tie break, no OFFSET.
- Concurrent sends from different authorized actors are both retained,
  each separate incident revision/receipt under canonical locking.
- Client's stale revision may be advisory for normal send if command
  framework permits; correction needs a version/head check.
- A duplicate operation_id does not create two messages or notifications.
- Lost response yields UNKNOWN until canonical receipt or bounded
  authoritative read resolves it; never assume 500 means no commit.
- Current incident revision and timeline sequence are not identical
  to message_id, created_at, or local queue insertion index.
- B1 changes and Room cached message version apply under same durable
  cursor advancement rule; no cursor commit ahead of message state.
- Shared Realtime hint delivery is best effort, never source of truth.
- If two message edits target same latest message, one becomes explicit
  stale conflict, NOT silent last-writer-wins.

20. FAILURE MATRIX — IMPLEMENT ALL APPLICABLE PATHS
=======================================================================

A. Network absent BEFORE send:
   keep scoped DRAFT/QUEUED, user sees no SENT success.

B. Server commits but HTTP response lost:
   identical operation UUID replay/receipt lookup, never duplicate.

C. Message commit succeeds but notification enqueuing fails in same
   transaction:
   either whole transaction rolls back or deterministic enqueue
   occurs in an approved deferred reliable path; do not claim delivery.
   Existing M10 transaction pattern takes precedence.

D. FCM provider fails AFTER commit:
   durable message intact; foreground fetch eventually sees it.

E. Realtime packet duplicated/out of order:
   coalesce and fetch by server cursor; no duplicate rendering.

F. Current org membership revoked:
   immediate hide on confirmed denial, prevent future send,
   retain protected unsent draft evidence per account rules.

G. Unit member leaves / unit is reassigned:
   refresh authorization; old UNIT-private message hidden if no longer
   permitted, even if old Room row physically remains until safe cleanup.

H. Incident scope changes mid-pagination:
   reject stale page, hide unauthorized cached state, restart permitted
   snapshot or page; no mixed-audience pages.

I. Correction races another correction:
   one committed immutable successor; other STALE_VERSION.

J. Reconnect with old message page cursor:
   do not silently skip newly appended messages; use refresh at head
   plus keyset history and documented fence/watermark semantics.

K. Message body too large/empty:
   deterministic validation; preserve editable draft, no success.

L. Another organization tries direct RPC:
   SQL-denied; no existence/content leakage in error.

M. Account switch during network result:
   late result must not write into active new account's Room/view.

N. Incident lease expired offline:
   body hidden; unsent intent preserved; verified online scope required.

O. Unsupported B2 Android Realtime dependency:
   rely on M10/foreground/WorkManager; do not fake WebSocket or edit Gradle.

P. Archive/terminal incident:
   read only when authorized; no new operational messages.

Q. SIM/TRAINING incident:
   labeled training; no REAL broadcast or notification audience.

R. Duplicate notification from same message:
   M10 deterministic source key prevents duplicate notification
   effects where existing architecture allows.

S. Server reports malformed audience:
   reject. Do NOT widen from UNIT to ORGANIZATION/INCIDENT.

T. Unexpected SQL/PLpgSQL error:
   return safe code; preserve draft/receipt evidence, avoid logging body.
