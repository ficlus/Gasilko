## 1. Primary objective

Turn the existing M14.5C training environment and M14.5D road-navigation system into a practical **autonomous, deterministic incident simulator**.

An authorized training operator should be able to:

1. Open a training incident.
2. Create/select simulated incident units.
3. Issue existing configured commands through M14.5A/M14.5B.
4. Prepare an actual road route through M14.5D.
5. Enable autonomous execution for a simulated unit.
6. Watch the virtual unit react to the command.
7. Observe the unit moving along the calculated road geometry.
8. See simulated acknowledgement and execution progress.
9. Accelerate or pause the scenario clock.
10. Inject delays, breakdowns, road-access problems and communication loss.
11. Stop, resume or override individual simulated units.
12. Inspect detailed simulation event history.
13. Run reproducible training exercises.

The simulation should work without Android devices, physical vehicles, real GPS or actual field responders.

**The simulation must remain completely separate from real operational execution.**

## 2. Mandatory architectural invariants

Preserve the governing principle:

**COMMAND INTENT != EXECUTION PLAN != TELEMETRY**

### Command intent

An M14.5A task says what must be done.

Example:

```text
Task:
  MOVE_TO
  Recipient: GVC-1
  Target: Hydrant H-000123
```

The task alone never moves the unit.

### Execution plan

An M14.5D NavigationSession contains the planned road route, distance, travel duration and routing provider.

Example:

```text
NavigationSession:
  assignment_id
  current_route_id
  route geometry
  estimated travel duration
```

The navigation session alone never moves the unit.

### Simulated execution

M14.5E introduces a separate simulation agent that can follow an already prepared route.

Example:

```text
SimulationAgentRun:
  incident_unit_id
  task_assignment_id
  navigation_session_id
  route_revision_id
  simulated_progress
  simulated_execution_state
```

### Simulated telemetry

The agent publishes explicit SIMULATED position observations into the existing M14.5C simulation position projection through an authorized backend-only pathway.

Never create ACTUAL_GPS observations.

Never infer that a real firefighter acknowledged a command merely because a virtual agent responded.

Never treat a simulated arrival as proof of operational arrival or safety.

## 3. Essential implementation boundary

M14.5E must make the simulator autonomous **without bypassing M14.5A or M14.5D human authorization**.

Existing M14.5A task transitions are bound to authenticated real users and contain actor references.

Existing M14.5D navigation execution also requires legitimate execution authority.

A virtual unit does not have a real authenticated human identity.

Therefore:

**Do not impersonate `auth.uid()`.**

Do not create fake users, fake JWTs, fake profiles or invented Unit Leader memberships.

Introduce an explicit trusted **SIMULATION_ENGINE** execution identity, used only for simulator-owned state and clearly classified simulation events.

For M14.5E MVP, distinguish:

```text
REAL TASK:
ISSUED

SIMULATED RESPONSE:
SIM_ACKNOWLEDGED
SIM_IN_PROGRESS
SIM_ARRIVED
```

The original assignment remains governed by M14.5A.

In the UI, display both concepts separately.

Example:

```text
GVC-1

Command:
MOVE_TO H-000123

Operational task status:
ISSUED

Simulation execution:
SIM_IN_PROGRESS

SIM location:
2.4 km along planned route
```

This is correct and intentional.

The simulator may exercise the command and visualization pipeline without forging human execution history.

If, after inspecting the complete existing task/audit model, a safe narrowly authorized first-class system-executor extension can be introduced without changing real-user semantics, it may be documented as a future extension.

**Do not make that extension a dependency for autonomous movement in this milestone.**

The primary implementation must remain functional using separate simulation execution state.

```text

```

Use existing UUIDs.

Do not identify agents by callsign or display label.

## 7. Simulation agent lifecycle

Implement an independent, finite, deterministic state machine.

Suggested lifecycle:

```text
IDLE
  ↓
COMMAND_DETECTED
  ↓
WAITING_TO_ACK
  ↓
SIM_ACKNOWLEDGED
  ↓
PREPARING_EXECUTION
  ↓
SIM_IN_PROGRESS
  ↓
SIM_ARRIVED
  ↓
SIM_COMPLETED
```

Additional states:

```text
SIM_BLOCKED
SIM_UNABLE
SIM_PAUSED
SIM_SIGNAL_LOST
SIM_CANCELLED
```

These are **simulation execution states**, not new values for M14.5A task assignments.

Do not modify the existing M14.5A task-status enum.

Transitions must have explicit rules.

For example:

```text
WAITING_TO_ACK -> SIM_ACKNOWLEDGED
SIM_ACKNOWLEDGED -> SIM_IN_PROGRESS
SIM_IN_PROGRESS -> SIM_ARRIVED
SIM_ARRIVED -> SIM_COMPLETED
```

The agent must not progress when:

- scenario is PAUSED or FINISHED;
- simulation guard is disabled;
- relevant assignment is cancelled/terminal;
- incident becomes terminal;
- unit is released/unavailable;
- route becomes invalid;
- another conflicting agent run owns the unit.

An interrupted run may enter SIM_PAUSED or SIM_BLOCKED with an explicit reason.

## 12. Road-following movement algorithm

Implement a deterministic route-progress algorithm.

The agent must move **along the actual stored road geometry**, not in a straight line from origin to destination.

For a route LineString:

```text
P0, P1, P2, ..., Pn
```

Precompute cumulative geographic segment lengths:

```text
L0 = 0

Li = Li-1 + distance(Pi-1, Pi)
```

Let:

```text
route_length = Ln
progress = traveled distance along route
```

Find segment i such that:

```text
Li-1 <= progress <= Li
```

Interpolate the position within that segment.

Use a robust WGS84-appropriate segment-distance calculation and safe interpolation.

Handle:

- zero-length segments;
- repeated coordinates;
- short segments;
- dateline/longitude wrapping;
- invalid or nonfinite values;
- endpoints;
- large provider geometries.

Do not treat geographic longitude/latitude as ordinary planar meters.

Do not add a full physics engine.

### Planned travel speed

Use the route's existing planned duration as the baseline.

Conceptually:

```text
baseline_speed_mps =
  route_length_m / planned_duration_s
```

Then apply the selected bounded simulation behavior profile.

Do not use the route geometry to infer an actual vehicle's speed.

The model is for deterministic testing, not physical vehicle dynamics.

### Per-tick progress

Conceptually:

```text
simulated_delta_seconds =
  elapsed_real_seconds * time_scale

distance_advance =
  simulated_speed_mps * simulated_delta_seconds

new_progress =
  min(route_length, previous_progress + distance_advance)
```

Adjust for failure modes, pauses and lifecycle.

All progress must be monotonic during normal movement.

No movement when simulation time is paused.

Never move backward merely because of a retry or delayed worker response.

Conceptually:

```text
simulation_clock

scenario_id
simulated_time
time_scale
last_advanced_at
tick_sequence
status
version
```

Default:

```text
time_scale = 1
```

Supported initial speeds:

```text
1×
5×
10×
```

The clock must be authoritative on the server.

The browser may display the simulated time but must not own it.

### Pause

When scenario is PAUSED:

- simulation time stops;
- autonomous movement stops;
- simulated ACK timers stop;
- failure timers stop;
- no catch-up movement accumulates.

### Resume

Resume from the persisted simulated time.

Reset the real-time advancement anchor.

Do not apply the entire paused wall-clock duration as movement time.

### Time scale change

Allow the authorized operator to change speed.

Take effect at a defined clock boundary.

Record an event.

Do not retroactively rescale historical movement events.

### Recovery after downtime

If the scheduler was unavailable for a significant period:

- do not teleport units over the entire elapsed wall time;
- apply a conservative maximum simulated-time increment per tick;
- mark the runner behind/stale if necessary;
- resume in bounded steps;
- display an operator-visible warning.

## 19. Response profiles

Create configurable simulation-only behavior profiles.

Initial profiles:

### NORMAL

- normal ACK delay;
- normal travel speed;
- successful arrival;
- optional completion delay.

### SLOW_RESPONSE

- longer ACK delay;
- delayed start;
- ordinary movement after response.

### NO_RESPONSE

- no simulated ACK;
- no automatic movement start;
- operator sees a clear attention state.

### BREAKDOWN

- movement begins;
- a deterministic fault occurs at a configured progress point;
- unit stops;
- simulation status becomes SIM_BLOCKED.

### COMMUNICATION_LOSS

- simulate communication/telemetry freshness failure;
- distinguish missing reported updates from actual virtual movement;
- do not claim a fresh observed position after contact is lost.

### ROUTE_BLOCKED

- simulated road execution stops at a configured route progress point;
- display route obstruction;
- wait for explicit operator intervention or permitted route replacement.

These are examples of data-driven simulation profiles, not new M14.5A Action Definitions.

Avoid hardcoded tactical command labels.

Keep profile parameters bounded.

## 22. Simulated task execution

After simulated ACK:

1. Agent enters a simulated execution state.
2. Agent checks that a valid route revision is attached.
3. Agent waits for configured start delay.
4. Agent begins advancing along the road geometry.
5. Agent publishes simulated positions.
6. Agent reacts to pauses/failures.
7. Agent reaches the route endpoint.
8. Agent records SIM_ARRIVED.
9. Agent may record SIM_COMPLETED after configured simulated delay.

Do not automatically update canonical M14.5A assignment status to COMPLETED.

Do not automatically call real M14.5D ARRIVE.

The training UI must show both:

- authoritative operational status;
- virtual simulation execution status.

A training operator can still use a real training account with legitimate execution authority to exercise the ordinary M14.5A lifecycle separately.

## 26. Failure injection

Allow an authorized training operator to inject controlled failures.

Initial supported events:

```text
SIM_BREAKDOWN
SIM_ROUTE_BLOCKED
SIM_SIGNAL_LOSS
SIM_NO_RESPONSE
SIM_HOLD
SIM_RESUME
```

Every injection must be:

- explicitly selected;
- validated;
- authorized;
- recorded;
- idempotent;
- scenario-scoped.

No arbitrary JavaScript or SQL execution from scenario inputs.

No arbitrary script upload or eval.

### Vehicle breakdown

Stop simulated route progress.

Set simulated speed to zero.

Display a simulated failure event.

Do not mark the permanent vehicle inventory as broken.

### Road blocked

Stop movement at the current progress point.

Do not alter actual OSRM road graph.

Do not modify road closure data in production.

Do not automatically reroute unless an authorized operator prepares/selects a suitable route through existing navigation functionality.

### Signal loss

Retain the last published SIM position with stale/lost-signal indication.

Distinguish:

- internal simulated movement state;
- last externally visible simulated observation.

Never publish fresh fake observations while displaying the data as unavailable.

## 28. Scenario pause, reset and finish

Integrate with existing M14.5C scenario lifecycle.

### Pause

Stops simulated clock progression.

Agent runs remain persisted.

SIM positions remain at their last authoritative observations.

### Resume

Continues eligible paused agent runs from their saved progress.

No catch-up teleport.

### Reset positions

Preserve M14.5C semantics.

Reset must not erase historical tasks, routes or simulation events.

Active autonomous runs must be stopped or superseded before resetting positions.

Do not silently resume the old route after reset.

### Finish

Stop all autonomous execution.

No further ticks should mutate scenario positions.

Navigation and task history remain intact.

Do not close the incident automatically.

For a completely fresh exercise, guide the operator to create a new training incident/scenario rather than deleting immutable history.

## 29. Concurrency and tick idempotency

A scheduled worker may be invoked twice.

An earlier invocation may overlap a later one.

The operator may also manually advance the scenario.

Protect against:

- duplicate ticks;
- duplicated ACK;
- duplicated arrival;
- double movement;
- replay after FINISHED;
- stale position overwrites;
- two workers advancing the same agent simultaneously.

Use:

- row/advisory locks following repository conventions;
- a monotonic scenario tick sequence;
- agent run version;
- expected position version;
- unique event identity;
- durable tick/operation receipt;
- atomic transaction per bounded unit of work.

If two workers race, only one should commit advancement for the same scenario tick.

A repeated identical tick must not advance the unit again.

Do not hold a database transaction across an external routing request.

There should be no routing request during an ordinary simulation tick.
