5. ARCHITECTURE / DATA FLOWS
================================================================================

Suggested boundaries (ADAPT TO ACTUAL CURRENT CODE, do not assert names):

Android Compose [driver opts in, selects eligible vehicle]
      -> Incident ViewModel / Repository
      -> authenticated START_SHARE command, original operation UUID
      -> server creates short-lived, versioned, actor-scoped session
      -> Android starts user-visible FGS(location) while app is foreground
      -> Android validated GNSS sample, no old coordinate backlog
      -> bounded authenticated WRITE_LATEST(position) RPC
      -> server revalidates current session + unit/org/actor + sequence
      -> one ephemeral per-deployment latest REAL observation
      -> narrow server-authorized bulk READ_CURRENT read model
      -> existing C3 / C1 Web/Android source-specific map presentation
      -> user STOP/LEAVE / server revoked / lease expired -> hide + stop

Realtime (if used): minimal revision/invalidation HINT ONLY.
No coordinates in the hint. Normal scoped authenticated bulk reads are
authoritative. Existing polling fallback stays.

Proposed on-wire state machines (adapt exact names):
  Sharing:
    NOT_ELIGIBLE / OFF / AWAITING_CONSENT / ENROLLING /
    ACTIVE / INTERRUPTED / STOPPING / STOPPED / REVOKED /
    LEASE_EXPIRED / OUTCOME_UNKNOWN
  GPS fix:
    NO_FIX / RECEIVED_UNVALIDATED / ACCEPTED_SERVER /
    REJECTED / EXPIRED / NOT_AUTHORIZED
  Viewer:
    CURRENT / LAST_KNOWN / UNAVAILABLE / LOCKED /
    OFFLINE_UNCERTAIN / SCHEMA_UNAVAILABLE

Consent is an app and server session approval separate from Android OS
runtime location permission. `ACCESS_FINE_LOCATION` by itself is not
a server sharing grant. A selected acting organization is not proof
of vehicle or command authority.

START_SHARE must be a true authenticated first-party user action,
with a caller-bound immutable request/operation_id/receipt; a later
lost response cannot start another duplicate active share. A cancelled
or revoked session must not be resurrected by retrying an old UUID.
If receipts are reused, preserve existing receipt table shape and
collision/mismatch behavior. Explicit first retry uses same exact
immutable request; do not silently rebase a frozen operation.

Stop must be effective locally immediately, even if network is down.
Offline revoke intent should keep only operation/session identifiers
(not coordinate trail), be durable/authoritatively reconciled in
existing D1 queue model if the type fits, and never drop merely because
network/server is unavailable. On server, honor an authenticated stop
even if incident controller permissions were revoked, provided the
actor can prove ownership of the share being stopped; stop must not
require now-missing controller authority.

Concurrent devices: single active producer LEASE per canonical deployed
vehicle+incident. Server should compare holder/generation/expiry and
reject stale attempts. New operator takeover requires visible deliberate
action, current authorization, audited metadata and immediate invalidation
of old session. Default: fail closed rather than automatic takeover.

Unit-release and incident close lifecycle should make sharing
non-uploadable and invisible immediately, even if no teardown packet
arrives. Avoid modifications of canonical incident commands solely to
start or stop location sharing; use authority predicates and scoped
invalidation.

9. OFFLINE, FAILURE, CONCURRENCY & PRIVACY EDGE CASES
================================================================================

Handle at minimum:
  1. Start RPC response lost -> receipt-first recovery / no duplicate share.
  2. GPS WRITE result uncertain -> next sample uses monotonic sequence;
     no backfilled trace.
  3. STOP offline -> local service stops NOW; revoke intent persisted
     without coordinates; no resurrection on reconnect.
  4. Server cannot verify authorization -> do not upload / fail closed.
  5. Org/incident/account switch -> local capture stops; no stale cross-
     scope UI sample or pending replays in wrong context.
  6. Driver leaves vehicle but phone remains running -> stop.
  7. Vehicle released, role lost, org removed, incident closed ->
     server refuses new samples, hides existing location immediately;
     local service stops on next safe authority check.
  8. Another authorized phone tries takeover -> exact generation,
     compare-and-swap, no dual green producers.
  9. Old device comes back -> stale session / sequence rejected.
 10. Device clock drift/future timestamp -> reject untrusted fix,
     do not make stale samples current.
 11. Android background start restrictions -> no stealth fallback.
 12. Device reboots/OS kills app -> no automatic sharing restart.
 13. GPS service loses permission/location provider -> local stop,
     safe UI warning, server lease eventually expires.
 14. Low quality location -> display source accuracy, never make
     a spoofed precise fix.
 15. Zero/NaN/WGS84 lat-lon confusion -> fail-closed validation.
 16. Two active incident contexts on one account/device -> enforce
     explicit single pairing/session policy, no accidental dual source.
 17. Offline lease expires during capture -> stop/deny uploads.
 18. Stop command races with queued GPS upload -> stop wins under
     server lock and session generation; old sample rejected.
 19. No incoming traffic after last sample -> physical retention
     still must be eventually enforced by approved cleanup.
 20. Read after consent withdrawn -> no exposure even if 15-minute
     last-known period was not exhausted.
 21. Same unit in TRAINING and REAL -> no SIM conversion.
 22. Position age computed from actual observed_at, not server read
     time, login, push hint or route creation.
 23. B1 gap/reset and D1 UNKNOWN do not lose task/attachment evidence.
 24. Web/Android older version -> capability absent is explicit and
     no secret field leaks; new client old server fails safely.
 25. No permission to see other unit precise GPS based solely on
     unit label visibility.

Privacy distinctions:
 - GPS capture while user's screen is OFF via a visible FGS is allowed
   only for the already user-started active, consented session; this is
   NOT stealth location monitoring or automatic location permission.
 - If the org's policy forbids personal-phone vehicle tracking,
   the capability remains DISABLED, not enabled by a code default.
 - Stop/opt-out must never keep displaying a last-known marker under
   the normal disconnected-GPS stale exception. They are different
   states: voluntary withdrawal vs temporary signal loss.
 - "No trail" includes analytics, operation receipts payloads,
   backend logs, retries, exception reports and unbounded local
   queues. Audit only bounded metadata for start/stop without
   longitude/latitude.
 - Trusted timestamp/accuracy and retention must be verifiable
   on server, not just visually assumed by Android.
 - Record server-owned generation, received_at and revision to
   prevent clock skew and replay.
