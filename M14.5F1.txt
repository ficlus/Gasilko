# CODEX IMPLEMENTATION PROMPT — M14.5F1
## Responsive Command Map & Incident View Switch

You are working in the existing **Gasilko** monorepo.

Implement **M14.5F1 — Responsive Command Map & Incident View Switch** as a focused, production-quality frontend milestone.

**Important:** This milestone establishes the responsive, map-first incident workspace. Direct RTS context commands, tactical object creation, and live command notifications belong to later milestones and must NOT be implemented here.

Create one focused PR. Do not merge it.

---

## 1. Product goal

The existing incident workspace is functional but too form-heavy and does not use available screen space effectively.

Introduce two explicitly selectable workspace modes:

1. **Klasični pogled** — the existing incident workspace with all current capabilities.
2. **Poveljniška karta** — a new, responsive, map-dominant workspace for operational command.

The user switches between modes using a clearly visible segmented control in the incident header.

The new mode must feel like the foundation of an RTS command interface: the map is the main working surface, while supplementary information is available through collapsible panels.

However, no existing authorization, incident, command, navigation, or simulation semantics may change.

## 4. Header view switch

Provide a clearly visible control in the header of an opened incident:

**Klasični pogled | Poveljniška karta**

Requirements:

- First visit defaults to **Klasični pogled**.
- Selection persists in `localStorage`.
- Use a stable, namespaced preference key, such as `gasilko.incident.workspace.view.v1`.
- The preference is browser-local, not an incident database field.
- Handle malformed or unavailable browser storage gracefully.
- Avoid SSR/hydration mismatches in Next.js.
- Keep the control accessible using mouse, keyboard, and touch.
- Keep the selected state obvious.
- The control must remain easy to access even when the incident workspace is scrolled.
- It must not be hidden inside an unrelated administrative dropdown.
- Mode switching must not trigger mutations or reload the entire browser page.
- Switching must not create/cancel tasks or restart/pause simulations.
- Switching back to Classic View must restore the normal existing layout.

Use the existing i18n/localization mechanism. Provide appropriate Slovenian and other already-supported locale translations.

Do not introduce hardcoded Slovenian strings into otherwise localized components.

## 5. Classic View — preserve existing functionality

The Classic View should remain visually and functionally as close as possible to its existing behavior.

## 6. New Command Map View

Create a dedicated, responsive map-first layout using existing incident/map components.

### Desktop layout

The map must dominate available screen space.

Recommended structure:

```text
┌─────────────────────────────────────────────────────────────────────┐
│ INCIDENT HEADER    Klasični pogled | Poveljniška karta             │
├──────────────┬───────────────────────────────────────┬──────────────┤
│              │                                       │              │
│ UNIT /       │                                       │ CONTEXT /    │
│ RESOURCE     │                                       │ DETAILS      │
│ ROSTER       │             LARGE MAP                 │              │
│              │                                       │ Tasks        │
│ Collapsible  │                                       │ Navigation   │
│              │                                       │ Selection    │
│              │                                       │              │
├──────────────┴───────────────────────────────────────┴──────────────┤
│ COMPACT MAP CONTROLS / STATUS — existing capabilities only         │
└─────────────────────────────────────────────────────────────────────┘
```

This is conceptual; adapt it to the existing components and styling.

Implementation requirements:

- Use a responsive CSS grid or equivalent layout.
- Main map column must use `minmax(0, 1fr)` or equivalent.
- Avoid horizontal overflow.
- Avoid unnecessary global maximum widths for Command Map View.
- Support large 1440p and 4K displays.
- Map should fill the available viewport height below persistent site/incident headers, without covering them.
- Use viewport-aware sizing and safe fallbacks.
- Do not impose one fixed `58dvh` map height across all screen sizes.
- Panels should have sensible minimum and maximum widths.
- Panel content must scroll independently when needed.
- Map must remain usable with either or both panels collapsed.
- Provide explicit, accessible panel open/close controls.
- Do not force large administrative forms into the always-visible map area.
- Provide access to existing functions through panel sections or links to Classic View.

### Panel defaults

Suggested behavior:

- Left roster: open on sufficiently wide displays.
- Right context panel: open when there is sufficient space and meaningful content.
- On narrower displays, panels should start collapsed.
- Prefer adapting to the actual available workspace width, not merely the physical device width.

The user must always be able to regain access to collapsed panels.

### Header and vertical space

Review the entire administration shell, not only the map component.

Do not leave the Command Map artificially constrained by an ancestor `max-width` or padding designed for forms.

Any wider layout styling should be scoped to the incident Command Map so unrelated administrative pages retain their existing appearance.

## 7. Tablet and mobile behavior

The Command Map must remain functional at narrow widths.

### Tablet

- Map remains the primary region.
- Supporting panels become collapsible overlays/drawers where appropriate.
- Only one obstructive panel should be open at a time on narrow layouts.
- Panels must be dismissible.
- Prevent overlay controls from trapping or blocking map access unintentionally.

### Mobile

- Map uses the full available content width.
- Appropriate viewport height: not a tiny map surrounded by stacked forms.
- Roster, context details, and supplementary controls open as compact drawers or sheets.
- Touch targets should be comfortable and accessible.
- Do not depend on hover.
- Do not depend on keyboard modifier keys for essential functionality.
- Respect device safe-area insets.
- Handle mobile browser dynamic viewport behavior.
- Avoid scroll trapping and accidental horizontal page scrolling.

Reuse existing design-system primitives if appropriate. Do not add an unnecessary drawer library.

## 8. Expanded map-focus mode

Provide a button such as:

**Razširi karto**

And a clear exit:

**Zapri razširjeni pogled**

Requirements:

- Enlarge the map to occupy as much of the available application viewport as reasonably possible.
- Hide or collapse nonessential side panels.
- Preserve access to the incident identity, view switch, exit control, and essential safety/status indications.
- Support `Esc` to exit.
- Return to the previous panel arrangement when leaving expanded mode.
- Avoid triggering the browser Fullscreen API unless it is already a supported pattern in this application.
- Avoid breaking page navigation, browser history, or accessibility.
- Map must resize correctly upon entry and exit.

The view switch in the incident header must remain accessible in expanded mode.

## 11. Security and operational invariants

Preserve all existing role checks and RLS-backed server authorization.

In particular:

- Organization administration roles are not interchangeable with incident command roles.
- Switching workspace modes never grants extra capabilities.
- Unauthorized users must not gain command controls through the new layout.
- Data visible in the new mode must be limited to what the existing application authorizes.
- Read-only incident participants must remain read-only.
- SIM data must remain clearly distinct from real incident telemetry.
- Never display planned routes as actual vehicle movement.
- Never simulate or invent live GPS data.
- Never bypass the existing task/command creation workflow.

Remember the established distinction:

**Command intent ≠ execution plan ≠ observed telemetry.**

This is a presentation milestone, not a change to the operational truth model.
