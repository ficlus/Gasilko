## 1. Product objective

Give incident commanders a coherent, visual overview of the actual incident command structure and enable authorized command-management workflows directly from **Poveljniška karta**.

The experience should resemble a tactical RTS hierarchy while respecting real fire-service incident authority.

Primary workflows:

1. Open a compact **Poveljniška struktura** panel.
2. See the incident commander, actual delegated roles, sectors and their responsible commanders.
3. Expand a sector to see its associated people, units/resources and tasks, where these relationships are supported by authoritative data.
4. Select a sector to highlight its actual COP geometry and associated visible units.
5. Right-click a sector or commander to see relevant authorized actions.
6. Open existing authorized assignment/delegation/transfer workflows in a compact UI.
7. Confirm an actual organizational change through the existing server-authoritative command model.
8. See confirmed changes reflected automatically through the F4 live refresh mechanism.

No drag-and-drop authority reassignment.

Do not create a parallel command hierarchy or a new permission model.

## 3. Critical architectural rule

**Organization hierarchy, incident command authority, operational sector membership, and task assignment are different concepts.**

They must not be conflated.

For example:

- A municipal or organizational administrator is not automatically the incident commander.
- An agency's leader is not automatically authorized to command all participating agencies.
- A sector commander only has authority within actual delegated scope.
- A vehicle appearing inside a sector polygon does not automatically belong to that sector.
- A task recipient is not necessarily a permanent member of the task's sector.
- A command post COP point is a map object, not an automatic source of command authority.

All displayed relationships must have an identifiable authoritative source.

If a relationship is not modeled, show **Unassigned / Not available**, or omit it.

Never fabricate hierarchy edges.

## 5. Visual hierarchy panel

Add a compact **Poveljniška struktura** panel or tab within Command Map.

Suggested presentation:

```text
VODENJE INTERVENCIJE
  └─ Vodja intervencije
       ├─ Namestnik / delegated role (if actually present)
       ├─ Sektor A — existing role and authority
       │    ├─ Authorized sector commander
       │    ├─ Assigned units/resources
       │    └─ Related tasks
       └─ Sektor B
            ├─ Authorized sector commander
            ├─ Assigned units/resources
            └─ Related tasks
```

The structure is illustrative, not an instruction to invent missing levels.

Render only levels that exist in the current incident command model.

Each node should show:

- Display name.
- Actual role or entity type.
- Active/inactive status where supported.
- Scope where meaningful.
- Number of associated resources/tasks when reliably derivable.
- Warning when a role is vacant or an authorized assignment is pending.

A node click must immediately highlight the relevant item in the hierarchy.

Do not fetch a complete organization directory merely to render the tree.

Use existing scoped incident DTOs and readers.

## 6. Sector interaction

Selecting a sector should:

1. Mark its node selected.
2. Highlight the corresponding existing COP sector geometry, if present and authorized.
3. Show its responsible command role.
4. Show linked units/resources and tasks only when the authoritative model supports those relationships.
5. Offer existing authorized actions.

The Command Map must remain stable:

- Do not remount MapLibre.
- Preserve camera unless the user explicitly chooses **Prikaži na karti**.
- Do not steal focus while a command modal is open.
- Do not cancel a current RTS unit selection merely because a sector was inspected.
- Do not confuse sector geometry with command scope.

If a sector has no geographic polygon, it should still exist in the hierarchy if it exists in the command model.

If a polygon exists without an authoritative command-sector association, show it as a COP geometry rather than manufacturing a hierarchy mapping.

- Change an authorized role holder.
- Revoke an existing delegation.

- View pending acceptance or handover.
- Open existing sector management workflow.

Do not invent RPC commands.

Do not use direct browser table writes.

Do not silently elevate an organization or agency administrator to incident command authority.

### Required interaction contract

For any modifying action:

1. Check current server-derived UI eligibility.
2. Open the actual existing command-management form or compact adapter.
3. Show affected role, scope, current holder and proposed change.
4. Perform the existing validation.
5. Require explicit confirmation.
6. Use existing server RPC and version/idempotency rules.
7. Wait for authoritative confirmation.
8. Refresh the existing incident context.
9. Render confirmed hierarchy state.

A right-click never directly transfers command or grants permission.

If the existing command workflow requires a recipient's acceptance, preserve that requirement.

Do not show a pending transfer as completed.

If an operation is too complex to implement safely in a compact drawer, open the existing Classic workflow prefilled where supported.

## 11. Scope-aware permissions

Server-side authorization remains authoritative.

The UI must enforce the existing M14.2 security model, including:

- Incident commander authority.
- Delegated/sector command scope.
- Agency participation boundaries.
- Cross-organization visibility rules.
- Read-only incident participant restrictions.
- Expiry/revocation of authority.
- Incident lifecycle restrictions.

A user who may read the entire hierarchy does not automatically have permission to modify all its nodes.

Never trust frontend flags as the sole authorization mechanism.

Avoid exposing unauthorized personnel or sector membership through broad search endpoints.

On definitive access loss:

- Close privileged modification drafts.
- Clear inaccessible hierarchy data.
- Unsubscribe/stop relevant incident refresh work through existing scope lifecycle.
- Prevent stale context menus from issuing mutations.

## 17. Important invariants

Keep the existing distinction:

**COMMAND INTENT != EXECUTION PLAN != OBSERVED TELEMETRY.**

Also preserve:

**ORGANIZATION ROLE != INCIDENT COMMAND ROLE.**

And:

**SECTOR GEOMETRY != SECTOR COMMAND AUTHORITY.**

A visual connection in the hierarchy must represent an actual modeled relationship.
