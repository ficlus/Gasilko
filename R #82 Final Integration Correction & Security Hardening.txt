## 2. Priority 1 — Action Definition version identity

Inspect:

`android/app/src/main/java/si/gasilko/app/feature/incidents/IncidentScreen.kt`

Currently the issue-task editor finds a catalog row, immediately extracts its configuration, then attempts to read the action version ID from the configuration:

```kotlin
val selected = catalog.find {
    it.text("id") == definition
}?.obj("configuration")
```

Later:

```kotlin
put("action_version_id", selected!!.text("id"))
```

Review the actual authoritative `operational_action_catalog` response.

Establish whether the immutable action version ID exists on the catalog row, the configuration or another specific field.

Do not assume the configuration contains identity metadata.

Use the correct canonical Action Definition VERSION ID in `incident_issue_task`.

Keep separate variables for:

- selected catalog row;
- immutable action version ID;
- editable/display configuration.

Never submit a blank, stale or unrelated version ID.

Validate the immutable action version against the selected configuration and recipient eligibility.

Ensure issued tasks reference the same definition/version displayed in the Android review UI.

## 3. Priority 2 — Offline dependency version correctness

Inspect:

`IncidentRepository.kt`

Especially `request()`, `send()`, `transition()` and the durable queue.

Current dependency preparation derives the next expected version using the parent's originally expected version plus one.

Confirm this against the actual `incident_transition_task_assignment` receipt and version contract.

Do not assume a single increment unless the authoritative RPC explicitly guarantees it for every successful transition and idempotent replay.

Prefer the authoritative confirmed assignment version.

If the existing receipt lacks this value, use an authorized read/reconciliation before preparing the dependent request.

Preserve:

- original operation UUID;
- immutable request once prepared;
- canonical expected versions;
- correct ACK → START → COMPLETE dependencies;
- safe offline persistence;
- no out-of-order sends;
- no silent version rebasing after dispatch.

Do not regenerate an operation UUID for a request with an unknown outcome.

When the parent was definitively rejected, do not submit its dependent operation.

Distinguish definitive rejection, transport ambiguity and authoritative success.

Verify that independent task assignments can progress without being unnecessarily blocked by an unrelated failed assignment.
