## 1. Confirmed user-facing defect

The user encountered the following issue:

1. Opened SIM scenario library.
2. Copied an existing wildfire scenario into a DRAFT.
3. Edited the scenario.
4. Attempted "Save Draft".
5. Received a generic failure and an unconfirmed-operation warning.
6. Could no longer open any scenarios in that browser tab.
7. Restarted the Next.js server.
8. The original tab remained blocked.
9. Opened a fresh browser tab.
10. Scenarios became accessible again.

Source investigation identified:

`web/features/incidents/useTemplateMutation.ts`

stores pending requests in `sessionStorage` under an account/organization/surface-scoped key.

`web/features/incidents/TemplateLibrary.tsx`

uses:

`busy = loading || mutation.busy || !!mutation.pending`

and its normal scenario `open()` method checks `busy`.

Consequently, a single unresolved write can block all scenario reading/opening in the current tab indefinitely.

This is a confirmed UX/state-management defect.

The original server-side reason for the SAVE failure has NOT been conclusively identified.

Do not assume the underlying failure was necessarily a missing migration, invalid data, authorization or network outage.

Investigate the current implementation and correct the recovery model without sacrificing idempotency.

# PART A — CRITICAL SAVE/RETRY RECOVERY

## 4. Correct global UI blocking

A pending template mutation must not indefinitely prevent unrelated READ operations.

Separate:

- read loading state;
- editor loading state;
- active mutation execution;
- unresolved mutation;
- current template write lock;
- unrelated template navigation;
- unsaved local changes.

Do not use one broad boolean to disable the entire library.

While a template SAVE is unresolved:

- Allow viewing the library.
- Allow reading existing templates when safe.
- Keep the unresolved operation visible.
- Preserve the original operation UUID and payload.
- Prevent incompatible writes to the affected template.
- Prevent accidental duplicate CREATE, COPY or START.
- Do not silently discard unsaved editor data.
- Do not allow a second SAVE with different data against the same unresolved operation.

Browsing must remain available.

Actual mutation authority remains server-side.

## 5. Explicit mutation states

Implement an explicit, reusable mutation state model.

Conceptually:

```typescript
type MutationState =
  | "IDLE"
  | "SENDING"
  | "CONFIRMED"
  | "DEFINITIVELY_REJECTED"
  | "OUTCOME_UNKNOWN"
  | "RECOVERING";
```

Distinguish:

- confirmed database success;
- confirmed domain rejection;
- ambiguous response/timeout;
- unavailable server;
- account authorization loss;
- stale revision;
- unresolved previous operation.

A generic SERVER error is not sufficient evidence that an operation was never committed.

Do not treat all errors as safe to retry with a new UUID.

Do not treat every HTTP failure as an ambiguous committed operation if authoritative evidence proves a definitive rejection.

## 6. Retry must remain idempotent

Preserve the original:

- operation UUID;
- actor/account;
- organization;
- template;
- action;
- expected version;
- exact payload.

"Retry same action" must reuse the original immutable request.

Never regenerate operation UUID on an exact retry.

Never rebase the original request silently onto a newer template revision.

Never allow a retry to unexpectedly create a second exercise.

Preserve current durable database operation receipts.

## 7. Operation reconciliation

Implement a safe server-authoritative recovery process.

Prefer existing receipt infrastructure if sufficient.

If necessary, add a narrowly scoped read-only operation-resolution RPC that determines whether a previous operation was durably recorded.

It must:

- authenticate the current user;
- verify exact organization authority;
- check the operation UUID;
- bind it to the expected actor/org/action/request identity;
- return a sanitized result;
- never expose arbitrary receipts or instructor-only data;
- never disclose credentials or raw internal SQL;
- not report "not committed" merely because the request was not immediately found while it may still be in flight.

Possible resolution:

- confirmed applied;
- confirmed rejected with safe reason;
- unresolved/unknown.

A receipt lookup must not claim definitive failure based only on absence of a receipt.

If resolution succeeds:

- clear the obsolete pending request;
- refresh authoritative template data;
- restore the correct editor state;
- show a useful success message.

If outcome remains ambiguous:

- keep original request available;
- allow exact idempotent retry;
- allow safe read-only navigation;
- provide a clear explanation.

If the operation cannot safely be discarded, do not implement a dangerous generic "Clear Pending" button.

## 8. Recover editor state

Preserve local unsaved template data separately from the immutable pending request.

Protect:

- template definition;
- virtual unit positions;
- initial objects;
- event plan;
- hazard plan.

A user should not lose hours of scenario editing because one SAVE response failed.

Use bounded, account/org/template-scoped local draft recovery where appropriate.

Do not store credentials.

Do not allow account switching to expose another person's private instructor content.

On return to the same editor:

- identify recoverable unsaved changes;
- show recovery/compare options;
- never silently overwrite newer authoritative data;
- handle version conflicts explicitly.

Avoid uncontrolled localStorage persistence of sensitive operational information.

## 9. Fix actual SAVE failure diagnostics

Inspect the current failure path through:

`POST /api/incidents`

and the Supabase RPC error mapping.

Distinguish:

- unsupported RPC argument/version;
- invalid template;
- invalid event plan;
- invalid hazard plan;
- stale revision;
- missing permissions;
- request size limit;
- definite SQL rejection;
- transport ambiguity.

Only expose allowlisted safe error codes to normal users.

Preserve detailed database diagnostics server-side where permitted, with safe correlation IDs.

Do not log secrets, authentication headers, full private scenario definitions or sensitive payloads unnecessarily.

Use SI/DE messages that explain the problem and recovery action.

Check compatibility with:

`20261019150000_simulation_hazard_models.sql`

including correct `hazard_plan`/`event_plan` SAVE behavior.

Do not edit previously applied migrations.

If a real SQL defect is found, use a forward-only migration.
