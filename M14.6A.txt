# CODEX IMPLEMENTATION PROMPT — M14.6A
## Scenario Designer, Reusable Templates & Custom Training Exercises

Repository: https://github.com/ficlus/Gasilko

Implement **M14.6A — Scenario Designer & Reusable Training Templates**.

Create one focused pull request targeting the latest `main`. Do not merge.

**Prerequisite:** M14.5H2 / PR #73 must be corrected and merged before implementation.

This is the first milestone of M14.6 — Dynamic Incident Simulation.

## 1. Product objective

Build a user-friendly, map-based training scenario designer that allows Gasilko users to:

1. Choose an existing prepared exercise template.
2. Customize a prepared template.
3. Create an entirely new exercise from a blank map.
4. Configure initial incident conditions.
5. Position the incident and training objects geographically.
6. Configure which virtual units participate.
7. Save draft exercise definitions.
8. Publish reusable exercise templates.
9. Start new protected SIM incidents from saved definitions.
10. Reuse the same scenario for multiple independent training sessions.

The primary workflow should feel like designing an RTS mission.

**Prepared scenarios AND fully custom scenarios are mandatory.**

Do not build only a form with template selection.

Do not build only a template library without a visual editor.

Do not yet implement dynamic fire propagation or autonomous scenario events. Those belong to M14.6B–E.

## 5. Map-based scenario objects

The designer should support declarative initial objects, including:

- Incident location.
- Command post.
- Staging area.
- Triage point.
- Temporary water source.
- Access point.
- Exercise note.
- Editable points or bounded polygons where the existing COP model supports them.

These are **template definitions**, not already activated live incident objects.

Upon creating a real SIM training instance, supported starting objects may be instantiated into that specific incident through an authorized server workflow.

Preserve their incident-scoped identity and audit history.

Do not bypass existing `incident_put_map_object`, authorization or version rules merely to simplify template creation.

If existing tactical-object APIs cannot safely support atomic initialization, implement a narrow training-only initialization operation with appropriate domain guards.

Do not create ordinary incident objects on the production incident during template editing.

## 6. Virtual units and initial placement

Allow the editor to configure the training unit composition:

- Number of SIM units.
- Unit category/capability where supported.
- Callsign preview.
- Suggested starting location.
- Starting orientation, if explicitly modeled.
- Default response profile.
- Optional initial staging or deployment association.

The user should be able to preview and adjust suggested initial positions on the map.

### Important compatibility

The existing simulator provisions virtual fixture units and stores protected positions using dedicated APIs.

Reuse those mechanisms.

Do not create a second virtual resource registry.

Do not allow a template to impersonate a real vehicle.

Do not attach real vehicles to a SIM scenario through the designer.

Do not make template placement a fake GPS observation.

Any initial position applied to an actual training instance must be explicitly marked as simulated and validated by the existing simulation domain.

### MVP placement workflow

Prefer defining initial spawn positions in the template and applying them during protected scenario initialization.

If the current backend requires initial provisioning followed by explicit simulated position commands, implement an authorized, idempotent bootstrap sequence instead of browser-side unchecked table inserts.

Preserve version guards and audit events.

### Training instance provenance

The actual table names and fields may differ after inspecting the repository.

### Required guarantees

- Bounded JSON definitions.
- Schema versioning.
- Valid coordinates and supported geometry.
- Audit history.
- Stable template/version identifiers.
- No destructive edits to previous versions.

## 9. Definition schema

Create a precise, versioned definition schema.

Suggested logical structure:

```json
{
  "schema_version": 1,
  "metadata": {
    "title": "Industrial warehouse fire",
    "category": "STRUCTURE_FIRE",
    "description": "A configurable training exercise",
    "difficulty": "INTERMEDIATE",
    "objectives": []
  },
  "world": {
    "center": [15.0, 46.0],
    "radius_m": 1000,
    "incident_location": [15.0, 46.0]
  },
  "initial_objects": [],
  "virtual_units": [],
  "briefings": {
    "commander": "",
    "instructor": ""
  },
  "simulation_defaults": {
    "clock_scale": 1,
    "automatic_execution": false,
    "response_profile": "NORMAL"
  }
}
```

This is conceptual; derive the final schema from existing domain types.

Do not treat sample coordinates as actual defaults or user location.

### Strict validation

Enforce:

- Supported schema version.
- Valid categories.
- Valid coordinate ranges.
- Bounded scenario radius.
- Bounded unit count.
- Bounded number of objects.
- Bounded text lengths.
- Bounded JSON size.
- Supported geometry.
- Unique stable object-local IDs.
- Supported SIM response profiles.
- Consistent template references.
- No real vehicle references.
- No unauthorized organization IDs.

Use server-side validation. Frontend validation is supplementary.

Reject unknown security-sensitive configuration fields.

## 10. Template lifecycle

Required states:

```text
BUILT_IN
    |
    +--> COPY AS DRAFT

DRAFT
    |
    +--> EDIT
    |
    +--> PREVIEW
    |
    +--> PUBLISH
              |
              +--> START NEW SIM EXERCISE
              |
              +--> CREATE NEW DRAFT REVISION
```

The lifecycle should be server-authoritative.

Do not let editing a draft overwrite a published immutable revision.

Do not delete templates referenced by historical training sessions.

Archive or deactivate safely rather than destructively deleting history.

## 11. Secure template APIs

Prefer a small set of explicit authenticated RPCs.

Suggested operations:

- `simulation_template_list`
- `simulation_template_read`
- `simulation_template_create`
- `simulation_template_save_draft`
- `simulation_template_publish`
- `simulation_template_copy`
- `simulation_template_archive`
- `simulation_template_start`

Adapt names to existing conventions and avoid unnecessary duplicate endpoints.

### Mutation requirements

- Authenticated user.
- Active acting organization.
- Protected TRAINING environment.
- Authorized scenario/template editor role.
- Expected version.
- Idempotent operation UUID.
- Exact-payload retry semantics.
- Audit event.
- Server validation.
- No cross-org writes.
- No effect on normal incidents.

### Read requirements

- Organization-scoped.
- Bounded pages.
- Search/filter by category and status.
- Built-ins readable to eligible users.
- Drafts visible only according to scoped permissions.
- Instructor-only content hidden from ordinary command-view readers.

Do not grant broad table writes to authenticated users.

## 12. Creating an exercise from a template

This is one of the most important requirements.

Required workflow:

1. Select published template or explicitly choose a valid draft preview.
2. Select authorized organization.
3. Review initial location, objects and virtual units.
4. Confirm creation of a protected SIM incident.
5. Create the real simulation instance through the existing secured simulation-creation domain.
6. Record immutable source-template version.
7. Initialize supported starting objects.
8. Provision/attach supported virtual units.
9. Apply validated initial simulated positions.
10. Leave the scenario in DRAFT or another existing safe pre-start state.
11. Show a review of what was created and what remains manual.
12. Start the scenario only after the user explicitly confirms.

Do not implicitly START the exercise simply because a template was selected.

Do not silently enable H1 automation when the stored template suggests it.

The effective automatic-execution setting must remain server-authorized, default OFF, and require its existing explicit confirmation.

### Idempotency and recovery

A retry after ambiguous network failure must not create a second incident.

Use durable operation identity for creation and bootstrap.

Any partial initialization must be recoverable without duplicate tactical objects, duplicate virtual units or conflicting identity assignments.

If an all-or-nothing transactional bootstrap is impractical because of existing API boundaries, implement durable initialization progress and explicit recovery states.

Do not solve this with a browser-only sequence of unchecked mutations.

## 18. Data safety and training isolation

Critical invariants:

**SCENARIO DEFINITION != SIMULATION INSTANCE**

**COMMAND INTENT != EXECUTION PLAN != TELEMETRY**

**REAL INCIDENT != TRAINING EXERCISE**

**HUMAN COMMAND != SIMULATED RESPONSE**

Requirements:

- No real incident affected by template editing.
- No shared mutable template data between active scenarios.
- No real GPS inserted through a template.
- No fabricated firefighter ACK.
- No copying of real operational vehicle identity as SIM fixtures.
- No unauthorized cross-organization templates.
- No automatic unit movement during setup.
- No task creation merely by saving a scenario.
- No new privileges from being a scenario author.
- No real operational command authority granted by a template.
- No service-role secrets in browser code.

The existing single Supabase project contains both real and training data. Enforce isolation at the database boundary.
