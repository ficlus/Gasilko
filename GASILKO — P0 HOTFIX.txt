# GASILKO — P0 HOTFIX: Simulation Hazard Batch SQL Ambiguity

Repository: https://github.com/ficlus/Gasilko

Base branch: current `main` after merged M14.6D PR #79.

Create ONE new focused hotfix PR. Do not merge or deploy.

## Confirmed production defect

The existing Supabase project repeatedly returns:

`HAZARD_BATCH_UNAVAILABLE`

from `incident-simulation-runner`, although the Edge Function receives HTTP 200 requests approximately every five seconds.

A database diagnostic invocation of `public.simulation_hazard_batch()` conclusively returned:

```text
SQLSTATE: 42702
column reference "s.id" is ambiguous

PL/pgSQL function public.simulation_hazard_batch()
line 9 at FOR over SELECT rows
```

The function is present, SECURITY DEFINER is enabled, and service_role has EXECUTE permission.

The failure happens before any hazard models can be processed.

Observed consequences:

- RUNNING simulation.
- Hazard model last_step = 0.
- Simulation clock already at step 162.
- Fire does not progress.
- APPLY_WATER returns OP_CATCHUP_REQUIRED.
- The Edge runner catches the error, returns HAZARD_BATCH_UNAVAILABLE and continues its other phases.

## Root cause

The authoritative function was redefined in:

`supabase/migrations/20261023120000_simulation_operational_effects.sql`

It declares composite PL/pgSQL variables:

```sql
m private.simulation_hazard_models;
s public.simulation_scenarios;
```

and simultaneously uses `m` and `s` as SQL aliases in its opening cursor query.

This produces the confirmed ambiguity.
