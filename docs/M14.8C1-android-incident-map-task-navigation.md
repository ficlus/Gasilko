## Source-backed implementation decisions

1. Existing target-only map was point-only and did not carry full incident context.
   It is replaced at the incident navigation boundary by a repository/Room-derived
   map. Normal hydrant maps, route maps and inspection flows retain their APIs.
2. Existing general incident map/nav reads have broader projections and may expose
   protected simulation information. The field projection adds only:
   sectors of currently visible own deployments or referenced visible task sectors;
   active map objects referenced by visible tasks; active incident links to active
   hydrants OWNED BY the exact acting organization. No full COP, descriptions,
   hidden instructor model, private messages, resource details or position samples.
3. Linked hydrants require BOTH the incident link projection and the independently
   authorized local registry UUID before display. Registry rows come from the
   current organization Room map flow with its existing active/role normalization.
   No cross-org registry fallback and no direct Supabase map fetch. Linked marker coordinates/code/version are rendered from that current Room hydrant (including pending local edits), while the server link UUID remains the relationship identity. Issued task geometry remains frozen separately.
4. Frozen task targets are separate TASK_TARGET features keyed by assignment UUID.
   Live contextual versions never replace their destination. Multiple tasks may
   point to one hydrant without duplicating the canonical hydrant.
5. Navigation sessions mutate separately from incident aggregate revisions:
   source navigation_event writes navigation history/audit, not incident timeline.
   Therefore an independent opaque DATA watermark was necessary in the EXISTING
   batched directory; it is NOT an authorization fingerprint or new cursor.
6. Android's canonical INCIDENT_TASK worker allowlist does NOT dispatch
   incident-navigation Edge preparation/lease/commit. This milestone creates NO
   new navigation mutation or local queue. Read of permitted stored road geometry
   and explicit target-only/external fallback are delivered. Internal creation,
   route recalculation and navigation execution controls are NOT IMPLEMENTED here.
   This is the brief's safe fallback, not a fake route-preview success.
7. ACTUAL_POSITION is rejected by existing SQL until a genuine authorized incident
   position source exists. No device GPS is submitted, stored or shared.
   Protected SIM-origin routes are deliberately NOT exported by this field DTO.
   Manual planning origins are labeled as plans, never telemetry.

## Field-map DTO, bounds and atomicity

Nested core field_map:
`{schema:1,status:COMPLETE|MAP_TOO_LARGE,revision:<decimal string>,
source:<opaque32>,features:[...],routes:[...]}`.

Feature row: canonical id, kind, safe label, geometry, version string,
hydrant_id only for a linked canonical hydrant.
Route row: assignment_id, session_id, session_version, status, route_id,
route_revision, geometry, provider, distance_m, duration_s,
origin_source=MANUAL_PLANNING_POINT, calculated_at, destination, stale.
No full raw table rows or navigation event payloads.

Context <=200 features (201 lookahead); routes <=25 (26 lookahead);
combined addon <=768KiB. On overflow the ENTIRE addon is an explicit
MAP_TOO_LARGE with empty contextual features/routes, not a partial current set.
Permitted frozen task targets remain available from existing assignments.
Combined field projection still <=3MiB; no limit relaxation. If even a tiny
capability marker cannot fit, omit addon and gate the feature, preserving B1.
Organization-wide B1 total remains3MiB; a too-large replacement retains the old
authorized leased cache as stale. Larger geometry sets need a later owner-approved
bounded protocol/limit decision; no unauthorized Room change was attempted.

Canonical context geometry uses Point/LineString/Polygon, WGS84 [longitude,latitude],
64KiB/2000 pairs per geometry. Client rejects missing/nonfinite/out-of-range/
malformed geometry, wrong task incident reference, unrecognized kinds and oversized
input. It never silently swaps axes; if both swapped values happen to lie within
valid ranges no coordinate-only validator can detect that semantic error.
NAV geometry remains bounded by its existing50000-point server contract AND
this smaller addon byte budget. No simplification, centroid, edge destination,
straight-line road fallback or fake [0,0] marker.

B1 manifest core contains addon under SAME pinned incident revision and scope.
Five-minute TTL, per-page checks, final directory scope check and atomically
saved Room projection/cursor remain. Missing addon is a DATA incompatibility:
fresh manifest, no preemptive access revocation. If only NAV watermark differs,
same expected-revision/scope entities read replaces projection. Final watermark
drift marks the committed complete projection STALE and retains next refresh;
it is not a claim of caught-up state. No second durable cursor.
Concurrent network failures do not delete the prior leased map or pending intent.
Known route-only denial atomically clears routes first; failed reread cannot
resurrect them. Actual B1 scope narrowing/denial or lease expiry hides the whole
protected incident according to existing rules.

## Navigation and GPS privacy

Existing permitted stored MANUAL_PLANNING_POINT route is shown only for exact
selected assignment/destination. Provider/distance/planned duration/calculation
time/session status and stale state are visible. No ETA, spoken maneuvers or
turn-by-turn claims. Existing optional provider steps are NOT rendered here.
A field responder lacking an eligible unit-assignment route or original NAV read authority still has target-only
guidance. Personal crew walking navigation remains outside canonical NAV2.

External navigation:
select one valid point -> explicit warning/review -> Android ACTION_VIEW
`geo:0,0?q=latitude,longitude`. Only coordinates are transferred, never
incident IDs, labels, notes or account/org metadata. It may need network and is
outside Gasilko's privacy boundary. Missing app/security rejection leaves static
coordinates visible. Review freezes exact feature/point/source version/incident revision inside the keyed actor/org/incident screen. A changed target/version/revision cancels the review and asks for explicit re-review. Final UI confirmation uses IncidentViewModel -> IncidentRepository.verifyMapHandoff(org,incident,kind,id,geometry,revision,version): under existing remote/identity mutexes and one Room read transaction, recheck the secure lease/current account/org, exact target membership/geometry/version/revision and current local registry UUID where needed. Callback also requires the same still-open intent and live keyed screen; cancelled/old callbacks cannot launch an external app.
There is NO task ACK/start/complete, incident/unit status change, route/session
mutation, arrival inference, GPS upload, background tracking or location history.
Existing foreground location controls remain user-invoked camera aids only;
no new permissions/service/dependency and no onLocationUpdate upload.
