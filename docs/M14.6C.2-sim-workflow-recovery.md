# M14.6C.2 — SIM workflow recovery

## Implementation-only delivery

No tests, builds, lint, typecheck or CI were performed. No browser/runtime checks, emulator, migration execution or deployment checks were performed. No tests were added. Nothing was deployed. This document describes source changes and the user's later acceptance procedure, not verified runtime results.

## Before / after architecture

The existing Next.js → authenticated incident API → authoritative Supabase RPC architecture remains. Template receipts, immutable published versions, optimistic revisions, incident command/consent, simulator runner, existing Cron, H1 routes, B events, B1 confirmed samples and C hazard physics remain authoritative.

Before, TemplateLibrary used one busy value for list loading, mutation execution and any retained pending request. Its open function rejected reads whenever that value was true. A lost SAVE response could therefore lock the entire library indefinitely.

After, list loading, editor loading, execution and unresolved writes are separate. Reads/back/filter/page navigation remain usable; a retained operation blocks mutations and editing of the affected template until resolved. Other templates remain usable. This avoids incompatible SAVE and duplicate CREATE/COPY/START. Browsing does not clear pending operations. The old broad busy gate was a proven source-level cause of the lock.

## SAVE investigation and diagnostics

The M14.6C RPC already accepts definition, event_plan and hazard_plan in SAVE. No alternate mutation contract was introduced. Source inspection found an ambiguous SQL identifier in validate_hazard_plan: the PL/pgSQL variable e also named the relation alias in the duplicate event-effect query. The new forward migration qualifies effect_row.value instead. This is a concrete source defect, but without runtime diagnostics it does not establish the cause of the user's original SAVE failure.

Existing validators retain their bounds and behavior, with separate safe INVALID_TEMPLATE, INVALID_EVENT_PLAN and INVALID_HAZARD_PLAN failures. The API distinguishes REQUEST_TOO_LARGE and SCHEMA_MISMATCH. Logs contain only correlation ID, RPC name, SQLSTATE and allowlisted code; no definitions, headers, private payload or raw database message. SERVER/transport/schema/auth failures do not assert that nothing committed.

## Mutation and receipt policy

The shared hook exposes IDLE, SENDING, CONFIRMED, DEFINITIVELY_REJECTED, OUTCOME_UNKNOWN and RECOVERING. The immutable JSON request, actor-scoped storage key, organization, UUID, action, expected revision and payload are retained before dispatch. If durable session storage cannot retain the identity, dispatch is refused.

A first authoritative domain rejection clears the pending request, leaving the editable draft intact. A rejection after an earlier ambiguous attempt cannot prove the earlier attempt failed; that exact request remains retained. No generic Clear Pending button exists. Retry does not regenerate UUID or rebase version. Read-only resolution compares the exact normalized request against existing private receipts and current account/organization authority. Absence/mismatch returns OUTCOME_UNKNOWN, never "not committed". Confirmed receipts clear the obsolete pending request and refetch authoritative state. Resolution can still require an authorized operator after access is restored.

Template commands and initialization use their existing receipts. Simulation controls use existing incident receipts. Quick creation and training incident mutations additionally retain their full exact pending request in account/org-scoped session storage. Training request callbacks cannot update a switched scope. FINISH and core lifecycle retain distinct domain boundaries.

## Local drafts

Recoverable definition, units, objects, event plan and hazard plan are stored separately from the immutable request. Session storage is scoped by account, organization and template. Maximum: 200,000 serialized characters per draft, eight drafts and 1,000,000 characters total in the tab. No eviction of other drafts; storage exhaustion warns and blocks unsafe navigation. No credentials, localStorage or persistent offline authorization are added.

A successful authorized template read precedes displaying a recovered draft. Restore requires explicit comparison; if the server revision changed, the warning explains that the reviewed draft will use the current revision for a new operation. Original ambiguous requests cannot be rewritten. Discard deletes only the explicit local draft, never an unknown operation. Account/org keys separate private content; revocation hides protected UI.

This is tab/session recovery, not a multi-device draft service. A new independent tab reads authoritative data and cannot recover another tab's private session storage. Closing the browser/tab may remove recovery data. Browser clearing/storage restrictions can prevent recovery. Keep the editor open when storage warnings occur.

## SIM home and editing

The SIM entry distinguishes four existing quick presets (seed/area, no automatically generated hazard plan) from versioned scenarios (units/objects/events/hazards). Existing quick and library URLs still work. My drafts, active exercises and finished exercises have explicit entry points; active/finished filtering occurs before server pagination.

The editor reuses existing specialized components through sections: overview, area, units, objects, hazards, events, defaults and review. Only the active specialized map mounts. Shared map context includes scenario origin, units, objects, model extents/origins and event locations; selection links to the corresponding inspector. Existing hazard initial previews and coordinate tools remain. Field editing does not run the simulator.

Warnings explain broken references, hidden/initial visibility, initial ignition and that layer toggles do not create models. Readiness links to invalid sections; it is advisory and never replaces server validation. Published/built-in previews stay read-only. Canonical IDs, source/owner, version, state and update time distinguish duplicate titles. No title deduplication or template deletion occurs.

SAVE includes all three plans. PUBLISH retains immutability. START remains the existing server command and explicitly confirms source version, organization, location, counts and setup requirements. DRAFT preview starts a separate exercise without publishing the source. Confirmed exercise creation navigates to the existing incident.

## Preparation, running and closure

The training workflow shows command confirmation, activation, initialization and start separately. Existing command controls and capability-driven actions remain. Initialization displays safe provenance, counts, source preview state, duration and authoritative readiness; no private instructor briefing is projected into incident DTOs.

Initialization remains one server transaction with existing UUID receipts; a lost response is retried/reconciled, not reinitialized with a fresh operation. Disabled setup explains command/consent/state prerequisites.

START/PAUSE/RESUME/RESET/FINISH remain explicit confirmed simulation commands with original version checks. The operational summary uses already-loaded scoped clock/unit/job/event/hazard state. Counts describe the visible/current bounded data, not organization-wide analytics. Map visibility toggles are presentation-only; hidden participant information is not inferred.

FINISH stops simulation progression through existing server behavior; it does not complete tasks or close the incident. Final unit positions remain visible without SIM movement eligibility or interpolation. Existing fast-sample polling stops for FINISHED. The UI points to resource/task cleanup and normal stabilize/close/cancel actions. Existing reason, consent, authorization and active-resource closure guards remain. REAL incident transitions are not weakened.

## Historical access

The existing incident timeline, SIM event history, scenario-event history and unit projections remain accessible to authorized users. Template initialization adds safe original title/version/duration/count summaries. A new bounded hazard-history read returns only version, step, kind and timestamp: no raw configuration, effects, private payload or receipt. Participant history requires current revealed visibility and a revealed snapshot at that historical version; instructor checks reuse existing controls.

This is a historical summary, not M14.7 replay or M14.8 analysis. Hidden instructor material is not made accessible merely because an exercise finished. No fire/smoke physics, movement algorithms, scheduler, REAL dispatch, GPS, inspection, hydrant status or Android behavior changed.

## Limitations and risks

- Source-only implementation. Type safety, rendering, SQL execution, concurrency and end-to-end behavior still require the user's release verification.
- Requests are bounded to eight per scoped surface; only conflicting template writes are blocked. Network dispatches remain serialized.
- Session storage is bounded and tab-local, not a durable cross-device editing service.
- No fabricated "not committed" result. In-flight/absent receipt, revoked permissions or disabled environment may leave an operation unknown until the authorized server can resolve it.
- Client readiness checks are advisory; full existing validators decide validity.
- Historical summaries are bounded and privacy-filtered; no replay or analytics.
- No claim that the original observed SAVE failure was reproduced.

## PR #78 correction and completion

### Confirmed source defects corrected

- Corrected malformed dollar delimiters in the three validators and hazard history function in the **same unapplied** `20261021120000_simulation_workflow_recovery.sql`. Function bodies use named delimiters; the surrounding transaction is retained. Historical migrations are unchanged.
- Kept the qualified `effect_row.value` duplicate-effect check. Numerical limits and hazard physics are unchanged. The original reported SAVE error was **not reproduced**.
- SAVE acknowledgement no longer unconditionally deletes a later local draft: removal requires matching original revision and canonical submitted payload. A matching editor baseline is advanced only from the acknowledged revision, followed by an authorized current read.

- Map selection recognizes event proxy IDs and model origins/zones, including line geometry. Switching sections/selections cancels unfinished placement and polygon vertices.
- A rejected SIM proposal's Review action now awaits a fresh authorized snapshot before offering a newly identified request for explicit confirmation. Unknown requests cannot take that path.

### Additional hardening

The receipt resolver remains read-only and compares actor, organization, operation identity and the canonical immutable request. SIM lookup also explicitly binds incident and command code. Missing or mismatched receipts remain unknown. No receipt-listing API was added.

The existing pending storage key accepts its legacy single request or a bounded envelope (eight requests, 200,000 characters each, 1,000,000 total). This permits independent template work without overwriting an unresolved operation. Storage failure prevents dispatch; failed cleanup retains the original identity. No automatic eviction occurs.

SIM control now uses a synchronous request lock, scope guard and pending ref. Recovery must load before new dispatch. Storage is written before dispatch. Read reconciliation and exact retry preserve FINISH identity; terminal receipt behavior on the server is unchanged. Dialog focus returns to its opener. Access loss hides control content and does not erase the durable pending request.

Editor maps retain session viewport across specialized editor mounts and avoid redundant source updates when geometry is unchanged. Only one specialized map is present at a time; a single permanently mounted map host across every specialized editor is intentionally not introduced. Field edits do not recenter the map.

The existing authorized hazards read includes additive preparation state, without hidden configuration. Layer messaging distinguishes unavailable/loading, uninitialized, no revealed models, disabled/hidden/unignited instructor models, empty fire/smoke, lag/error and historical FINISHED data. Detailed configuration reasons require the existing instructor projection. A layer toggle remains presentation-only.

The lifecycle panel identifies the next command, activation, initialization or start step from existing authorized state; terminal incidents show history. Existing close actions, required reason and authoritative refusal messages remain in the incident workflow. FINISH does not imply CLOSE or complete tasks. No special training closure bypass was added.
