# M14.6C — deterministic training hazards

This is an educational model, not a physical fire prediction, measured smoke concentration, structural assessment or operational command authority. Every displayed feature has SIM provenance. No location, ACK, task completion, road restriction, water use or suppression effect is inferred from vehicle proximity.

## Existing flow and integration

The base includes merged PR #76. M14.6A keeps definition schema v1 strict; M14.6B adds a separately versioned event plan. Template creation/copy/revision/save/publish/start already use operation receipts, organization locks and immutable published versions. Protected template initialization creates a scenario before preparing its units and COP objects.

M14.6E/H1 owns the durable simulation clock and shared agent locks; M14.6B consumes that clock for bounded events. B1 owns fast positions and independent complete route reconciliation. C extends these paths rather than adding a scheduler, map, selection store or position poller.

A separate private hazard-plan row belongs to each immutable template version. Old templates without this row resolve to an empty plan. Copy and revision carry it forward. Save validates it atomically with the definition/event plan; publish and start revalidate it. Initialization copies model configuration only into a protected scenario. There is no API to attach hazards to an existing real incident.

Runner order remains movement, B events, then a bounded hazard phase, then H1 road preparation. Hazard RPC failure is isolated at the Edge boundary, so it cannot suppress the subsequent preparation call. The existing five-second Cron, bearer secret, JWT gateway policy and routing provider are unchanged.

## Model registry and numeric rules (version 1)

Supported types are exactly STRUCTURE_FIRE and WILDFIRE. Both use five simulated seconds per step. There is no uncontrolled randomness: seed 0 denotes the deterministic policy. Exact accepted configuration, model version, input effects, step cursor and snapshots are persisted.

### Coordinates and field

The local grid uses R = 6,371,008.8 m, x = R cos(latitude0) delta-longitude and y = R delta-latitude, with angles in radians. Inverse conversion uses the same fixed latitude. Configuration is restricted to latitude ±75°, longitude ±179°, radius at most 250 m. This small-area projection is an explicit training approximation; no terrain/weather observations are invented.

Wildfire cells are 25 or 50 m. Only cells whose whole square fits inside the radius are included. A bounded 21 by 21 candidate grid provides an absolute ceiling of 441 cells (the circular mask yields fewer). Origins must map into included, combustible cells. Explicit blocked cells have zero fuel; other cells use configured fuel and moisture. Multiple initial origins in the same cell take the maximum initial intensity.

Structure sources keep their original configured point and one bounded state element per origin, rather than inventing building geometry.

### Synchronous evolution

All cells see the previous step (Jacobi update), not partially updated neighbors. State is rounded to six decimal places.

Wildfire uses eight neighbors. For each neighbor, directional influence is its intensity multiplied by max(0.2, 1 + windSpeed/10 × directional cosine), divided by eight. Heating increases by 0.12 × spread × (1 − moisture) × fuel × neighbor influence × 25/cellWidth and is capped at 2. At heat >= 1 an unburned combustible cell ignites at intensity 0.2.

An active source grows by 0.02 × spread × (1 − moisture) each step, capped at 1. Consumed fraction increases by 0.005 × new intensity / max(0.1, fuel), capped at 1. Fully consumed cells extinguish. Fuel cannot become negative.

Derived wildfire states:
- NON_COMBUSTIBLE: fuel = 0.
- BURNED: consumed fraction >= 1.
- BURNING: intensity > 0.
- HEATING: intensity = 0 and accumulated heat > 0.
- UNBURNED: otherwise.

Structure fires share bounded intensity/consumption but do not spread to neighboring sources. Their configured decline time (0 disables it) starts a decrease of 0.025 per step. Presentation phases are INITIAL below 0.25, DEVELOPING below 0.7, INTENSE at/above 0.7, DECLINING after the configured threshold while active, and EXTINGUISHED at zero. No flashover, room-to-room or collapse physics is claimed.

Model ENABLE=false freezes its state while recording elapsed logical steps. Re-enabling affects future steps only. This is separate from scenario PAUSE, which freezes processing and the authoritative clock.

### Smoke and heat

Structure smoke = clamp(0.9 × previous smoke + 0.08 × new fire intensity, 0, 1). Its bounded plume offset moves with configured wind by windSpeed × 5 seconds per step, limited to half the configured radius. Dormant sources do not pre-drift; ignition resets the plume offset. Smoke radius is 10 + 40 × concentration metres.

Wildfire smoke = clamp(0.65 × local smoke + 0.25 × weighted neighbor smoke + 0.08 × new intensity, 0, 1). Neighbor drift weight is max(0.05, 1 + 0.8 × min(1, windSpeed/10) × directional cosine). At zero wind it is symmetric. Dilution and loss through the field boundary dissipate smoke after sources weaken. Concentration below 0.01 is not displayed.

Heat zones are derived when intensity >= 0.7. Structure heat radius is 10 + 30 × intensity metres; wildfire heat follows the cell. Display polygons are bounded to the configured local envelope. Manually configured HEAT_ZONE, SMOKE_ZONE, COLLAPSE_RISK, HAZARDOUS_MATERIAL and ACCESS_HAZARD circles are separately marked INSTRUCTOR. B annotations and operational COP objects are not modified.

## Time, effects and failure recovery

The durable cursor advances only to floor(authoritative clock seconds / 5). No browser time is used. An invocation processes at most four fairly ordered models, ten steps per model, with a two-second cooperative deadline checked between steps/models. Each SQL step is itself bounded; this is not a proven hard execution-time guarantee. Edge waits at most 3.5 seconds for the hazard RPC. Locks have a 100 ms timeout.

The engine uses existing agent/scenario/clock locks before model locks and rechecks state/authority under them. A transaction commits state, step history and snapshots together; a crash/timeout rollback cannot leave a half-applied step. Overlapping calls re-read the committed cursor. Catch-up never skips intermediate steps. Lag remains visible, especially at accelerated clock speeds; these budgets are not a throughput benchmark.

Instructor effects are IGNITE (a configured origin), WIND, SPREAD, BOOST (existing flames only), ENABLE, REVEAL and STOP (extinguish active sources). STOP is an explicit exercise control, not an operational suppression simulation. Version guards and existing account/org-scoped durable mutation receipts protect retries. Pending requests reuse the same operation/payload. Stale requests require a new explicit review.

Effects enter an append-only queue at ceil(clock seconds / 5), ordered by boundary and durable sequence. At most four due effects are applied in each bounded application batch; a model never advances past remaining due effects. While paused, effects wait for resume. An acknowledged queue request is not presented as an already-applied effect.

Existing B events link to one allowlisted model effect per event/model. The link lives in private model configuration, not in ordinary B event DTOs. B's existing transactional effect block enqueues it with the event's stable operation ID. A duplicate event cannot enqueue or apply another ignition. B records a failed enqueue through its normal retryable outcome; hidden effect parameters are not copied into the public event result. The hazard history records the actual model revision/step, input, actor/event identity and origin on application.

Scenario RESET retains the original clock semantics: it does not rewind time or delete history. It queues a model reset to its immutable initial configuration at the current time boundary; age for structure development restarts there. B event receipts remain executed and do not fire again. A new template session is the way to replay the entire event plan. FINISH freezes the latest committed model state and records a final snapshot; any unfinished backlog is retained and is not secretly simulated after finish.

A processing exception rolls back that model's batch and records a sanitized error. The model stops until explicit instructor RETRY; retry does not change its state or replay completed effects. Repeated contention is retried by the next existing runner invocation. Revoked/ineligible scenarios receive a scan timestamp so they do not monopolize the fair queue.

## Bounds, persistence and replay

- 4 models per scenario, at most 1 wildfire.
- Radius 25–250 m, integral multiples of 25/50 m cell width.
- Up to 8 configured origins and 8 manual hazard zones per model.
- 40 event links per model; each references an actual saved B event.
- 30 KB hazard plan, 200 KB current state, 1.5 MB read-response ceiling.
- Existing combined template mutation/request size limits are retained.
- At most 5,760 steps (8 simulated hours). No growth after the horizon; lag/limit remains visible.
- 200 accepted queued effects per model, including lifecycle resets.
- History version guard at 9,980 with reserved final/limit records and a database ceiling of 10,002. At exhaustion the model stops explicitly; scenario FINISH still works.
- Full immutable snapshots initially, every 60 steps (5 simulated minutes), after applied effects and at finish/limit. Other lifecycle records are compact.
- STEP history records the exact step, model version, burning count and deterministic state hash. Immutable initial configuration plus ordered effects and snapshots permit replay without using today's geometry.
- An unchanged grid is not rewritten: only cursor/history metadata advances. Changed state is stored as one bounded JSON projection, not one permanent row per particle.
- Set-based neighbor calculations, not one database/API request per cell. Worst-case candidate comparison is bounded by the small field.
- Display uses square cells and 16-segment local circles; fewer than 10,000 coordinate vertices per scenario under the configuration bounds. No per-cell React components.
- No automatic retention deletion. Old histories remain immutable. Limits halt new modeled work rather than discard history.

These are policy limits, not measured infrastructure capacity. Multi-scenario and accelerated workloads require the manual capacity checks below.

## Authorization and UI

All new tables are private, RLS-enabled, with application and service-role table privileges revoked. Private helper execution is revoked. Only the fixed authenticated read/command RPCs and the service-role-only bounded worker RPC are granted. All security-definer functions use an empty search_path.

Controller access reuses the existing template editor, simulation operator/controller, incident and organization predicates. Workers additionally recheck the creator's current authority and READY template setup. Ordinary reads return only revealed models, no hidden counts, configurations, event links or future ignition definitions. A full instructor projection requires an explicit instructor flag and server authorization. Future origins are omitted from ordinary markers until activated. Switching scope or losing access clears the corresponding UI projection.

Visibility is model-level: START, or HIDDEN until an explicit instructor/event REVEAL. Zones needing different disclosure must be configured in separate models. There is no GPS-proximity observation policy.

The editor uses existing TemplateMap/CoordinateEditor for origins, center, blocked cells and manual zones, with a labeled initial configuration preview. Existing published definitions remain immutable. Traffic/sandbox exercises receive no fire unless explicitly configured.

The live panel reuses F4's slow success generations and existing mutation confirmation/retry UI. It does not add a timer or put hazard payloads into B1's position lane. Three independent display switches control fire, smoke and hazards without changing simulation state. The map uses one stable source, five passive layers below operational features, version-keyed updates and one coalesced animation-frame submission. It adds no hit-testing, camera movement or map remount. Selected-model details show phases, configured hazards, wind, step, lag, freshness and controller diagnostics. SI/DE labels are provided.

## Future M14.6D boundary

A future operational-effect API must resolve a current authorized assignment and its capability/resources on the server, lock the scenario/model, validate bounded target geometry and accepted effect parameters, and enqueue a stable operation with explicit assignment provenance. It should reuse the step/effect/history boundary, not write current cells directly. The current public API accepts instructor controls only and has no arbitrary JSON dispatch, resource consumption or automatic MOVE_TO suppression.
