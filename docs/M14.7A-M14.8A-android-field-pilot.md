# M14.7A / M14.8A — Android incident field pilot

## Readiness boundary

Implementation for a **controlled human-operated pilot**, not verified emergency readiness.
It does not replace ZA-RE, dispatch, 112 or CAD. No deployment, migration execution,
push delivery, runtime acceptance or automated checks were performed for this change.

## Scope and authorization

The field projection is actor-bound: there is no target-user parameter.
An active account with exact organization membership and ACTIVE incident participation
sees its active crew relationship or currently effective UNIT_LEADER unit.
Within that unit a responder sees their own crew assignments and unit-directed
context; a leader additionally sees the current roster and crew task states.
Another organization, inherited membership, ADMIN or MANAGER alone grants no field
command power.

The immutable assignment UUID is the inbox identity. The aggregate task is not
treated as completed when one assignment completes. Explicit ACK, start, block,
resume, complete and unable use the canonical transition function; cancellation
remains the existing issuer/Web action. Opening a notification/map never changes
task state. Unit leaders can issue to eligible subordinate crew only, and can
report ON_SCENE → RETURNING online where the existing resource-command guard
allows it. Release, unavailable, command transfer, deployment and other authority
changes remain in their existing Web workflows; no broader offline authority is added.

The current schema identifies TRAINING through its existing
`simulation_scenarios.incident_id` association, not a new client flag or invented
`incidents.mode` column. Field reads return only the classification, never private
scenario configuration, SIM positions or instructor hazard state. Other incidents
are labeled REAL. Training mode is not a privilege.

## Exact RPC contracts

### New: incident_field_snapshot

- Arguments: `p_acting_organization_id uuid`.
- Actor: `auth.uid()`; active exact organization membership; effective own
  unit/crew relationships. No anonymous or service-role EXECUTE grant.
- Result: `{account, organization, verified_at, incidents: [...]}`.
- Each incident has `id, reference, title, status, mode, latitude, longitude,
  version, revision, timeline_sequence, units, assignments, history`.
- Unit projection: canonical deployment id/name/status/version, effective
  leader name, leader flag, can_return and bounded current scoped crew.
- Assignment projection: canonical assignment id/version/status/recipient kind,
  recipient id/name, unit id, mine, can_execute, immutable explicit participant task projection (no raw row expansion).
- History: sequence string, recorded_at, event code and canonical event data,
  restricted to returned tasks/assignments; latest 100. Not a general incident timeline.
  Data is event-specific, not raw timeline JSON: shared TASK_ISSUED exposes task_id
  and action_version_id, TASK_CLOSED task_id/outcome, TASK_CANCELLED task_id.
  Allowed assignment events expose task_id, task_assignment_id, from_status/status;
  reason is included only for the actual crew recipient or effective unit leader.
  Shared unit-task viewers without leadership do not receive the private reason.
  Unknown TASK_* event codes are omitted, not passed through. No recipient count,
  actor IDs, arbitrary comments, instructor metadata or unrelated JSON fields are copied.
- Maximum 50 relevant incidents, 100 units per incident, 100 visible crew per
  unit, 100 assignments per incident and 3 MiB total response. Exceeding a bound
  raises `FIELD_SNAPSHOT_LIMIT`; no partial page is accepted as a complete snapshot.
- Organization security lock and shared incident locks pin the projection.
  Exact membership is rechecked after acquiring the lock. Active incidents exclude
  RELEASED/UNAVAILABLE units; crew-specific visibility requires the actual ACTIVE
  crew episode, not another active episode belonging to the same person.
  Snapshot reads can contend with canonical mutations: the existing serialization
  is retained for consistency, with a 1500 ms lock-wait timeout restored on success
  (an error rolls back the transaction). This is not a measured latency guarantee.
  There are no cursors mixed across requests. A successful complete snapshot
  atomically replaces the organization projection in one Room row.
- All versions/revisions/sequence values are decimal strings.
- Read-only, no operation receipt or expected version.
- `NOT_AUTHORIZED` (42501), `FIELD_SNAPSHOT_LIMIT`; errors are shown without
  provider/SQL details. Missing personal relationship produces no corresponding row.
- SECURITY DEFINER, empty search_path, bounded fixed SQL; private helper functions
  are revoked from PUBLIC/anon/authenticated/service_role.

### Reused: incident_transition_task_assignment

Arguments: `p_operation uuid, p_acting_organization_id uuid,
p_incident_id uuid, p_expected_version bigint, p_payload jsonb`.
Payload: `{id: assignmentUUID, status: targetStatus, reason: string}`.
Expected version is the assignment version. Actor is server-derived. Current
recipient/effective leader, participation, incident and immutable action configuration
are rechecked by `private.incident_task_command`. Returns the existing receipt:
incident_id, operation_id, task_id, version, revision, timeline_sequence.
The existing durable receipt compares the exact original request before replay.
Errors include NOT_AUTHORIZED, STALE_VERSION, OPERATION_REUSED,
INVALID_TASK_TRANSITION, INCIDENT_TERMINAL, VALIDATION_FAILED and TASK_NOT_FOUND.
No command function or state-machine guard is replaced.

### Reused: incident_issue_task

Same argument envelope as the transition RPC, but expected version is the incident
version. Payload: `id` (new task UUID), `action_version_id`,
`title`, `notes`, `parameters`, `target`, and `recipients`.
Each recipient is `{id: assignmentUUID, type: INCIDENT_CREW_MEMBER,
recipient_id: crewEpisodeUUID}`. Canonical API supports 1–100 recipients;
this pilot deliberately issues to one selected subordinate at a time.
Target is the existing discriminated shape:
`{kind:NONE}`, `{kind:COORDINATE,coordinate:[longitude,latitude]}`,
`{kind:HYDRANT,entityId}`, or
`{kind:INCIDENT_MAP_OBJECT|INCIDENT_SECTOR,entityId,incidentId}`.
Coordinates are user entered; hydrants come from the current Room registry;
map-object/sector selection is limited to references already present in the
authorized assignment snapshot. No arbitrary cross-incident object directory is added.
The server revalidates targets, definitions, parameter types/bounds and recipients.
Returns canonical receipt. Additional existing errors: INVALID_ACTION_DEFINITION,
INVALID_ACTION_PARAMETERS, INVALID_TASK_TARGET, INVALID_TASK_RECIPIENT,
TASK_POINT_REQUIRED and TASK_LIMIT_REACHED.

### Reused: operational_action_catalog

Arguments `p_organization_id uuid, p_admin boolean=false,
p_query text='', p_page integer=0`; exact active organization member.
Response `{rows,more}`; up to 100 definitions in the first page.
Read-only; no expected version/receipt. Android displays crew-compatible definitions.
  The actual SQL returns row.id = definition UUID and configuration = to_jsonb(v),
  where v is the immutable version row joined through d.current_version_id.
  Thus configuration.id IS the correct version UUID in the original PR; it was
  not an absent field. The correction separates selectedRow, actionVersionId and
  display configuration, validates configuration.definition_id == row.id and
  configuration.version_number == row.version, active flags and recipient types.
  Review freezes that exact row and payload and displays the version number/UUID.
  Before a new issue is persisted, the repository fetches the current bounded
  catalog and verifies the same version/configuration and current eligible crew.
  It does not substitute a newer definition into a frozen request. Existing
  unknown-outcome retries skip re-preparation and replay the exact original request.
Private definition administration is not exposed. Pilot selection is bounded to
the first catalog page; larger catalogs need a subsequent picker enhancement.
Errors NOT_AUTHORIZED and VALIDATION_FAILED.

### Reused: incident_update_unit_status

Same mutation envelope; expected version is incident version.
Payload `{id: unitAssignmentUUID, version: decimalString, status: RETURNING}`.
Current unit and incident versions, effective unit management and allowed transition
are enforced by the existing resource command. Returns the existing incident
receipt; retries keep the original operation UUID and request. NOT_AUTHORIZED,
STALE_VERSION, INVALID_UNIT_STATUS and existing resource guards remain authoritative.
This online action is never background-dispatched.

### Notification transport

Existing `notification_preferences(request jsonb)`, registration, claim and finish
RPC signatures and grants remain unchanged. New category `INCIDENT_TASK` is
editable and enabled by default. Assignment insert/status-change trigger emits
`INCIDENT_TASK_CHANGED`, one event per assignment UUID/version. Event `teams`
holds assignment scope identifiers for this category only; plan categories retain
their original interpretation. Existing resolver/claim path rechecks current
person, organization, unit/crew/leader access and preferences before delivery.
No second delivery pipeline, public subscription or credential is introduced.

## Room and local authorization

Version **14 → 15**, `MIGRATION_14_15` adds:

- `incident_field_cache`: account/organization primary key, bounded authoritative
  JSON projection, local verification wall/elapsed clocks and boot counter.
- `incident_operation_dispatch`: primary key matching the existing durable queue
  sequence; parent sequence, prepared immutable canonical request, receipt/error.

No old rows, files, tables or queue history are removed. No destructive fallback.
Generated Room schema exports are intentionally untouched; a human's normal
subsequent Android build must generate the version-15 export.

An encrypted lease anchor uses the existing Android Keystore session adapter.
Room's clock fields alone cannot grant access. The lease is at most **24 hours**,
intersected with the existing organization authorization window and authenticated
session. Two-hour warning is separate from the unchanged registry 7-/1-day warnings.
Elapsed realtime plus wall time and boot count fail closed on rollback/reboot.
After reboot a new online verification is required. Successful denial clears the
lease/projection; a successful snapshot removes scopes no longer authorized.
An expired lease hides protected fields but does not erase pending evidence.
There is no offline password authentication or offline issuance authority.

Credential-changing sign-in/sign-out/Google actions serialize with field RPC
dispatch so a request captured for one account cannot use a newly switched account.
Composition/account/org keys cancel old collectors and foreground reads.
Scope checks precede requests and cache writes. A confirmed response may record
its receipt in the original account partition even if the screen has gone away.

## Durable operations and recovery

Task intents append `operation=INCIDENT_TASK` to the **existing**
`pending_hydrant_changes` table, with account, organization, entity, operation UUID,
immutable intent/payload/expected base version and local creation time.
Dispatch metadata is inserted in the same Room transaction. Hydrant-only DAO
queries exclude this discriminator so it cannot block or masquerade as a hydrant edit.
Existing scheduler selects the active account/org and the existing worker invokes
incident dispatch and the existing hydrant drain; shared mutex prevents duplicates.

States: LOCAL_PENDING → SENDING → SERVER_CONFIRMED, or OUTCOME_UNKNOWN on
transport/server uncertainty, NEEDS_ATTENTION on semantic rejection.
A restarted SENDING row is retried verbatim, and is shown as uncertain when no
matching in-process request is running. A definitive rejection is retained without automatic repair.
One assignment's rejected/uncertain parent does not block independent assignments.

An offline dependency A(ACK) → B(START) → C(COMPLETE) stores parent queue sequences.
Source inspection confirms that the canonical SQL increments assignment.version
once on a successful transition and receipt replay returns without executing that
update again. However the receipt's version is the INCIDENT version, not the
assignment version. The pilot no longer calculates expectedAssignmentVersion+1
or fabricates assignment state from it.

After a parent's receipt is durably confirmed, the child obtains an authorized
snapshot. Its exact assignment must remain executable, match the intended status
and task/incident identities, and have changed_revision equal to the parent's
receipt.revision. Only then is the returned assignment.version frozen into the
child's canonical request. A later edit/cancellation/reassignment, missing episode
or revision mismatch becomes NEEDS_ATTENTION (DEPENDENCY_CHANGED), never silent
rebasing. A transient read failure leaves the child unsent for later reconciliation.
A rejected parent blocks its children; independent assignments still progress.
Missing parent evidence is retained for review.

Prepared requests are immutable and retried with the same UUID even after process
death. No receipt is inferred from an observed task state. On a lost-response retry,
the canonical RPC supplies the original matching receipt. A prior confirmed event
newer than the cached projection can parent further LOCAL intent while offline,
but its authoritative version still has to be read before that child is sent.
This also avoids duplicate ACKs from a briefly stale cached ISSUED view.

The current assignment display is the latest authoritative snapshot, and operation
history shows each requested action separately from its delivery state. A receipt
is committed to Room before subsequent reconciliation, without an invented cache
version or renewed lease. A later read failure cannot relabel a confirmed mutation
as rejected. In-process dispatch activity determines SENDING; a restored SENDING
row without a live dispatch is shown as OUTCOME_UNKNOWN even if unrelated hydrant
work is running. A denial when recovering an earlier ambiguous send retains
NEEDS_ATTENTION with RECOVERY_REJECTED: it does not claim the earlier send failed.
No automatically generated replacement UUID is used.

Issuance and unit return are durable **online-only** proposals in the same queue.
They are never background issued. Explicit retry reuses the frozen original
request. An uncertain issuance survives process death and is offered for explicit
same-request retry from its incident. Closing an unsent form discards only the
in-memory proposal; a prepared/dispatched operation remains in history.

## Notifications, foreground freshness and navigation

FCM contains only the established account/event/type/category/entity_type/entity/
organization envelope; `entity_type=INCIDENT`, entity is incident UUID. No GPS,
instructions, names, signed URLs or secrets. Lock-screen content is generic.
The existing Firebase service triggers a coalesced refresh hint and existing
selected-scope worker even when notification presentation permission is denied.
Delivery never equals human acknowledgement.

A tap uses the existing deferred NotificationTap path through authenticated account
restoration and valid organization selection. It opens the incident inbox, not an
automatic ACK. Revoked/expired targets show unavailable/locked state.

The existing Supabase client installs Auth, Postgrest and Storage, **not Realtime**.
No dependency/Gradle change was allowed. Therefore PRIVATE Realtime, a full change
feed and revision-pinned multipage manifests remain deferred. This implementation
uses one conflated foreground refresh stream, 30-second bounded polling while
STARTED, resume refresh, push hints, and manual synchronization. Room is the
display source; neither FCM nor its metadata is treated as canonical content.

The existing MapLibre screen opens authorized incident/task point geometry and
shows cached canonical organization hydrants with existing location/nearby controls.
It does not show SIM or invented unit positions. The current Android turn-by-turn
session is plan/team-specific; arbitrary incident target navigation is not wired
to it and is not fabricated by creating a fake inspection plan. No arrival action
changes task status. Non-point task geometry stays readable as target context;
polygon/line navigation is not introduced.

## PR #82 integration correction — source contracts and remaining manual work

Corrected issues: implicit catalog/version coupling and missing draft constraints;
locally inferred assignment version/state; raw participant timeline JSON; old crew
episode visibility; inaccurate SENDING inference from unrelated worker activity;
and notification hint/link races. The original configuration.id lookup itself was

version; transition expects assignment version; unit return expects incident
version plus payload.version as a STRING. Existing requests are never automatically
sent by the worker unless their RPC is incident_transition_task_assignment.
