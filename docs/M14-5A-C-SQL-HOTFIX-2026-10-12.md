# GASILKO — M14.5A/C SQL ambiguity hotfix (2026-10-12)

## Scope

This is a **forward-only** repair for SQLSTATE `42702` seen in a manually
deployed M14 database:

- `public.simulation_command`: ambiguous `unit_id`, discovered when provisioning
  five simulation units. The user's database already received a manual
  `<<sim_vars>>` block-label repair and now displays five SIM positions.
- `private.validate_action_parameters`: ambiguous `d` when issuing a task.
  The user's database already received the manual `AS def(value)` repair.
- `private.incident_task_command`: ambiguous `r` when inserting task
  recipients. Task issuance was **not yet confirmed to work**.

**Do not edit** any previously applied migration. The repair belongs in:

`supabase/migrations/20261012120000_m145_sql_ambiguity_hotfix.sql`

The script is intentionally compatible with the known manual repairs. It
obtains existing installed function definitions, performs exact guarded
replacements only when necessary, and preserves current body extensions
(e.g. M14.5D navigation-related hooks), ownership, grants, SECURITY DEFINER
and search_path via `CREATE OR REPLACE FUNCTION` generated by PostgreSQL.
Unexpected function source stops the transaction with `HOTFIX_*_SOURCE_DRIFT`.

This is a source-reviewed repair; **it has not been run against the user's database**.

## Manually add it to GitHub

1. Create a new branch from `main`. PR #64 (M14.5E) is still open and must
   not be merged as part of this hotfix.
2. In GitHub choose **Add file → Create new file** and enter the full path
   `supabase/migrations/20261012120000_m145_sql_ambiguity_hotfix.sql`.
3. Paste the contents of the supplied `.sql` file verbatim.
4. Optionally create `docs/M14-5A-C-SQL-HOTFIX-2026-10-12.md` with this text.
5. Commit (`fix(m14): qualify PLpgSQL variables and SQL aliases [skip ci]`).
6. Open a single small PR and merge it yourself after review.

There are no Web or Edge Function changes required for this SQL hotfix.

## Manual SQL Editor execution (same target project as previous M14 migrations)

1. Confirm the correct Supabase project and take the desired backup/snapshot.
2. After checking that migrations through M14.5D have been applied, run only
   the **new** SQL file in Supabase SQL Editor (not the old migrations).
3. Expected notices include **already repaired** for `unit_id` and `d`
   on the current database, and **repaired** for `r` if it was not fixed.
4. If the migration throws `HOTFIX_*`, stop and inspect the installed
   function definition; **do not** keep applying arbitrary string patches.
5. Do not click "new task". Return to the already open task-confirmation dialog
   and choose **"Ponovi isto zahtevo"** with the existing operation UUID.
6. The `incident_issue_task` call should either succeed or show a new,
   specific error. If it fails, collect the PostgreSQL error code/message.
7. Only after task issuance works, choose an Action Definition whose
   **native behavior is `MOVE_TO` or `WITHDRAW_TO`**, and prepare an
   M14.5D road route from a SIM position using `incident-navigation`.

Important: a custom action labelled "Vzpostavi vodno oskrbo" is not
automatically a `MOVE_TO` action. Inspect its native behavior.

## Frontend React key warning (optional adjacent change)

`web/features/incidents/IncidentArea.tsx` on the inspected `main` gives
the three sibling components `IncidentCop`, `IncidentTasks`,
`IncidentResources` the **same** React `key`:

```tsx
key={`${account}/${org}/${detail.id}`}
```

Give each sibling a distinct prefix:

```tsx
<IncidentCop key={`cop/${account}/${org}/${detail.id}`} ... />
<IncidentTasks key={`tasks/${account}/${org}/${detail.id}`} ... />
<IncidentResources key={`resources/${account}/${org}/${detail.id}`} ... />
```

Only change the three `key` props. A separate `.patch` file is supplied
for local `git apply` workflows; in GitHub Web editor make the three edits
directly. This is a cosmetic React correctness fix, independent of SQL.
