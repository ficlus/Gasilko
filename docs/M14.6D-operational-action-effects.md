## Architecture and native kernel

The existing task/action-definition model, assignment episodes, SIM positions, scenario clock, hazard cadence and runner remain authoritative. There is no second clock, Cron, runner, task engine, route engine or wildfire model.

COMMAND INTENT != EXECUTION != PHYSICAL EFFECT.

The version-1 kernel supports APPLY_WATER, STOP_ACTIVITY (including stopping water), RESUME_ACTIVITY, CONNECT_SUPPLY, DISCONNECT_SUPPLY and explicit instructor REFILL. Repositioning stays in H1; observation is read-only through the existing map and history. These are capability codes, not localized label matching.

An instructor explicitly arms an execution, either against a configured task assignment or as a direct authorized instructor action. Task-backed arming requires the exact configured immutable action-definition version, unit recipient and frozen Point target. Only native behavior NONE can be bound, so MOVE_TO and WITHDRAW_TO never become suppression. Bindings fix flow and duration.

It never fabricates recipient acknowledgement or completion. This release does not automatically enroll every new task as a physical effect or create new autonomous tactical orders. Direct instructor arming is explicitly distinct from a task assignment.

## Resource and supply model

Private water resources track capacity, remaining liters, pump flow, reach, efficiency and optimistic version. They never modify permanent organizational inventory.

This bounded first kernel supports **finite virtual-unit tanks/reserves only**. A source also needs explicitly configured transfer/pump flow. A source may feed one consumer, a consumer has one source, and active links cannot share endpoints or chain. This deliberately excludes cycles, self-connections, unrestricted graphs and shared-source competition.

Canonical incident hydrant linkage remains contextual, not a physical water connection. Real hydrants have no inferred capacity, pressure or infinite policy. Hydrant/reservoir adapters and branching networks are not supported by this kernel; no fake unlimited fallback is introduced.

Connections must be within 100 m and both resources must be available and stationary. Source and consumer must belong to the same scenario. Both source and consumer versions are checked when connecting. Connections capture both SIM position versions; a subsequent position revision, release or unavailability invalidates supply until an explicit disconnect/reconnect. Legacy connections have no trustworthy baseline and must also be reconnected. Reconnection is allowed for a BLOCKED consumer, followed by explicit RESUME; it does not rearm automatically. Active source tanks cannot simultaneously run their own suppression.

REFILL is an explicit, reasoned instructor addition to simulated inventory, capped by configured capacity. It is not a claim that a real source supplied water. The quantity, reason, actor and operation are retained. Disconnecting blocks an active consumer; it never silently switches to its own tank.

## Consumption and suppression equations

Each existing five-second hazard step processes operational effects after normal hazard progression and before the existing queued boundary effects for that step:

1. Existing queued effects at the previous boundary.
2. Existing M14.6C fire/smoke progression.
3. Eligible operational executions, ordered by execution UUID.
4. One final hazard step record, marked STEP_WITH_OPERATIONS when delivery occurred.
5. Existing instructor/scenario-event effects due at the new boundary.

For each execution:

```text
rate = min(requested, consumer pump, source pump, connection flow)
requested_liters = rate * min(5, remaining active duration) / 60
delivered_liters = floor(min(source remaining, requested_liters) * 1000) / 1000
```

For the consumer's own tank, connection/source pump terms are omitted. Fixed numeric inventory uses 0.001 L precision. New configuration, refill and flow commands reject finer precision rather than silently rounding it. New flows must be at least 0.012 L/min (one millilitre per five-second step); legacy zero-delivery flows become BLOCKED with FLOW_BELOW_PRECISION without consuming water or advancing active duration. No negative inventory and no consumption beyond remaining capacity.

The target is a validated Point; eligible existing burning cells have centers within a fixed 25 m footprint. The source must have an authoritative stationary SIM position within its configured 1–100 m reach. Its captured position version must remain unchanged; moving it blocks the execution and requires explicit review/resumption.

```text
per_cell_reduction = delivered_liters * configured_efficiency / eligible_burning_cells
next_intensity = round(max(0, previous_intensity - per_cell_reduction), 6)
```

No active cells means completion with zero consumption. No fuel, source template, real hydrant status or GPS is rewritten. Smoke/heat continue through the existing hazard model; this is not certified hydraulic engineering or real-world fire prediction.

## Transaction, cadence and fairness

The existing `simulation_hazard_batch` invokes a private step helper inside its existing per-model subtransaction. No Edge Function modification is necessary: the current runner already calls this batch.

Lock ordering reuses `agent_locks`: environment/organizations/people, incident, scenario and clock before model/resource rows. Commands use the same lock path. Existing batch fairness, four-model bound, ten-step catch-up, two-second work budget and isolated error handling remain.

Each execution's durable last_step advances with its inventory debit and hazard state in the same transaction. A rollback rolls all of them back. Concurrent ticks cannot double-consume the same interval. Inventory/connection changes reject unprocessed active catch-up; stop and disconnect remain available even when the operational history admission budget is exhausted. Disconnect also remains available for an unavailable consumer or a model still catching up; it blocks the consumer before further water delivery. Resume sets a fresh baseline and never replays blocked time.

Pause does not advance effects. RESET and FINISH cancel live executions and end connections while preserving inventory and append-only history; RESET does not conjure replacement water. This is execution reset, not full replay: foundation resets active SIM positions, C queues the initial hazard configuration at a step boundary, but the clock, tasks, event receipts and history do not rewind. PAUSE/RESUME continues the same exercise without inventory changes. A fresh scenario instance is the path for initial inventory and a new exercise. The resource UI states this explicitly. FINISH never completes tasks or closes the incident.

## Authorization and recovery

State is private, RLS-enabled, without table grants even for application service_role. Only restricted security-definer RPCs expose reads/mutations. No browser inventory or hazard writes.

Commands require authorized training visibility, operator access, scenario controller, template editor and existing active command authority. Task executions additionally recheck the original issuing actor through the factored canonical M14.5A command-scope predicate and recipient eligibility at arming and each step. The existing can_issue_task wrapper retains its authenticated acting-membership gate; the actor-explicit helper is private with no client/service-role execution grant. The effective-role predicate checks current active account, organization membership, participation, incident state and role validity. No token impersonation is used.

This kernel supports INCIDENT_UNIT recipients with an explicit immutable NONE-behavior binding and Point target. INCIDENT_CREW_MEMBER is explicitly rejected. M14.5A UNIT_LEADER authority applies only to subordinate crew members and remains available for normal tasks; it does not authorize arming unit-level effects. No simulator-only role is added. If command handover removes the original issuer's authority, the armed execution blocks on the next processed step; a different controller cannot adopt it simply by resuming. A new authorized task/arming is required unless the original issuer legitimately regains the required scope. Existing cancelled/terminal assignments remain ineligible. Released/unavailable/moving resources, hidden/disabled hazards and cancelled/terminal tasks cannot keep applying effects.

Mutations use the existing immutable template receipt store. Identity binds actor, organization, operation UUID and the exact incident/action/expected-version/payload request. Receipt lookup precedes live-state/version rejection, so lost-response retries remain recoverable after FINISH. A changed request cannot reuse an operation.

The existing shared mutation hook persists the exact request before dispatch. One scoped mutation instance serves every resource panel, preventing independent controls from overwriting the same pending record. Unknown outcomes retain the request and offer exact retry. No automatic conflict resolution or automatic rearming occurs.

BLOCKED is durable. The instructor can stop it or explicitly resume after fixing the cause. Completed/cancelled executions cannot restart. An assignment has at most one execution record, including history.

## Final correction: confirmed source defects

- Independent inline issuer roles are replaced by reuse of the canonical command relationship predicate, with explicit unit-only kernel recipients and eligibility checks.
- NULL execution history previously exposed raw refill reasons to participants. Recorded visibility plus an allowlisted projection closes that path.
- Connections previously checked only current availability/range and could survive a source moving away and back. Position baselines now require explicit reconnect; source version increments on disconnect.
- A BLOCKED consumer previously could not reconnect without stopping its unique task execution. It can reconnect while blocked and then explicitly resume.
- Disconnect could be blocked by unavailable consumer/catch-up, and STOP by the history admission budget. Both cleanup paths remain accessible under their existing authority/version gates.
- Sub-millilitre inputs could be rounded by fixed-scale storage; very small flows could advance an execution with no water. Precision validation and durable FLOW_BELOW_PRECISION prevent these outcomes.
- Pending retry feedback was nested inside resource panels and disappeared on read failure. One shared recovery surface now remains available while the SIM scope is authorized; confirmations do not cover it while a request is pending.
- A selected task that disappears from the eligible read no longer silently falls back to direct instructor arming; the user must explicitly change the selection.
- UI distinguishes armed versus awaiting ACK, pause/finished state, own versus connected water, and confirmed-server/storage-cleanup state. Map overlays do not imply active delivery while paused or lagging; stale connections are not drawn.
