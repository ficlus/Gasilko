# CODEX IMPLEMENTATION PROMPT — M14.5F3
## Tactical Incident Objects & RTS Map-First Creation

You are implementing **M14.5F3 — Tactical Incident Objects & RTS Map-First Creation** in the existing Gasilko monorepo.

**Prerequisite:** PR #66 (M14.5F2 — RTS Context Commands) has been merged into `main`.

Create one focused implementation branch and pull request targeting the latest `main`. Do not merge it.

## 1. Objective

Allow authorized incident commanders to create, inspect, edit, and deactivate tactical incident objects **directly from the Poveljniška karta**, using the existing right-click / long-press interaction.

Required user workflow:

1. Right-click an empty map location.
2. Choose a tactical object type.
3. Enter a short name and optional description.
4. Preview its exact geographic position.
5. Confirm using the existing COP command workflow.
6. The server persists the object.
7. The confirmed object appears on the map with a recognizable icon.
8. Right-click the existing object to view, edit, or deactivate it.

Keep the existing **Klasični pogled** fully operational.

Do not implement drag-and-drop unit movement or a separate map application.

## 2. Critical discovery: reuse existing COP objects

The repository already has a tactical map-object model.

Current frontend definitions include:

`web/lib/incidents/cop.ts`

```typescript
export const mapKinds = [
  'COMMAND_POST',
  'STAGING',
  'HAZARD',
  'WATER_SOURCE',
  'ACCESS_POINT',
  'PERIMETER',
  'NOTE',
] as const;
```

Existing semantics:

- `COMMAND_POST` = Poveljniško mesto
- `STAGING` = Zbirno mesto
- `WATER_SOURCE` = Vodni vir
- `HAZARD` = Nevarnost
- `ACCESS_POINT` = Dostopna točka
- `PERIMETER` = Obod / zapora
- `NOTE` = Opomba

The current COP supports:

- incident-scoped objects;
- persistent point/line/polygon geometry;
- object identifiers and versions;
- incident and sector scope;
- object create/update through `object_put`;
- object deactivation through `object_deactivate`;
- established confirmation, conflict, audit, and authorization flows.

**Do not introduce a duplicate `tactical_objects` table or parallel object API.**

Extend the current COP infrastructure instead.

### Missing object type

Introduce:

`TRIAGE_POINT` = Triažna točka

Only add database changes necessary to make that new type valid in the existing backend.

Do not invent a new `ASSEMBLY_POINT` type because the current `STAGING` type already represents the existing Slovenian "Zbirno mesto".

Do not duplicate `WATER_SOURCE` as `TEMPORARY_WATER_SOURCE`. In this feature, the existing incident COP water-source object represents a temporary incident annotation; permanent hydrants continue to live in their separate register.

- Reuse expected-version checks, retry behavior and conflict handling.
- Avoid generating a new UUID or changed payload during retry of an ambiguous response.
- Never bypass the existing incident command APIs with direct browser table writes.

The example above is illustrative; inspect the exact existing command payload contract and match it.

**Do not duplicate the server-side authorization or command engine in the new UI.**

## 10. Server-side permissions

Only authorized incident-command roles may create or modify tactical objects.

Follow the actual existing command model.

Required policy:

- Incident commander: authorized within actual current command scope.
- Delegated/sector commander: authorized only within their granted operational scope.
- Ordinary participant: read access only where permitted.
- Organization administrator without incident command authority: no automatic tactical write access.
- Revoked/expired command role: no new mutations.
- Closed/cancelled incident: respect existing mutation restrictions.

Do not weaken the current authorization model.

If `cop.can_manage` or sector `can_edit` is already authoritative and sufficient, reuse it.

If any current path allows unauthorized organizational administrators to create tactical objects independently of incident command authority, fix that server-side permission path narrowly without changing unrelated administrative behavior.

Do not trust `can_manage` flags sent by the browser.

The server must resolve acting identity, organization, incident and current command scope itself.

Preserve RLS and existing RPC security posture.

## 18. Operational safety

Preserve:

**COMMAND INTENT != EXECUTION PLAN != OBSERVED TELEMETRY**

A tactical object is a map annotation, not:

- a task assignment;
- proof that a vehicle arrived;
- a navigation session;
- GPS telemetry;
- a real-time inventory record;
- a permanent hydrant.

Do not automatically move units when a tactical object is created.

Do not automatically create a task when a command post or triage point is created.

Only use actual configured actions when a user explicitly chooses to send units to an existing point object.

SIM objects are incident-scoped training records, never ordinary operational annotations.

The shared Supabase project must not allow cross-incident or cross-org mutations.
