## 1. Main goal

Turn M14.5A's form-based multi-recipient task engine into a fast, tactical, map-first command interaction workflow.

Desired operator flow:

**Select recipients → Choose configured action → Select target → Review → Explicitly confirm → Issue task → View status.**

The commander should not need to leave the active incident map or repeatedly search for already selected units.

Support:

1. Single selection.
2. Ctrl/Cmd multi-selection.
3. Shift range selection in ordered lists.
4. Rectangle/box selection on the map.
5. Freehand/lasso selection on the map.
6. Persistent in-workspace selection summary.
7. Configurable action command palette.
8. Target acquisition from map click or existing objects.
9. Bulk task issuance through M14.5A.
10. Read-only command-intent overlays.
11. Keyboard shortcuts.
12. Responsive mouse, keyboard and touch interaction.
13. Clear eligible/ineligible recipient feedback.
14. Existing task detail and execution status integration.

The result must feel like one operational command workspace, not another independent feature page.

## 2. Non-negotiable architectural principle

**COMMAND INTENT != EXECUTION PLAN != TELEMETRY**

Example:

Commander orders:

> GVC-1, move to point X.

This creates a command/task assignment.

It does NOT:

- move GVC-1's map marker;
- change its actual position;
- create a GPS observation;
- mark the unit EN_ROUTE;
- calculate road routing;
- create a navigation session;
- generate ETA;
- infer arrival;
- assume the command has been acknowledged.

A unit without an authoritative actual position must remain without a physical position marker.

A sector assignment is NOT the physical unit location.

A polygon centroid is NOT a unit position.

A vehicle's permanent inventory location is NOT the current location of its deployed incident unit.

This milestone is primarily about **command interaction and visualization of intent**, not movement execution.

## 4. RTS interaction state

Add a small, explicit interaction state model to the existing IncidentWorkspace or a closely scoped controller.

Suggested conceptual model:

```ts
type RtsMode =
  | 'NORMAL'
  | 'SELECT_BOX'
  | 'SELECT_LASSO'
  | 'CHOOSE_TARGET';

type RecipientSelection = {
  type: 'INCIDENT_UNIT' | 'INCIDENT_CREW_MEMBER';
  id: string;
};

type RtsSession = {
  mode: RtsMode;
  recipients: RecipientSelection[];
  actionVersionId: string | null;
  target: ExistingOperationalTarget | null;
};
```

These are conceptual interfaces. Reuse actual existing M14.5A types rather than creating incompatible duplicates.

Rules:

- RTS selection is local presentation state, not a new database relationship.
- Preserve the existing `SelectedEntity` and single-entity deep-link behavior.
- Do not overload the URL with a large list of recipients.
- One selected detail entity may coexist with an RTS multi-selection.
- Store recipient identity as **type + ID**, not display name or map feature ID.
- Clear transient RTS state when incident, acting organization or authenticated account changes.
- Prevent selection from leaking between incident contexts.
- Cancelling the flow must not modify task or unit data.
- Refreshing read data must not silently change the meaning of an already prepared command.
- Navigation away from the workspace must not accidentally issue a command.

Existing ordinary map interaction remains available in NORMAL mode.

## 5. Recipient eligibility and identity

Supported task recipients are exactly those already supported by M14.5A:

- `INCIDENT_UNIT`
- `INCIDENT_CREW_MEMBER`

Distinguish:

- deployed incident unit = possible recipient;
- active matching crew member = possible recipient;
- permanent vehicle inventory record = not automatically a recipient;
- hydrant = target, not recipient;
- sector = target/context, not recipient;
- tactical map object = target, not recipient;
- inspection team = not an incident unit;
- resource allocation = not automatically a task recipient.

Reuse the existing authorized recipient read API.

Relevant existing read patterns include:

- `incident_task_recipients`
- `incident_resource_selection_page`

Do not introduce a new unbounded incident-wide personnel download.

Display at least:

- recipient name/callsign;
- recipient type;
- owning organization/agency;
- current incident sector where available;
- incident/deployment state where available;
- selection state;
- command eligibility;
- concise ineligibility reason when safely known.

**Server authority is final.**

The UI may prefilter using already authorized read-model information, but it must never treat visible geometry, organizational ADMIN/MANAGER membership or a selected map object as proof of command authority.

Preserve M14.5A authority:

- IC incident-wide scope;
- Agency Commander own-agency scope;
- Sector Commander explicit sector scope;
- Unit Leader own-unit/crew scope;
- no automatic Deputy promotion;
- no inherited organizational WRITE authority;
- no authority inferred from geographic polygon containment.

Do not expose hidden recipients merely to provide an "ineligible" row.

If backend eligibility cannot be determined safely from the existing API, show an appropriately neutral state and rely on authoritative validation before issuance.

- Click ordinary object without RTS selection modifier → preserve existing `SelectedEntity` and contextual actions.

## 8. Rectangle / box selection

Add an explicit **Box Select** map tool.

The user activates the tool, then drags a screen-space rectangle across the map.

Use MapLibre projection or its existing map layer feature query to identify **currently displayed, authorized, actual unit-position features** within the rectangle.

Do NOT synthesize unit coordinates to make units selectable.

Rules:

- The tool must work with actual rendered recipient features only.
- Do not select hydrants, sectors, map objects or permanent vehicles as recipients.
- Do not select a unit merely because its sector polygon overlaps the rectangle.
- Do not select units hidden by authorization.
- Do not select units that exist only in a text list but have no actual map location.
- Deduplicate by recipient type + canonical ID.
- Disable map dragging/panning only while the selection gesture owns the pointer.
- Restore normal map controls after completion/cancellation.
- Do not interfere with existing sector/map-object drawing tools.

If current M14 implementation has no authoritative physical unit positions, box selection must:

- remain architecturally ready for future position layers;
- not fabricate selectable markers;
- show a clear localized empty/unavailable explanation;
- leave normal list-based selection fully usable.

This is preferable to fake position markers.

## 9. Lasso selection

Add a freehand lasso tool using pointer coordinates in the rendered map viewport.

Suggested algorithm:

1. On pointer down, start collecting local screen coordinates.
2. Sample movement sufficiently for a usable polygon without excessive points.
3. Show a temporary lasso outline.
4. On pointer release, close the local screen-space polygon.
5. Evaluate authorized visible recipient marker screen coordinates using a standard point-in-polygon algorithm.
6. Deduplicate selected recipients.
7. Merge or replace selection according to the explicit interaction mode.
8. Remove the temporary lasso geometry.

Prefer screen/pixel geometry for the selection gesture. This is UI selection, not geographic GIS geometry.

Do not persist the lasso to `incident_map_objects`.

Do not create a new spatial table or PostGIS dependency.

Do not accidentally select all units whose sector geometries intersect the lasso.

Apply a bounded point/vertex sampling approach and avoid expensive calculations on every pointer move.

If no actual unit markers exist, the lasso simply selects none, with appropriate explanation.

## 13. Target selection mode

Add explicit **Choose Target on Map** mode after an Action Definition is chosen.

Supported existing M14.5A target types:

- `NONE`
- `HYDRANT`
- `INCIDENT_MAP_OBJECT`
- `INCIDENT_SECTOR`
- `COORDINATE`

The selected Action Definition determines which target types are allowed.

The interface must never offer a target type that the selected action version disallows.

### Target acquisition

Hydrant click:

- use existing canonical hydrant UUID;
- reuse existing authorized hydrant/map data;
- preserve ordinary hydrant status;
- no hydrant record copy.

Sector click:

- preserve existing sector UUID;
- preserve sector geometry semantics;
- do not reinterpret sector as a point.

Tactical map object click:

- preserve canonical same-incident object UUID;
- preserve original geometry type.

Free coordinate click:

- use MapLibre geographic coordinates;
- store WGS84 longitude/latitude in the correct order;
- use the existing `OperationalTarget` representation;
- display the coordinates before confirmation.

`NONE` target:

- supported only where Action Definition allows it;
- no map click required.

### Point-only native behaviors

For:

- `MOVE_TO`
- `WITHDRAW_TO`

the target must resolve to an actual point under the existing M14.5A rules.

A sector polygon is NOT converted to its centroid.

A line/polygon tactical object is NOT silently converted to a point.

If a target is invalid, show a localized explanation and allow correction.

Client-side checks improve UX; server validation remains authoritative.

### Map mode safety

During target selection:

- show visible target-acquisition cursor/crosshair;
- distinguish target selection from normal object selection;
- keep existing pan/zoom usable;
- provide Cancel target selection;
- Escape exits target mode;
- prevent accidental map-object editing/drawing;
- prevent accidental command issuance;
- do not persist a new tactical object for a free coordinate click.

Do not infer authorization from the clicked geometry.

## 20. Failure and concurrency handling

Preserve M14.5A operation semantics.

### Stale versions

If incident/task/action/recipient state becomes stale:

- display a clear localized conflict message;
- retain the operator's draft selection and intent where safe;
- refresh authoritative data;
- require explicit review/reconfirmation;
- do not silently replay a changed payload under the old operation ID.

### Ambiguous transport failure

If the server may have committed a command but the response was lost:

- preserve the exact original payload and operation ID;
- allow an idempotent retry using existing infrastructure;
- do not generate a new task UUID merely because the request timed out;
- do not create duplicate assignments.

### Authorization loss

If incident membership or command authority becomes invalid:

- stop the issuance flow;
- clear inaccessible read data;
- never continue with cached authorization;
- display an appropriate SI/DE explanation.

### Incident closure

For terminal incidents:

- preserve historical viewing;
- disable issuance and mutation controls;
- do not delete historical task overlays.

For released units or invalid crew membership:

- honor existing server-side guards.

### Partially loaded data

If the catalog/recipient data cannot load:

- show retry or explicit unavailable state;
- do not silently treat unknown recipients as authorized.
