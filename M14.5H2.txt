## 6. Live remaining-route visualization

When a vehicle advances along an existing committed route, the displayed route must progressively shorten.

The user should see the **remaining route**, not the entire original route drawn permanently behind the unit.

### Algorithm requirements

For each moving unit:

1. Read its currently authoritative navigation route.
2. Read the actual permitted position/progress source.
3. For SIM units, prefer authoritative agent progress along the assigned route when available.
4. For real units, use real observed GPS position only when available and valid.
5. Calculate or read the corresponding progress location on the route.
6. Clip the route polyline from progress to destination.
7. Display the remaining segment.
8. Update only when relevant state changes.

Do not modify the original stored route geometry.

Do not rewrite navigation history.

Do not call OSRM for every position tick.

Do not teleport a unit to the nearest segment.

Do not interpret an uncertain or stale GPS fix as reliable route progress.

### Numerical robustness

Account for:

- Short segments.
- Repeated coordinates.
- Long or complex polylines.
- Self-intersecting routes.
- Reversed travel directions.
- Position/progress precision differences.
- Zero-length sections.
- Route replacement.
- Stale or out-of-order location updates.
- Off-route positions.

Do not use a naive nearest-point algorithm that can jump to a later segment when the same road is traversed twice.

For SIM, rely on existing `progress_m`/route identity where available.

Clamp the displayed progress to the valid route length.

Avoid showing a route snapping backward from out-of-order telemetry.

Route shortening is a visualization concern, not a mutation of execution state.

## 10. H1 automatic SIM execution integration

M14.5H1 introduces durable server-side SIM automation.

This PR must make that automation understandable and practical in Command Map.

### Expected workflow

When scenario automatic execution is ON:

```text
Select unit / group
        ↓
Right-click map target
        ↓
Choose configured action
        ↓
Review and confirm
        ↓
Server accepts task
        ↓
H1 auto-enrolls eligible assignments
        ↓
Route planning where required
        ↓
Navigation becomes visible
        ↓
SIM agent starts automatically
        ↓
Existing Cron advances movement
```

The user must not need to press **Avtonomno vozi** separately for an eligible automatically handled assignment.

### Automatic execution state

Display the actual effective state:

- Automatic execution ON/OFF.
- Queued.
- Planning route.
- Route ready.
- Starting agent.
- Running.
- Blocked.
- Failed.
- Manual handling required.

Never show running before server confirmation.

### Important boundary

If automatic execution is OFF, preserve the existing manual workflow.

Do not secretly enable scenario automation.

Do not bypass required human confirmation.

Do not duplicate the H1 task/worker engine in React.

Do not add a browser polling scheduler.

If an actual H1 integration defect prevents automatic execution, implement a minimal fix in the owning component and explain exactly why it was needed.

Do not reimplement the whole orchestration engine.

## 17. Security and domain invariants

Mandatory:

**COMMAND INTENT != EXECUTION PLAN != TELEMETRY**

**REAL GPS != SIM POSITION**

**TASK ACCEPTANCE != HUMAN ACKNOWLEDGMENT**

- A navigation route is an execution plan, not proof of movement.
- Only actual simulation position/progress advances SIM visualization.
- Only actual observed GPS advances real units.
- Task issuance must never move a real unit.
- No simulated ACK may become a human ACK.
- No new authority inferred from control groups.
- No authority inferred from sector geometry.
- No new task mutation through map inspection.
- No access to routes belonging to unauthorized incidents or organizations.
- No browser service-role keys.
- No changes to the existing H1 runner secret or Cron security.

Preserve server-side validation and version guards.
