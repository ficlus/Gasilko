4. REQUIRED SERVER VERIFIER
===========================================================

Prefer implementing a small isolated server-side
cryptographic verification module using existing
Supabase Edge/Deno capabilities, if justified by the
actual source architecture.

Use standards-based WebCrypto where supported.

Expected algorithm:

P-256 / secp256r1
ECDSA
SHA-256

Public key:

RFC 5480 SubjectPublicKeyInfo
DER encoding
P-256 named curve
91-byte canonical public key representation

Signature:

Android JCA SHA256withECDSA returns ASN.1 DER.

Android DeviceProofEncoding provides DER-to-raw64 conversion.

WebCrypto verification should use exactly:

r[32] || s[32]

A verifier must check:

- exact SPKI encoding
- correct P-256 curve
- public point validity
- public-key fingerprint
- valid signature encoding
- signature length
- r and s scalar bounds
- exact challenge transcript
- supported protocol version
- matching registered credential
- matching authenticated identity

Reject:

- wrong curve
- malformed SPKI
- private key material
- altered transcript
- unknown protocol version
- zero or out-of-range ECDSA scalars
- truncated signature
- wrong signature encoding
- incorrect credential fingerprint

No fallback to a weaker algorithm.

No client-provided "verified=true" flag may count as proof.

Do not pretend PostgreSQL pgcrypto provides an
ECDSA/SPKI verifier without verifying its actual API.

If a trusted server verifier cannot be securely exposed,
implement a pure cryptographic module and document
the blocked callable path.

Do not create a dummy accept-all verifier.

8. TRUSTED CHALLENGE PROTOCOL
===========================================================

Implement safely where possible.

STEP 1 — ISSUE CHALLENGE

Authenticate the caller.

Recheck exact live authority in the database.

Reject if policy is unapproved and the requested
ceremony would constitute operational pairing.

For an authorized future inactive ceremony:

- identify the stored credential
- use a server-generated 32-byte nonce
- allocate a challenge UUID
- bind the exact 27 transcript fields
- record issued and expiry timestamps
- record original issue operation UUID
- record confirm operation UUID
- enforce request immutability
- enforce bounded outstanding challenges

Never let a client choose a replacement nonce or
retarget a challenge to another incident/vehicle.

STEP 2 — ANDROID SIGNS

The client uses the existing M15A.1 signer.

It must:

- check current identity context before signing
- check again after signing
- open an existing key without silent regeneration
- sign exactly the server transcript
- convert DER signature to raw64 as specified
- preserve original operation IDs
- never treat signing as accepted vehicle binding

Do not automatically invoke the signer on login.

STEP 3 — SERVER CRYPTOGRAPHIC VERIFICATION

Retrieve registered SPKI from trusted storage.

Do not accept an arbitrary replacement public key
supplied by the client.

Build exactly the same transcript bytes.

Verify ECDSA P-256 SHA-256.

Failure means no accepted proof.

A successful mathematical verification only proves
possession of the matching private key.

It does not approve location sharing.

STEP 4 — ATOMIC FINALIZATION

Consume the challenge exactly once.

Recheck:

- JWT actor
- exact organization
- incident and deployment
- current driver role
- vehicle assignment
- credential generation
- challenge expiration
- revocation
- expected versions
- immutable operation request

Allowed successful result:

PROOF_VALIDATED_INACTIVE

Never return:

GPS_ACTIVE
SHARING
PAIRING_APPROVED
CONSENT_APPROVED

STEP 5 — UNKNOWN OUTCOMES

A network timeout must not be treated as rejection
or as successful verification.

Original immutable operation UUID is retained.

Same operation ID and same request may recover
the original authoritative outcome.

Same operation ID and changed request must fail.

Different operation ID on an already consumed
challenge must fail.

Never allocate a new nonce during an original retry.

9. REAL CONCURRENCY PROTECTION
===========================================================

An Edge Function is not automatically part of one
PostgreSQL transaction.

Do not claim that:

SELECT challenge
await crypto.verify()
UPDATE challenge

is atomic.

If implementing an Edge verifier, use a properly
designed two-transaction claim/finalize protocol.

TX-A: CLAIM

Within an authenticated database boundary:

- lock challenge and credential consistently
- check authorization and current versions
- require challenge state ISSUED
- check trusted expiry
- check immutable request fingerprint
- check credential not revoked
- atomically reserve the challenge
- create a short-lived claim token/lease
- commit

OFF-DB: VERIFY

- import registered SPKI
- validate exact transcript bytes
- verify the raw64 ECDSA signature
- classify failure safely

TX-B: FINALIZE

Inside a trusted privileged boundary:

- validate claim identity/token
- lock the same challenge and credential
- check exact original request
- recheck current driver/incident scope
- recheck entity versions
- recheck revocation and expiry
- transition CLAIMED -> VERIFIED_INACTIVE
  only after genuine signature verification
- write immutable outcome/receipt
- commit

If verification fails:

- never produce VERIFIED_INACTIVE
- use an explicit bounded failure policy

If Edge crashes after CLAIM:

- outcome remains UNKNOWN
- do not create success
- claim expiration permits safe recovery
- no concurrent successful finalizations

If credential is revoked between CLAIM and FINALIZE:

- revocation must win
- confirmation fails
- stale requests cannot reactivate it

IMPORTANT TRUST BOUNDARY:

A client must never be able to call a public
finalize RPC with "signature_valid=true".

If the current infrastructure cannot securely
distinguish the trusted verifier from a client,
do not expose the endpoint.

Implement the pure verifier and document
the missing privileged boundary instead.
