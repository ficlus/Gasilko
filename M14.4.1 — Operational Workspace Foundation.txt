Implement one PR:

M14.4.1 — Operational Workspace Foundation

Base this work on the current main branch after M14.4 / PR #57 is merged.

This milestone is an integration and operational UX milestone.

It MUST NOT redesign the existing M14 domain model.

The goal is to turn the current incident detail page into the foundation of a real map-first incident command workspace before M14.5 adds tasking / RTS-style commands.

==================================================
CORE ARCHITECTURE RULE
==================================================

Preserve all existing domain and business semantics.

Do not redesign or bypass:

- authoritative tables,
- incident lifecycle/state machines,
- command authority,
- incident participant rules,
- Unit Leader rules,
- sector command rules,
- RLS,
- authorization,
- audit,
- idempotency,
- optimistic concurrency,
- existing canonical hydrant identity,
- inventory ownership,
- routing-provider boundaries,
- Android/offline contracts.

However, integration-safe changes to previous presentation/read modules are ALLOWED AND EXPECTED.

You may:

- extract shared map/presentation infrastructure,
- add bounded authorized read adapters,
- add contextual actions,
- compose existing domains into one operational workspace,
- add optional presentation hooks to existing components,
- reuse authoritative RPCs/APIs from another view.

Do NOT copy/fork business logic.

Cross-module mutations MUST call the original authoritative API/RPC and preserve its authorization, concurrency and audit semantics.

==================================================
VERY IMPORTANT FUTURE RTS PRINCIPLE
==================================================

This milestone prepares the UI architecture for future RTS-style command interaction, but DOES NOT implement the command/task engine yet.

The future model is:

select entity/entities
    ->
choose command/action
    ->
choose target
    ->
confirm intent
    ->
authoritative server command
    ->
execution / acknowledgement / telemetry later

Do not implement tactical actions such as:

- EXTINGUISH,
- DEFEND,
- RECON,
- WATER SUPPLY,
- SEARCH,
- RESCUE

as hard-coded commands in this milestone.

Future tactical actions will be configurable Action Definitions.

Do not invent a command vocabulary now.

Also preserve this future architecture principle:

COMMAND INTENT != EXECUTION PLAN != TELEMETRY

Example for future use:

COMMAND:
"move Unit A to Point X"

NAVIGATION EXECUTION:
current planned route / ETA

TELEMETRY:
actual GPS position

Do not conflate these concepts.

No GPS or navigation-session implementation belongs in this PR.

==================================================
1. INCIDENT WORKSPACE — MAP FIRST
==================================================

Refactor the ACTIVE / STABILIZED incident experience into a proper operational workspace.

The current long vertical IncidentArea must no longer make the user scroll through metadata, command, participants and timeline before reaching the COP.

For ACTIVE and STABILIZED incidents, implement a map-first desktop workspace conceptually like:

┌────────────────────────────────────────────────────────────────────┐
│ INC-2026-...  ACTIVE | type | lead org | commander | attention    │
├─────────────────┬────────────────────────────┬─────────────────────┤
│ OPERATIONAL     │                            │ SELECTED            │
│                 │                            │                     │
│ Command         │                            │ entity details      │
│ Sectors         │            MAP             │ status              │
│ Units           │                            │ context actions     │
│ Crews           │                            │                     │
│ Resources       │                            │                     │
│ Participants    │                            │                     │
├─────────────────┴────────────────────────────┴─────────────────────┤
│ Requests / command inbox / timeline / history                     │
└────────────────────────────────────────────────────────────────────┘

This is conceptual, not a requirement for exact pixel dimensions.

Requirements:

- Map is the primary operational surface.
- Existing incident metadata remains accessible.
- Command hierarchy remains accessible.
- M14.4 units / crews / resources become part of the operational left pane.
- Timeline/history becomes secondary and must not push the map below a large page.
- Existing command inbox/request functionality remains accessible.
- Existing COP functionality remains fully available.
- Do not remove any existing M14.0–M14.4 capability.
- Do not change authorization merely because the controls move.

DRAFT incidents may retain a more form/setup-oriented layout.

CLOSED / CANCELLED incidents must remain historical/read-only.

Responsive behavior:

Desktop:
- operational pane,
- map,
- selected entity pane.

Tablet:
- map remains primary,
- side panes may collapse/drawer.

Mobile:
- no requirement to emulate a desktop RTS UI,
- use tabs/drawers/stacking as appropriate,
- all information and actions must remain accessible.

No drag/drop-only workflow.

==================================================
4. AUTHORIZED BACKGROUND HYDRANTS ON INCIDENT MAP
==================================================

This is a required feature.

Today the COP shows hydrants primarily after they are explicitly linked to the incident.

For operational awareness, the incident map must also be able to show ordinary canonical hydrants that the current user is ALREADY authorized to read through the existing Hydrants authorization model.

Important:

INCIDENT PARTICIPATION MUST NOT GRANT HYDRANT REGISTRY ACCESS.

Do NOT broaden hydrant RLS.

Do NOT expose another organization's hydrants merely because that organization participates in the same incident.

Background hydrants must use the same effective read scope that the existing Hydrants module uses.

Use a bounded viewport-based read.

Requirements:

- query by visible map bounds,
- debounce viewport changes,
- bounded result count,
- active hydrants by default unless existing hydrant semantics require otherwise,
- preserve canonical hydrant UUID,
- no hydrant copies inside incident tables.

Background hydrants:

- subtle/smaller visual representation,
- preserve permanent hydrant status,
- should not visually imply that they belong to the incident,
- labels only when useful / selected / sufficient zoom.

Incident-linked hydrants:

- use the SAME canonical hydrant,
- render stronger than background hydrants,
- appear above the background layer,
- display incident context separately from permanent hydrant status.

Important visual rule:

DO NOT overload one color with multiple meanings.

Permanent hydrant status and incident relationship must use different visual channels.

For example:

marker fill/interior:
- canonical hydrant status

outer ring / secondary marker affordance:
- incident relationship/purpose

Do not make a linked hydrant lose its canonical status semantics.

5. HYDRANT SELECTION AND CONTEXT
==================================================

Clicking a background hydrant should select the canonical hydrant and show it in the right-side Selected Entity pane.

At minimum show authorized data such as:

- identifier/name,
- status,
- type if already part of authorized DTO,
- relevant organization display context,
- existing incident link state.

Existing authoritative actions may be surfaced contextually.

Examples where permitted:

- Open hydrant details
- Link as WATER_SUPPLY
- Link as REFERENCE
- Unlink existing incident relationship

Do not duplicate link/unlink business logic.

Use the existing authoritative incident hydrant APIs/RPCs.

Do not add unauthorized hydrant information to incident shared DTOs.

Do not expose private data simply because the hydrant is selected.

Navigation is NOT implemented in this milestone.

The UI may be architected so a future Navigate action can be added, but do not introduce a fake/stub navigation workflow.

==================================================

Do not redesign the M14.4 data model.

- active incident units,
- unit status,
- sector assignment,
- crew,
- Unit Leader,
- relevant allocations/resources.

IMPORTANT:

- do NOT place units on the map just because they exist,
- do NOT infer unit location from sector geometry,
- do NOT infer unit location from organization/vehicle/home station,
- do NOT create fake "ON_SCENE" positions.

A unit may be selected from the left pane without having a map marker.

This is intentional preparation for future live telemetry.
