PART 1 — PRODUCT CONTRACT AND NON-GOALS
===============================================================================

04. USER PURPOSE
   Permit an authenticated, authorized responder/leader/commander to capture, stage,
   upload, view and download incident evidence attached to exactly one authorized
   target, without leaking sensitive photos/documents across organizations, units,
   tasks, messages or past participants.

   Examples:
   - unit leader attaches a photo documenting a task obstruction;
   - firefighter attaches a field photo to a permitted own task;
   - officer attaches a PDF as incident-wide evidence if they have suitable authority;
   - a scoped operational note carries an image whose audience is NEVER broader than
     the note's effective current audience;
   - when offline, the user's prepared evidence remains durable, explicitly PENDING,
     and is retried with the same ID once the parent target is committed and access
     is revalidated.

05. NON-GOALS
   Do not add voice/video media, live streaming, recordings, OCR, facial recognition,
   geotagged live tracking, automatic image analysis, object recognition, AI summarization,
   automatic reports, public share links, guest downloads, unbounded full-bucket lists,
   automatic retention/deletion jobs, new chat semantics, read receipts or new command
   authority. Do not implement M14.8B/C/D, M14.9, or M14.10 within this PR.
   Photos are EVIDENCE, NOT command acknowledgements. Upload success never completes
   a task. Official radio remains essential for emergency operations.

06. TARGETS — ONE ATTACHMENT, ONE PARENT
   Support canonical target types:
   - INCIDENT: authorized incident-wide evidence; do not assume all incident readers
     are allowed to publish to this audience.
   - TASK: exact task UUID within same incident; visibility follows current task
     assignment/recipient and authorized command lineage, not mere incident membership.
   - MESSAGE: exact immutable M14.7C message UUID; visibility inherits its immutable
     audience (INCIDENT/ORGANIZATION/UNIT) AND current message visibility; do not let
     later correction/reassignment widen old attachment audience.
   Implement exact same-incident FK protection; never trust a client path or UUID alone.
   If source has another equivalent typed-target vocabulary, reuse/extend it without
   multiplying relationships. One and only one target reference must be non-null.

07. WHO MAY CREATE/VIEW
   Read/write rules must derive from CURRENT canonical incident authority, not org
   hierarchy or a cached role label. At minimum:
   - ACTIVE profile, exact current ACTIVE org membership, current ACTIVE org and
     appropriate ACTIVE incident participation for operational writes.
   - INCIDENT write: current effective IC/deputy or another existing explicit
     incident-wide evidence capability VERIFIED in source; a generic org ADMIN alone
     is insufficient.
   - TASK write: own active assigned task recipient or currently effective superior
     with existing domain ability to act on that task; define exact source predicates.
   - MESSAGE write: creator of current/authorized immutable note or explicitly
     authorized user whose audience exactly matches; initial safe default is original
     sender only. No historical correction grants fresh attachment write.
   - Reads require current ability to read BOTH incident AND exact target/audience.
     "I uploaded it" alone is NOT a permanent bypass to a revoked target.
   - Cross-organization participants see only content permitted by the target.
   - CLOSED/CANCELLED incidents: no new attachment writes; historical reads are
     denied unless existing proven target-specific historical policy is already
     established. Follow conservative C precedent; preserve metadata for reports.

08. FILE RESTRICTIONS
   Accepted normalized MIME:
   image/jpeg       <=10 * 1024 * 1024 bytes
   image/webp       <=10 * 1024 * 1024 bytes
   application/pdf  <=20 * 1024 * 1024 bytes
   Require nonempty data; no zero-byte files. Browser/Android prevalidate size and
   type for UX, but enforce on trusted backend before publishing READY.
   Reject GIF, PNG, SVG, HEIC, video, ZIP, Word, HTML, script, disguised binaries,
   double-extension tricks, malformed JPEG/WebP/PDF signatures and empty payloads.
   Never accept `Content-Type`/extension alone as sufficient validation. Check
   actual bytes/magic, length and preferably strict decoder/parser when existing
   safe libraries already exist. For PDF: basic signature checks do not prove it
   benign; render/download conservatively, no embedded JS execution.
   Check documented Storage global/bucket maximum settings as a human rollout item.
   Filename is display metadata only; strip path separators/control/bidi trickery,
   limit length, render escaped text, derive storage extension independently.

PART 2 — STORAGE SECURITY DESIGN
===============================================================================

09. PRIVATE BUCKET AND ISOLATED OBJECT PATHS
   Inspect whether the existing PRIVATE photo bucket can provide strict incident-
   scoped RLS without accidentally widening hydrant/inspection policies. Reuse only
   if exact authorization remains provably isolated. Otherwise add ONE dedicated
   private bucket in a forward migration or a manual bucket-creation instruction,
   e.g. logical id `incident-evidence` (confirm no collision).
   Never create/alter a public bucket.
   Suggested object key:
       {incident_uuid}/{attachment_uuid}/original.{jpg|webp|pdf}
   The bucket id and canonical path are derived on server, not supplied by clients.
   Avoid original filename, organization name, email, person ID, real-location name,
   secret, caption or audience label in the path.
   Object is immutable at a given attachment UUID; no upsert/overwrite.

10. STORAGE RLS
   Storage RLS is independent of ordinary incident-table RLS: implement explicitly.
   `storage.objects` is not itself a domain database.
   - Deny anon/public access.
   - INSERT only for a validated STAGED upload intent created by that exact authenticated
     actor, acting organization, incident and attachment UUID, within expiry and limits.
   - SELECT/download only after CURRENT exact incident AND target visibility; optionally
     use trusted per-request download handler for stronger revocation and short cache.
   - Do NOT allow arbitrary listing of a folder just because its first segment is
     an incident UUID.
   - No ordinary user UPDATE/upsert, COPY/MOVE, DELETE or broad admin bypass.
   - Object ownership alone grants no target read permission.
   - If Storage RLS needs policy operation differentiation, use supported official
     `storage.allow_only_operation` / `allow_any_operation` helpers after checking
     current Supabase docs; prevent an object-list permission from becoming read.
   - Do not edit storage system table rows by direct SQL for object lifecycle. Supabase
     recommends Storage API operations, not direct metadata mutation.
   - No service-role credential in mobile or browser; in a trusted function it must
     be tightly isolated, caller-validated, path-constrained and never used to bypass
     the canonical authorization decision.

11. SHORT-LIVED DOWNLOAD
   Preferred: authorized read RPC/handler authenticates requester, checks current
   org+incident+target+audi­ence, returns a narrowly scoped download capability,
   e.g. signed URL <=60 seconds OR an authenticated no-store stream when immediate
   revocation guarantees require stronger protection.
   Signed Storage URLs are bearer capabilities and may continue serving until expiry;
   cached responses can outlive an authorization change. Do not claim instant remote
   revocation of an already-issued URL. Never persist signed URLs in SQL, Room,
   plaintext logs, FCM, Realtime payload, crash reports or browser storage.
   Never place URLs in shared incident timeline or notification text.
   Set conservative cache-control and no-store on your own proxy responses; explain
   limitations of Supabase CDN/browser caches.
   Recheck authorization before every NEW capability issuance and each metadata page.

12. UPLOAD AUTHORIZATION AND EXPIRY
   Two separate concerns:
   (a) SERVER COMMITTED metadata upload INTENT for parent that already exists;
   (b) actual Storage bytes and their verification before READY registration.
   Client must never choose arbitrary bucket/path, claim a READY state or modify
   metadata via direct table DML. Use short-lived upload credentials if the existing
   architecture supports them, otherwise direct Storage RLS tied to the live intent.
   Consider that official Supabase `createSignedUploadUrl` tokens commonly last up to
   two hours; creating one does not guarantee immediate permission revocation. On
   completion, revalidate current authority before exposing the file. If authority
   disappears, keep evidence isolated/quarantined, never mark READY.
   Never use upsert and never overwrite a READY object's bytes.

14. CONCEPTUAL TABLE `public.incident_attachments`

       target_task_id UUID NULL
       target_message_id UUID NULL

       storage_bucket TEXT NOT NULL                 -- locked configured bucket
       storage_object_key TEXT NOT NULL UNIQUE      -- canonical derived immutable path
       original_filename_display TEXT NOT NULL
       normalized_mime TEXT NOT NULL

       schema_version INTEGER NOT NULL DEFAULT 1
   Additional immutable audience/provenance metadata as source demands. Avoid storing

15. PARENT FOREIGN KEYS AND VALIDATION
   Enforce same incident by composite FKs when existing targets have suitable unique
   keys; otherwise trusted SQL helper validates with row locks and appropriate
   indexes/constraints. Exactly one of target_task_id/target_message_id is present for
   targeted types, none for INCIDENT; `target_kind` must match. FK ON DELETE RESTRICT,
   no cascading disappearance of evidence. For MESSAGE inherit audience at creation
   from immutable canonical C message (not current Web client preview). For TASK
   never treat task id as a globally readable public id.
   Detect wrong incident, wrong unit/org, unknown task/message and uncommitted parent;
   return a safe uniform error without existence oracle across organizations.

16. PROVENANCE, VERSION, RETENTION
   Store uploader actor, acting org, canonical target, UTC server timestamps,
   object identity, actual validated MIME/bytes, immutable digest and operation id.
   Append status transitions to existing audit/evidence mechanism with only IDs and
   codes, not file bytes, private filenames or signed links. Reuse `private.write_audit`
   and incident receipt helpers if compatible; avoid duplicate audit subsystem.
   READY file bytes may not be silently replaced/re-signed as a new file.
   Corrections occur via a new immutable attachment row/version that references prior
   evidence if source contract supports this; no deleting original. Do not invent
   legal deletion/retention policy, legal hold service or background cleanup. Pending
   evidence is not orphan garbage.

17. OPERATION RECEIPTS / REPLAY
   Every mutation accepts a caller-generated stable operation UUID. Under the
   established advisory lock + incident/participant lock order:
   - exact replay of the same normalized request returns the original receipt/state;
   - same operation UUID with different incident/target/path/hash/MIME/size returns
     OPERATION_REUSED, no second file;
   - two concurrent attempts with same file UUID cannot yield separate READY rows;
   - a concurrent authority revocation is checked at commit;
   - ambiguous network success does not cause new attachment ID/path.
   Do not use an Android timestamp or filename as idempotency key.
   Approved auth reads cannot rely on a stale offline role snapshot.

18. AUTHORITATIVE RPC CONTRACTS (NAMES PROPOSED)
   Implement or adapt caller-bound SECURITY DEFINER RPCs:
   - incident_attachment_prepare(
       p_operation uuid,
       p_acting_organization_id uuid,
       p_incident_id uuid,
       p_attachment_id uuid,
       p_target_kind text,
       p_target_id uuid,
       p_metadata jsonb
     ) RETURNS JSONB
     Validates immutable intent, parent exists, upload authorization, file type,
     advertised size, bucket+path; creates STAGED row/receipt. Returns no service key.
   - incident_attachment_status(
       p_acting_organization_id uuid,
       p_incident_id uuid,
       p_attachment_id uuid
     ) RETURNS JSONB
     Returns authorized current state and recovery instructions, not arbitrary paths.
   - incident_attachment_finalize(
       p_operation uuid,
       p_acting_organization_id uuid,
       p_incident_id uuid,
       p_attachment_id uuid,
       p_verified_metadata jsonb
     ) RETURNS JSONB
     IMPORTANT: Caller-supplied verified_metadata alone must NOT be trusted as proof
     of actual bytes. Finalization must be gated by trusted Storage verification
     tied cryptographically/operationally to exact object path, observed length,
     signature and digest. Prefer separate private trusted finalize helper invoked
     only by authenticated, caller-authorized server handler after it verifies bytes.
   - incident_attachment_page(
       p_acting_organization_id uuid,
       p_incident_id uuid,
       p_target_kind text,
       p_target_id uuid,
       p_before_created_at timestamptz,
       p_before_id uuid,
       p_limit integer DEFAULT 30,
       p_expected_revision bigint DEFAULT NULL
     ) RETURNS JSONB
   - incident_attachment_access(
       p_acting_organization_id uuid,
       p_incident_id uuid,
       p_attachment_id uuid
     ) RETURNS JSONB
     Authorizes download and returns only bounded metadata/path to trusted handler.
   Adapt actual names to project conventions and Web route error mapper. Do not
   expose private helpers to ordinary clients.

19. SQL SECURITY PRACTICES
   SECURITY DEFINER search_path = '' and fully-qualified schema names; GRANT EXECUTE
   only to authenticated on intended RPC; REVOKE from anon/public; no direct DML or
   broad SELECT on private storage metadata; explicit RLS on public table.
   `auth.uid()` derives actor; no client-supplied "actor_user_id" authorization.
   Validate current exact membership AND incident participation AND target visibility.
   Bound every text/JSON input and page limit. No user-controlled table/function name,
   path interpolation, dynamic SQL or unsafe PL/pgSQL shadowed identifiers.
   Use safe error codes; no external ID enumeration. All numeric BIGINT counters cross
   Web/Android as decimal strings.

20. LISTING AND PAGINATION
   Strict keyset `(created_at DESC, id DESC)` maximum 50 rows/page (default 20/30).
   Authorize EVERY item, not merely incident membership. Return metadata only; no
   signed tokens, private bytes, arbitrary Storage URL or raw audit JSON.
   Distinguish STAGED/UPLOADING/VERIFYING/READY/REJECTED for creator without exposing
   partially uploaded bytes to other users. Only READY becomes target-visible evidence.
   Return normalized localized-friendly codes, safe displayed filename, MIME, size,
   creator display name only if already authorized and permitted.
   Never silently truncate and then mark a page complete.

21. B1/B2 INTEGRATION
   READY transition advances incident aggregate revision in established event/receipt
   transaction; preserve core version, task version and timeline sequence semantics.
   Private attachment metadata must NOT go into public/shared timeline, M10 payload or
   B2 Realtime hint. Reuse B1 coarse scope reset/collection invalidation where a new
   collection is not yet supported, and B2 metadata-only (incident/revision/cursor)
   hint; FCM optional generic type within existing M10 only if clearly required and
   recipient authority is rechecked. No new notification worker/broadcast channel.
   Revocation of message-specific attachment view must NOT wipe whole Android B1
   field cache. Apply the M14.7C fix pattern.

PART 4 — TRUSTED BYTE VALIDATION / STORAGE TWO-PHASE PROTOCOL
===============================================================================

22. TRUSTED SERVER VALIDATION IS MANDATORY
   SQL can validate row metadata, but cannot inspect Storage object bytes by itself.
   Implement an authorized trusted server step using EXISTING supported Web server
   handler or Supabase Edge Function runtime (choose based on actual source and SDK),
   which:
   - verifies current authenticated requester / exact acting org / target;
   - resolves object key FROM trusted metadata, never from client URL;
   - fetches Storage object with restrictive trusted privileges where required;
   - caps received bytes before unbounded allocation, enforces file size and type;
   - validates format magic (JPEG SOI, WebP RIFF/WEBP, PDF %PDF-) and actual MIME;
   - optionally uses existing safe content parser/decoder if installed, without adding
     dependencies or claiming full malware scanning;
   - computes SHA-256 on received bytes (trusted, not claimed by browser);
   - ensures actual key and stored object correspond to STAGED intent;
   - retries idempotently or marks a safe failure without publishing a corrupt file;
   - performs finalize under current SQL authority before READY visibility.
   If there is no secure supported verification path without new dependency or secret,
   do NOT mark bytes READY based on client data. Stop and report the concrete blocking
   integration instead of silently reducing this safety property.

23. PREPARE -> TRANSFER -> VERIFY -> READY STATE MACHINE
   Client-visible stages, carefully mapped to actual canonical codes:
   LOCAL_DRAFT (client only) -> LOCAL_QUEUED -> SERVER_STAGED -> TRANSFERRING ->
   SERVER_UPLOADED/VERIFYING -> READY.
   Failure branches: RETRYABLE, ATTENTION_REQUIRED, REJECTED, ACCESS_REVOKED.
   Invariant: READY requires trusted bytes AND current target authority at commit.
   Server never expects upload to be transactional with Postgres; use an idempotent
   two-phase/compensating design, no imaginary distributed transaction.

24. PREPARE
   Only after parent incident/task/message commit is known:
   - create stable attachment UUID and stable prepare operation UUID;
   - enforce permission and type/size limits in authenticated RPC;
   - reserve immutable canonical path; return a safe upload capability if supported;
   - do not create a duplicate parent on replay;
   - if offline parent message is still in LOCAL_PENDING, wait for its server receipt,
     keep attachment frozen in local queue and maintain parent dependency.

25. TRANSFER
   Transfer bytes using supported existing Supabase Storage client/API, not a
   custom unencrypted relay through insecure endpoints.
   - For Web: use SDK standard upload for smaller files; where TUS is already
     available, use resumable transfer for >6MiB or unreliable networks.
   - For 10/20MiB without existing TUS dependency, implement bounded streaming/
     replay-safe standard transfer plus explicit retry/resume semantics and explain
     reduced reliability; DO NOT add tus-js-client/other dependency unless authorized.
   - For Android: use existing `storage-kt` if available and suitable, otherwise
     supported authenticated HTTP transfer through existing stack; no Gradle changes.
   - Never upsert; conflict on existing path is not automatic failure if server
     status/digest confirms the same prior completed content.
   - Exponential backoff with bounded attempts via existing queue/worker.
   - No "upload succeeded" UI when bytes are merely staged.
   Do not issue a short-lived signed upload token while offline; obtain it online at
   dispatch and refresh when expired. It is NOT an offline credential.

26. VERIFY / FINALIZE
   Trusted validator obtains exact Storage object bytes, validates real content and
   observed metadata, then revalidates current parent/actor/target authorization.
   Idempotent finalization atomically records verified digest, length, MIME, READY,
   changed revision/audit/receipt and existing invalidation hint.
   A failing validation yields REJECTED/quarantined, never READY.
   If revocation occurs mid-upload, the object may physically exist but must never
   become visible or downloadable to former recipients. Do not call it orphan-safe to
   auto-delete pending evidence. Mark for human/admin remediation with limited access.
   If finalization response is lost, client calls status with same IDs and only retries
   original operation, never creates duplicate evidence.

27. ORPHAN / QUARANTINE AND CLEANUP
   Model:
   - STAGED but never transferred;
   - uploaded object but failed finalize;
   - validated bytes but lost ACK;
   - rejected content requiring retention policy decision;
   - account switched before upload;
   - parent scope revoked.
   Do not create a Cron/scheduler or automatic garbage collector in this milestone.
   Do not delete unowned-looking objects, especially with pending offline intents.
   Provide a safe, bounded audit/admin inventory proposal for later manual cleanup;
   do not expose object paths publicly or allow normal users to hard-delete evidence.

28. SECURITY LIMITS AND DENIAL OF SERVICE
   Server-side quotas based on true file size, active staged count per actor/org and
   bounded page size; choose explicit conservative limits only after checking realistic
   field needs, document them as implementation policy and not established facts.
   Prevent unlimited STAGED intents, repeated downloads, arbitrary signed URL
   generation, overlong filename/metadata and SQL lock starvation.
   Limit in-memory buffering; use streams if existing runtime supports them.
   Verification overhead must not block incident command transactions on network I/O.
   Do not call Storage while holding PostgreSQL locks.

34. DOWNLOAD CACHE, PRIVACY, LEASE
   Downloaded READY evidence belongs in private per-account/per-org/per-audience cache.
   Bound cache by bytes and age, and check current incident read lease (existing 24h
   maximum) before presenting; never give a Storage signed URL authority over local
   lease. Explicit confirmed message-scope revocation hides relevant attachments
   ONLY, not whole incident field projection. Global incident access revocation hides
   incident projection AND its evidence.
   Sign-out/org/account switch clears visible state, cancels in-flight downloads
   and stops stale response commits using generation tokens. Existing pending local
   owner evidence remains safely isolated for original account (not auto-uploaded
   under a different account).
   A cached attachment should not be assumed authorized indefinitely because the
   user previously downloaded it.
   If secure local encryption/expiry cannot be implemented using current facilities,
   use bounded online-only preview rather than insecure offline persistence and
   report the limitation.

   upload. On restart reconcile existing immutable IDs with server status first.
   Conflated FCM/B2 refresh may update page metadata but must not overwrite local
   pending evidence or leak revoked content.

     technical revocation cannot retrieve copies.

     and UI/cache hiding, not already-issued bearer URLs.
   - Magic-byte checks + hash do NOT constitute full malware scanning.
   - EXIF may exist inside JPEG/WebP; do not claim stripping unless actually done.
   - Secure local cache depends on actual Android encryption/no-backup behavior.
   - Manual owner QA/deploy required; no real incident operational readiness claim.

   `operation_id`, `storage_object_key` as appropriate after checking real schema.
   No CDN/public cache of private URLs beyond documented unavoidable behavior.
   Keep server SQL transactions short and no storage HTTP under locks.
