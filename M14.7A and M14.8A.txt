# GASILKO — M14.7A + M14.8A
# Real-Time Incident Commands & Android Operational Field Pilot

Repository: https://github.com/ficlus/Gasilko

Base: latest `main`, including merged M14.6D and subsequent hotfix/hardening commits available on main.

**Implement ONE integrated milestone in ONE pull request.**

Do not merge. Do not deploy.

## 0. Mission

Turn Gasilko's existing incident command and task system into a practical Android field workflow for authenticated firefighters and unit leaders.

The first deployment target is a **controlled pilot with real human accounts and manually created training incidents**.

A commander using the existing Web interface must be able to issue an authorized task to a real, logged-in Android user or their deployed unit.

The Android user must be able to:

1. Discover their incident.
2. Receive an incident/task notification when delivery is available.
3. Open the relevant incident and task.
4. Read the actual authoritative order.
5. Explicitly acknowledge the order.
6. Start performing the task.
7. Report that the task is blocked or cannot be performed.
8. Resume or complete the task where permitted.
9. See the server-confirmed status and history.
10. Recover safely after loss of network connectivity.

A legitimate UNIT_LEADER must additionally be able to:

- view their deployed unit and current crew;
- see unit-directed tasks;
- acknowledge and report on tasks directed to their own unit;
- see crew task status;
- issue new tasks to eligible subordinate crew members within the existing M14.5A command scope;
- observe acknowledgement and completion of those tasks.

The system must also support authorized REAL incident data contracts, but it must **not be declared ready for emergency operations solely because this PR is implemented**.

No real dispatch or emergency response should be triggered by pilot creation, testing or notification delivery.

# PART A — PRODUCT AND DOMAIN CONTRACT

## 2. Initial user roles

### Firefighter / RESPONDER

Can:

- view incidents they are currently authorized to read;
- view personally assigned tasks;
- view relevant unit task context;
- acknowledge their own assigned task;
- start an authorized task;
- report a blocked task;
- report inability to perform a task;
- complete their own assignment;
- view permitted history;
- read permitted target and map information.

Cannot:

- create unrelated incident commands;
- assign other units;
- acknowledge for another person;
- mark another person's task complete;
- gain command authority from organization membership alone.

### UNIT_LEADER

Can additionally:

- see the effective deployed unit assignment they lead;
- see the active crew episodes under that unit;
- receive and acknowledge tasks addressed to their unit;
- issue properly scoped tasks to eligible crew members in that unit;
- view responses from those recipients;
- perform existing authorized unit status/turnout actions where available.

Cannot:

- act as INCIDENT_COMMANDER without a separate effective assignment;
- command another unit based only on organization membership;
- change command hierarchy;
- allocate unrelated units;
- transfer incident command;
- impersonate a crew member's acknowledgement.

All capabilities must be derived from current server-authoritative role assignments and participation, not client-side role names.

### Other incident roles

The existing backend must retain full support for IC, agency commander, sector commander, operator and any other implemented roles.

However, the first Android UI scope is RESPONDER and UNIT_LEADER.

Existing Web commander workflows remain authoritative.

Do not weaken other roles or real-incident guards.

## 3. Training versus real operations

Pilot procedure:

- real authenticated accounts;
- existing approved organization memberships;
- manually created and clearly marked TRAINING incidents;
- real human acknowledgements;
- real server audit/history;
- no automatic SIM agent impersonation;
- no real-world dispatch;
- no emergency-service integration.

A training incident may use the existing SIM subsystem, but field task acknowledgements must be executed by actual authorized human accounts.

SIM movement, fabricated positions and simulated water effects remain in the TRAINING domain only.

REAL incidents must never receive simulated GPS, virtual water consumption or agent-generated acknowledgements.

No automatic 112/CAD integration.

Do not describe Gasilko as a replacement for ZA-RE radio.

## 5. Required assignment transitions

Use the authoritative M14.5A state machine:

```text
ISSUED
  |
  +--> ACKNOWLEDGED
  |       |
  |       +--> IN_PROGRESS
  |       |       |
  |       |       +--> COMPLETED
  |       |       |
  |       |       +--> BLOCKED
  |       |                 |
  |       |                 +--> IN_PROGRESS
  |       |                 +--> UNABLE
  |       |
  |       +--> UNABLE
  |
  +--> IN_PROGRESS
  |    Only when the immutable action definition
  |    explicitly permits starting without ACK
  |
  +--> UNABLE

Any nonterminal assignment:
  --> CANCELLED by its properly authorized issuer
```

Preserve actual current implementation guards.

Reasons must be supplied where required.

COMPLETED, UNABLE and CANCELLED are terminal.

Do not silently reopen them.

Do not mark a task successful merely because one recipient completed a multi-recipient task.

## 6. Command intent and execution

Strictly distinguish:

- task issued;
- notification sent;
- notification delivered;
- user opened task;
- user acknowledged;
- user started;
- user reported blocked;
- user completed;
- server confirmed.

Opening an FCM notification is not ACK.

Receiving a push is not ACK.

Selecting a task on the map is not START.

Reaching a location is not COMPLETED.

Completing a task must require an explicit authorized user operation.

- app-resume refresh;

Explicitly document that full private Realtime transport remains deferred.

## 12. Data reconciliation

Realtime or FCM is only a hint.

On every signal:

1. Check the current account and acting organization.
2. Schedule an authorized read.
3. Fetch the current server version.
4. Validate access.
5. Reconcile into Room.
6. Render the Room projection.

Duplicate or out-of-order hints must be harmless.

Do not treat a hint's revision as proof that the corresponding local data has been fetched.

Avoid excessive simultaneous refresh requests.

Debounce/coalesce signals without losing the need to reconcile to the latest revision.
