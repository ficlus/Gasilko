## 1. Main objective

Implement a proper **incident navigation execution layer** that connects issued M14.5A task assignments to navigable road routes.

Main operator workflow:

1. Commander selects an incident unit.
2. Commander issues an existing configured action whose native behavior is `MOVE_TO` or `WITHDRAW_TO`.
3. M14.5A creates the authoritative task and recipient assignment.
4. An authorized operator selects the assignment and chooses **Prepare navigation**.
5. The system resolves the issued immutable target snapshot.
6. The operator chooses an authorized route origin.
7. Backend routing calculates a route using the existing RoadProvider.
8. A versioned NavigationSession stores the route.
9. The route, distance and planned estimated duration appear in the incident workspace and map.
10. The session can be explicitly started, paused, resumed, stopped, cancelled or recalculated when authorized.

Navigation must be useful immediately in M14.5C training scenarios while remaining compatible with future real GPS observations and Android incident navigation.

**Do not implement automatic vehicle movement in M14.5D.**

## 2. Non-negotiable domain separation

The governing principle is:

**COMMAND INTENT != EXECUTION PLAN != TELEMETRY**

### Command intent

Example:

`GVC-1 → MOVE_TO → Hydrant H-000123`

This represents an issued instruction.

It does NOT imply:

- the recipient acknowledged it;
- the recipient started moving;
- a route exists;
- navigation was activated;
- the unit reached the destination;
- the task was completed.

### Execution plan

A NavigationSession represents one possible route/execution plan for a specific task assignment.

It may contain:

- authorized route origin;
- immutable command destination;
- RoadProvider geometry;
- planned road distance;
- planned duration;
- provider attribution;
- route revisions;
- navigation state.

A navigation plan is not a position observation.

### Telemetry

Physical position comes from a separate source:

- actual authenticated GPS observations, when implemented;
- explicitly simulated M14.5C positions in training incidents.

Never update a unit's observed position because:

- a task was issued;
- a route was calculated;
- navigation was started;
- time passed;
- an ETA elapsed.

Never infer unit safety, arrival, ACK or task completion from route geometry.

## 5. NavigationSession identity

A NavigationSession belongs to a **specific task assignment**, not merely to the parent task.

Relationship:

```text
Incident
  └── IncidentTask
        └── IncidentTaskAssignment
              └── NavigationSession
                    ├── RouteRevision 1
                    ├── RouteRevision 2
                    └── NavigationEvents
```

Example:

```text
One MOVE_TO task
Target: Hydrant H-000123

GVC-1 → assignment A → navigation session A
GVC-2 → assignment B → navigation session B
GVC-3 → assignment C → navigation session C
```

Each unit can have a different origin and therefore a different route and ETA.

Do not generate one shared route for all recipients.

Use the actual M14.5A assignment UUID as the canonical association.

For this MVP, road navigation supports:

`INCIDENT_UNIT`

Do not automatically create vehicle-navigation sessions for:

`INCIDENT_CREW_MEMBER`

Crew-member walking navigation is deferred unless the existing provider/domain can support it without new assumptions.

Permanent vehicle inventory records are not navigation recipients by themselves.

## 11. Navigation state machine

Use:

```text
PLANNED
ACTIVE
PAUSED
ARRIVED_REPORTED
STOPPED
CANCELLED
SUPERSEDED
```

### PLANNED

The route has been prepared and committed.

No indication that the unit moved or acknowledged the task.

### ACTIVE

An authorized executing actor explicitly started navigation.

The existence of ACTIVE navigation does not prove physical movement.

### PAUSED

Navigation guidance has been paused.

It does not prove the vehicle physically stopped.

### ARRIVED_REPORTED

An authorized actor explicitly reported arrival at the destination.

It does not complete the task automatically.

### STOPPED

Navigation guidance was explicitly stopped.

### CANCELLED

The navigation session was cancelled.

### SUPERSEDED

The navigation session was replaced by another valid navigation plan.

Preserve valid transition rules server-side.

Do not invent new M14.5A assignment statuses.

Do not couple navigation transitions to deployment lifecycle.

## 17. Prepare / provider / commit consistency

Routing calls can be slow.

Do not hold database locks while waiting for OSRM or GraphHopper.

Use a prepare/provider/commit workflow.

```text

task
assignment
recipient
action version/native behavior
issued target snapshot
origin source/version
navigation session version
actor scope
operation UUID
```

### Provider

Call the shared RoadProvider outside the database transaction.

### Commit

Recheck the current authoritative state.

The following may have changed:

- task cancelled;
- assignment completed;
- incident closed;
- incident command authority transferred;
- unit released;
- scenario paused/finished;
- simulation position changed;
- navigation session superseded;
- another route revision committed.

Do not persist geometry calculated from stale assumptions as the new current route.

- route-history pagination;

- bounded route vertices and JSON sizes;

- protect provider from excessive requests;
- no unbounded parallel route calculations;
- no busy polling;
- no per-frame database writes;
- no route calculation during ordinary map pan/zoom;
- no recreation of MapLibre during status changes;

Reuse existing provider timeouts and request validation.

For provider geometry, enforce reasonable safety limits while preserving normal realistic routes.

## 32. Security

All navigation mutations must be server-authoritative.

Authorization must distinguish:

- command authority;
- task execution authority;
- route-planning permission;
- protected simulation-controller permission.

Organization ADMIN/MANAGER does not imply incident command authority.

Sector geometry does not grant command scope.

A user who can read a hydrant is not automatically authorized to command a unit to it.

A unit's precise position must not be exposed solely because the user can read its permanent inventory record.

RLS and RPC checks must preserve incident/agency/sector scope.

Use current server-side account checks and revoke-sensitive authorization on every mutation.

Do not introduce browser-accessible privileged geometry commit operations.

Do not expose service-role keys, routing credentials or private simulation configuration.

Follow existing SECURITY DEFINER patterns, explicit qualification and safe search paths.
