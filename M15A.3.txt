11. ONE-TIME CLAIM AND VERIFICATION
============================================================

A naive sequence:

SELECT challenge
await crypto.verify()
UPDATE challenge

is not transactionally safe.

Supabase Edge invocation and PostgreSQL RPC
calls do not automatically share one transaction.

Design an explicit and safe boundary.

Recommended model:

TX-A: CLAIM

Database transaction:

1. Verify current actor.
2. Lock challenge row.
3. Lock credential/generation as needed.
4. Recheck current authority.
5. Compare immutable request identity.
6. Require challenge state ISSUED.
7. Require trusted current time < expires_at.
8. Confirm credential is INACTIVE, not REVOKED.
9. Allocate an unpredictable claim identifier.
10. Set short claim lease.
11. Transition ISSUED -> CLAIMED.
12. Commit.

OFF-DB:

Trusted verifier retrieves an authoritative
credential snapshot and challenge snapshot.

Never take these snapshots from untrusted client
replacement fields.

Call existing verifyDeviceProofV1.

No request may send a client-controlled
verified=true boolean to finalize.

TX-B: FINALIZE

Database transaction:

1. Identify original claim.
2. Verify caller is privileged trusted verifier,
   not the user/client claiming success.
3. Lock challenge and credential.
4. Recheck current authority.
5. Recheck role/deployment/vehicle versions.
6. Recheck revocation and generation.
7. Recheck expiry and original request hash.
8. Verify claim is current and not superseded.
9. Accept genuine verifier result only through
   the protected verifier trust boundary.
10. Set VERIFIED_INACTIVE at most once.
11. Store immutable authoritative receipt.
12. Commit.

A successful result may only mean:

PROOF_VALIDATED_INACTIVE

NOT:

BOUND_ACTIVE
CONSENT_APPROVED
GPS_READY
LOCATION_SHARING
TRACKING_ACTIVE

If there is no safe means for the database to
distinguish the real verifier from an HTTP client,
DO NOT expose FINALIZE.

This is a HARD blocker, not an optional warning.

============================================================
13. CONCURRENCY AND IDEMPOTENCY
============================================================

Handle these cases explicitly.

CASE A:
Two clients attempt to consume the same challenge.

Result:
At most one authoritative successful finalization.

CASE B:
The same original issue UUID is retried.

Result:
Return the existing authoritative response,
provided the normalized request is identical.

CASE C:
The same operation UUID has different payload.

Result:
OPERATION_CONFLICT.

CASE D:
Verifier crashes after CLAIM.

Result:
No false success.
Challenge remains claimed or becomes
recoverable according to bounded lease policy.

CASE E:
Verifier crashes after FINALIZE commit but before
HTTP response reaches the client.

Result:
Retry discovers the authoritative receipt.
No duplicate state transition.

CASE F:
Credential revoked between CLAIM and FINALIZE.

Result:
Revocation wins.
Finalize rejects the claim.

CASE G:
Incident deployment or vehicle reassigned
between ISSUE and FINALIZE.

Result:
Live scope/version check rejects confirmation.

CASE H:
Driver role removed between ISSUE and FINALIZE.

Result:
Confirmation denied.

CASE I:
Device key rotated.

Result:
Older generation cannot finalize.

CASE J:
Expired challenge is retried.

Result:
EXPIRED or the same already-confirmed
authoritative receipt, never a fresh consent.

CASE K:
Two different devices claim the same vehicle.

Result:
No operational binding occurs in M15A.3.
Future one-device-per-vehicle arbitration
remains blocked pending policy.

CASE L:
Old Android instance retries a saved request
after organization/account switch.

Result:
Do not retarget the original operation.
Reject the stale identity context.

CASE M:
A signature is mathematically valid but
current actor is unauthorized.

Result:
Reject authorization, regardless of signature.

CASE N:
A forged proof result is supplied by a client.

Result:
Never accepted by trusted FINALIZE.
