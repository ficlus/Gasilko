## 1. Objective

Create a practical, isolated **incident training and simulation environment** that lets an authorized operator:

1. Set up a training incident.
2. Add or select virtual incident units.
3. Define their initial geographic positions.
4. Display those positions on the existing incident operational map.
5. Select simulated units using M14.5B RTS interaction, including box/lasso.
6. Manually change simulated positions and selected simulation conditions.
7. Use the existing M14.5A command interface against correctly provisioned training-unit recipients.
8. Observe issued commands separately from simulated positions.
9. Pause, resume, reset and terminate a simulation.
10. Prepare the architecture for future autonomous movement and task-response simulation.

The simulator is not a replacement for incident operations.

It is a **training/test data source** integrated into the existing operational UI.

The first milestone must be useful without GPS hardware, Android clients or external routing services.

---

## 2. Mandatory architectural principle

**COMMAND INTENT != EXECUTION PLAN != TELEMETRY**

Three different concepts must remain separate.

### Command intent

The commander issues a real M14.5A task, for example:

`MOVE_TO → coordinate X`

This is an instruction.

Issuing the instruction must not change the unit's location.

### Execution plan

A future NavigationSession will determine route geometry, ETA, reroutes and navigation progress.

This is reserved for M14.5D.

### Position/telemetry

A unit's position is an independent observation.

In training mode it may be generated or manually updated by the simulator.

In real operations it must come from an authorized real location/telemetry source.

Never write simulated positions into a real location stream without explicit simulation provenance and isolation.

Never reinterpret a sector assignment, hydrant position, task target, station coordinate or vehicle inventory record as actual unit position.

## 4. Critical isolation requirement

**Simulation must never be confused with a real intervention.**

The preferred deployment model is a separate Supabase **staging/training project**, separate from production.

Implement the simulator as **disabled by default**.

Require a server-authoritative simulation enablement guard.

Suggested requirements:

- A protected backend setting explicitly enables simulation.
- Normal organization ADMIN/MANAGER cannot activate simulation globally.
- UI configuration alone is not sufficient.
- Production must remain disabled unless a trusted operator explicitly changes its protected environment configuration.
- Simulation write RPCs recheck the backend guard.
- Browser-provided `simulation=true` is not an authorization mechanism.
- Simulation is only available for incidents explicitly enrolled as training incidents.
- An existing live incident cannot be silently converted into a simulation.
- A simulation cannot silently become a live incident.

Document staging configuration without installing, configuring or deploying it.

Do not use the existing production Supabase project as a default training database.

Do not expose service-role credentials or backend configuration secrets.

## 5. Training incident model

Prefer to reuse the existing incident domain for training operations rather than creating a second incompatible incident engine.

Introduce a clearly isolated **SimulationScenario** linked to one existing incident.

Conceptually:

```ts
type SimulationScenario = {
  id: string;
  incidentId: string;
  title: string;
  kind: string;
  seed: number;
  status: 'DRAFT' | 'RUNNING' | 'PAUSED' | 'FINISHED';
  version: string;
};
```

This interface is conceptual.

Reuse repository naming conventions.

Requirements:

- One simulation scenario belongs to exactly one incident.
- An ordinary live incident has no simulation scenario.
- One incident must not be associated with multiple active simulation scenarios.
- Simulator actions require both the scenario association and server-side simulation enablement.
- Scenario identity remains stable.
- Scenario changes are auditable.
- Reset must not delete or rewrite historical M14 incident task records.
- No implicit transfer of simulation objects into production.

Use the existing incident create/participant/commander-consent lifecycle whenever possible.

Do not bypass M14.1/M14.2 business constraints to create a convenient demo incident.

If automated training-incident setup is impossible without violating those constraints, provide a clear guided setup using the existing authorized workflows.

## 7. Deterministic scenario generation

```text

```

Output:

```text

deterministic unit ordering
deterministic labels
```

The same seed and template should reproduce the same starting layout, subject to the same underlying fixture inputs.

Suggested initial placement:

- within a bounded configurable radius from the incident center;
- avoid invalid coordinates;
- do not place points outside WGS84 bounds;
- use `[longitude, latitude]` consistently;
- do not silently generate physical GPS observations;
- do not claim that generated locations are road-snapped.

These are **test starting coordinates**, not actual positions and not routes.

Do not call routing or geocoding services during fixture generation.

## 10. Simulation position model

Introduce an independent, authoritative-for-training **simulation position model**.

Do not add fake GPS coordinates directly to:

- `operational_units`;
- `operational_vehicles`;
- `incident_units`;
- `incident_tasks`;
- `incident_task_assignments`.

Suggested persisted projection:

```text
simulation_unit_positions

scenario_id
incident_unit_id
longitude
latitude
heading_degrees
speed_mps
observed_at
updated_by
version
```

Include the necessary foreign keys, incident consistency checks, indexes and RLS.

Position source must always be unambiguous:

```text
SIMULATED
```

Never present this as ordinary live GPS.

Suggested optional attributes:

```text
accuracy_m
position_state
```

Do not invent a real sensor accuracy. A simulated accuracy, if represented, must explicitly be a scenario parameter.

Use server timestamps for authoritative mutation ordering.

Validate:

- longitude -180 to 180;
- latitude -90 to 90;
- finite numeric coordinates;
- heading 0 to less than 360;
- nonnegative finite speed;
- reasonable maximum accepted values;
- same-scenario/same-incident association.

Prefer a single current-position projection per simulated incident unit.

Do not store a full GPS trail in `incident_units`.

```text

```

Use actual project RPC naming and conventions.

All writes must:

1. Authenticate the actor using `auth.uid()`.
2. Check the actor's active account.
3. Check backend simulation enablement.
4. Verify the incident is an authorized training scenario.
5. Check incident participation and appropriate operational command authority.
6. Check the referenced incident unit belongs to the same scenario incident.
7. Reject terminal or invalid deployment relationships where applicable.
8. Use optimistic concurrency.
9. Use durable idempotency where appropriate.
10. Write simulation history/audit.
11. Return bounded safe DTOs.

No broad `authenticated` INSERT/UPDATE/DELETE grants on simulation tables.

Prefer RPC-controlled writes and RLS-protected reads.

Use existing SECURITY DEFINER conventions, explicit object qualifications and safe `search_path`.

Do not grant write authority based on map geometry or permanent organization ADMIN status alone.

## 13. Actor permissions

Differentiate:

### Simulation controller

An authorized human operator who can create/control a training scenario.

The role must be explicitly scoped to the training incident and protected environment.

Do not introduce an unrestricted global ADMIN role.

### Training commander

An actual authenticated user holding a valid M14 incident command assignment in the training incident.

May issue task commands according to existing M14.5A rules.

### Training viewer

Can view only scenarios/positions permitted by the existing incident authorization model and simulation read policies.

Cannot move virtual units merely because they can read the map.

Simulation controller privileges do not automatically imply authority to issue real M14.5A commands.

A simulation control action must not silently grant Incident Commander or Unit Leader.

- 3–30 simulated incident units in ordinary scenarios;
- up to 100 in a controlled larger scenario;
- existing M14.5A 100-recipient task limit remains unchanged.

Requirements:

- one bounded position projection read for the scenario;
- no N+1 requests per marker;
- no MapLibre recreation on position update;
- stable marker/source identity;
- incremental GeoJSON source updates;
- bounded event-history pagination;
- avoid high-frequency DB polling;
- no permanent timer-based simulated movement loop in C;
- no full national inventory download;
- no unnecessary reloading of hydrant or tactical layers.

If a refresh strategy is needed, use an explicit refresh/manual fallback or existing infrastructure rather than introducing a new realtime subsystem.

Realtime streaming remains a future capability.
