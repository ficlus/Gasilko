## 1. Product goal

Transform the existing **Poveljniška karta** into a live operational command workspace.

Currently, command, COP, resources, navigation, and simulation components have separate refresh mechanisms. Some changes require clicking **Osveži** or waiting for an independent provider refresh.

The goal is:

**An authorized commander should see operational changes automatically, promptly, and consistently, without refreshing the browser or manually refreshing each panel.**

Examples:

- Another commander creates a tactical command post. It appears on the map.
- An authorized unit assignment changes status. The related task card updates.
- A command is accepted by the server. The UI clearly distinguishes accepted, acknowledged, in progress, blocked, and completed.
- A simulated unit moves along its existing valid navigation route. Its SIM marker updates without resetting the map.
- A simulated unit arrives or encounters an injected failure. A relevant notification appears.
- Another commander changes or deactivates a tactical object. The map updates.
- A session loses authorization. Privileged operational data and controls are revoked appropriately.

This is an operational synchronization and presentation milestone.

**Do not change the semantics of command execution, real-world telemetry, simulation, navigation, or incident authority.**

## 4. Architectural principle

**Server-authoritative state with event-driven refresh and bounded fallback.**

The architecture must distinguish:

1. **Change signal** — something may have changed.
2. **Authorized read** — determine the current server-confirmed state.
3. **UI state update** — refresh only the affected operational domain.
4. **Notification** — present an important confirmed transition.

A Realtime event is NOT itself an authorized operational snapshot.

The client must never trust an arbitrary socket payload as proof of task acknowledgment, successful command execution, vehicle arrival, or permission to access an incident.

Use existing server-side RPCs to obtain authoritative state.

Required invariant:

**COMMAND INTENT != EXECUTION PLAN != OBSERVED TELEMETRY.**

Introduce one lightweight incident-scoped live-update coordinator.

Suggested conceptual structure:

```text
IncidentWorkspace
└── IncidentLiveProvider
    ├── Scope & connection lifecycle
    ├── Change-signal subscription
    ├── Adaptive fallback refresh
    ├── Revision / sequence tracking
    ├── Domain invalidation dispatcher
    └── Notification derivation
         ├── COP
         ├── Tasks
         ├── Resources
         ├── Navigation
         └── SIM / Autonomous agents
```

Adapt to the existing provider nesting.

Do not create a second source of truth for domain data.

The coordinator should provide stable, lightweight refresh/invalidation signals to existing readers rather than owning duplicate copies of every COP object, task, resource, and navigation record.

Suggested domain invalidation categories:

```typescript
type IncidentLiveDomain =

  | 'COP'
  | 'TASKS'
  | 'RESOURCES'
  | 'NAVIGATION'
  | 'SIMULATION'
  | 'AGENTS'
  | 'TIMELINE';
```

These are examples, not mandatory backend identifiers.

### Required behavior

- Scoped by authenticated account, acting organization, and incident UUID.
- Stable cleanup on navigation or unmount.
- No duplicated subscriptions when switching Classic/Command modes.
- No duplicate timers when opening/closing panels.
- No event listeners that survive their owning provider.
- Abort or discard stale requests when their scope becomes invalid.
- Coalesce multiple rapid invalidations.
- Preserve the existing loading and mutation feedback mechanisms.

## 6. Realtime transport decision

Inspect existing Supabase capabilities before choosing a transport.

### Preferred approach

Use **authenticated, incident-scoped, private Supabase Realtime invalidation events**, provided that the repository can establish correct authorization and delivery.

Supabase's current documentation recommends Broadcast for scalable realtime changes.

Important requirements:

- Private channels only.
- Channel authorization must validate actual incident read access, not just authentication or a guessed incident ID.
- Respect acting-organization scope.
- Do not assume all incident participants can access every organization-specific record.
- Never expose secrets, sensitive command payloads, profiles, complete audit snapshots, or privileged metadata in broadcast messages.
- Emit only minimal change hints, such as an opaque incident-scoped revision or permitted domain identifier.
- Revalidate permissions using existing authoritative reads.
- Cleanly unsubscribe and remove channels when the scope changes.
- Handle token refresh, reconnect, timeout, and channel errors.
- Do not accept user-generated broadcasts as authoritative evidence of server changes.
- Do not make a broad RLS policy such as `USING (true)` merely to get Realtime working.
- Do not expose private simulation configuration or runner secrets.

Before implementing private Broadcast, inspect existing database functions and exact authorization APIs.

If an appropriate secure notification path does not exist, create the smallest possible forward-only migration to implement it, documenting the topic naming, RLS authorization, trigger source, events and rollback procedure.

### Important database safety

Do not add sensitive tables indiscriminately to `supabase_realtime`.

Do not enable broad replication of:

- audit logs;
- private simulator configuration;
- entire task command payloads;
- profiles;
- permission/role details;
- sensitive incident records.

Do not expose raw database row changes merely for UI convenience.

If the necessary secure authorization cannot be proven for this PR, use a **bounded, coordinated server-RPC polling strategy as the reliable implementation**, and explicitly document Realtime as deferred.

The implementation must remain useful when Realtime is disabled.

Do not deliver a UI that simply says it is live while no updates are arriving.

## 7. Fallback refresh strategy

A fallback mechanism is mandatory even if Realtime is implemented.

Requirements:

- Perform an authoritative initial read.
- Refresh after an event signal.
- Refresh after reconnect.
- Refresh when a hidden tab becomes visible again.
- Refresh after the browser comes back online.
- Periodically reconcile even if no events arrive.
- Avoid concurrent duplicate requests for the same domain.
- Avoid exponential request accumulation on errors.
- Abort or ignore obsolete requests.
- Back off on repeated failures.
- Do not trigger full-page router refreshes for ordinary state changes.

Suggested baseline:

| Situation | Suggested strategy |
|---|---|
| Successful Realtime connection | Event-driven refresh plus low-frequency reconciliation |
| Realtime unavailable | Bounded fallback polling |
| Visible active incident | Approximately 5–10 seconds for important changing domains |
| Active SIM movement | Reuse the existing 5-second autonomous-agent polling |
| Hidden browser tab | Pause unnecessary high-frequency reads |
| Tab becomes visible | Immediately reconcile |
| Network offline | Stop futile retries and show disconnected status |
| Network returns | Immediate authorized reconciliation |

These timings are suggestions. Tune them after inspecting current RPC cost and existing timers.

Do not globally poll every incident.

Do not poll historical pages, large action catalogs, all hydrants, or the entire organization repeatedly.

### Critical existing behavior

`AutonomousSimulationProvider.tsx` already runs a 5-second read loop.

Do not leave this loop running alongside a second independent 5-second read of the same endpoint.

Either reuse the existing loop or consolidate it into the coordinator while preserving its current functionality.

Avoid repeatedly invoking `SimulationProvider.refresh()` in a way that creates cascading reload loops.

## 13. Prevent notification storms and duplicates

This requirement is especially important during autonomous simulation.

The simulator may update many positions repeatedly.

Do not generate a notification for every marker position update.

Generate notifications for **meaningful state transitions**, such as:

- start of movement;
- arrival;
- blocked/failed execution;
- acknowledgment;
- completion;
- SIM incident event.

Use stable identifiers and sequences.

Suggested notification identity:

```typescript
type NotificationIdentity = {
  incidentId: string;
  eventId?: string;
  domain: string;
  entityId: string;
  transition: string;
  version?: string;
};
```

Use actual event IDs where available.

Requirements:

- Do not replay historic events as new alerts on initial mount.
- Do not duplicate events after reconnect.
- Do not duplicate alerts when both Realtime and polling report the same transition.
- Deduplicate across Classic/Command switching.
- Bound in-memory notifications.
- Avoid persistent sensitive notification caches.
- Respect incident and organization boundaries.
- Handle browser reloads without showing a large flood of old events.

When a domain lacks reliable history or versions, do not fabricate event identity. Use a safe conservative strategy or omit that alert category until a trustworthy transition can be established.
