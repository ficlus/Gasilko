## 2. Product goal

Make SIM incident commands behave like a practical RTS command system.

When a commander issues a configured task from the **Poveljniška karta**, the system should automatically execute the appropriate simulation preparation and execution steps.

Example:

1. Select SIM unit GVC-1.
2. Right-click an appropriate target on the map.
3. Choose a configured action.
4. Review and confirm the task.
5. The backend accepts the task.
6. If automatic SIM execution is enabled, the backend enrolls the eligible assignment.
7. If the action requires road navigation, calculate an actual route using the existing OSRM/GraphHopper infrastructure.
8. Create or reuse the authorized navigation session.
9. Start the corresponding virtual simulation agent.
10. The existing background runner advances the simulated unit.
11. The map and notification system display server-confirmed progress.

**No manual route calculation or separate agent START step should be required for eligible automatic SIM commands.**

Support more than `MOVE_TO`.

The system must respect the configured action's actual native behavior rather than blindly routing every task.

## 4. Action execution policy

Provide one centralized, explicit SIM execution policy for each supported native behavior.

Expected behaviors to inspect:

| Native behavior | Automatic SIM treatment |
|---|---|
| `MOVE_TO` | Route planning followed by simulated movement |
| `WITHDRAW_TO` | Route planning to the withdrawal destination followed by simulated movement |
| `HOLD_POSITION` | Supported virtual non-moving execution |
| `REQUEST_STATUS` | Supported virtual non-moving response workflow |
| `NONE` | No implicit automatic execution |

Do not infer eligibility merely from the presence of coordinates.

The backend must check the actual configured action behavior, target type, recipient type and training policy.

### Moving behavior

For `MOVE_TO` and `WITHDRAW_TO`:

- Resolve the real configured destination.
- Require a supported point destination.
- Calculate an appropriate road route.
- Create a navigation session belonging to the correct assignment and unit.
- Start a virtual agent against the valid current route.
- Let the existing simulator advance movement.

### Non-moving behavior

For `HOLD_POSITION` and `REQUEST_STATUS`:

- Do not calculate a road route.
- Do not change the simulated geographic position.
- Use only supported virtual response/ACK/completion semantics.
- Never fabricate a human response or acknowledgment.
- Do not silently interrupt an unrelated active run.

### Unsupported behavior

For unknown actions or `NONE`:

- Leave the assignment available for manual handling.
- Show a clear unsupported/manual status.
- Do not execute an arbitrary guessed behavior.

Future action types must be addable through a centralized execution-policy mapping.

Do not scatter unrelated string comparisons across components.

## 5. Scenario-level automatic execution setting

Add a server-persisted setting:

**Samodejno izvajaj SIM ukaze**

Support:

- OFF — existing manual simulation workflow.
- ON — automatically process eligible newly accepted SIM assignments.

### Requirements

- Default OFF.
- Stored durably per simulation scenario.
- Server-authoritative.
- Controlled by an authorized training controller.
- Only available for actual SIM incidents.
- Explicit user confirmation when enabling.
- Visible effective state in the Command Map.
- SI/DE localization.
- Audit setting changes.
- No localStorage-only implementation.

### Enrollment boundary

Enabling automatic execution must **not** automatically execute historical unresolved tasks.

Only new assignments accepted after automation was enabled may be automatically enrolled.

Capture this decision durably at authoritative task acceptance.

If recovery of an older assignment is needed, it must require a separate explicit authorized action.

### Disabling

Turning the switch OFF:

- Stops future automatic enrollment.
- Must not silently stop or cancel already running agent executions.
- Does not change real incident behavior.
- Does not erase past job history.

Use an existing explicit STOP operation for active runs.

## 6. Durable orchestration state

Implement a small, durable, simulation-only automation workflow.

Suggested logical states:

```text
TASK_ACCEPTED
      |
      v
ELIGIBILITY_CHECK
      |
      +---- UNSUPPORTED / BLOCKED
      |
      +---- NEEDS_NAVIGATION
      |             |
      |             v
      |       ROUTE_PENDING
      |             |
      |             v
      |       ROUTE_READY
      |             |
      +-------------+
                    |
                    v
              START_PENDING
                    |
                    v
              AGENT_STARTED
                    |
                    v
           EXISTING SIM RUNNER
                    |
                    v
        ACK / MOVE / ARRIVE / COMPLETE
```

Use actual persisted statuses appropriate to the existing database.

### Durable job requirements

Each eligible assignment must have:

- Stable job UUID.
- Scenario UUID.
- Incident UUID.
- Task UUID.
- Assignment UUID.
- SIM incident-unit UUID.
- Native behavior and relevant action version.
- Current orchestration state.
- Retry counter.
- Next eligible processing time.
- Navigation session reference, when applicable.
- Agent run reference, when applicable.
- Error code and safe error details.
- Creation/update timestamps.
- Immutable logical operation identity for retries.

Prefer extending an existing suitable persistence structure if one already exists.

Only create a new queue table if necessary.

### Concurrency

- Claim work atomically.
- Support bounded worker leases.
- Prevent duplicate processing of the same assignment.
- Use row locking or another suitable concurrency mechanism.
- Support overlapping Cron invocations safely.
- Recover from interrupted workers.
- Use idempotent navigation/session/run creation.
- Never create two active agent runs for one logical assignment.
- Prevent older results from overwriting newer authoritative state.

Do not implement this queue in React state or browser memory.

## 8. Secure navigation planning

For actions requiring a route:

1. Validate the existing automation job.
2. Revalidate the scenario and assignment.
3. Confirm the task remains active and eligible.
4. Confirm the recipient is an actual SIM unit.
5. Resolve the supported destination.
6. Read the latest valid SIM position.
7. Create or reuse the correct navigation session.
8. Call the existing shared OSRM/GraphHopper routing provider.
9. Validate returned road geometry and route metadata.
10. Commit the route through existing navigation rules.
11. Revalidate position/session versions.
12. Start an agent only after a valid current route exists.

### Supported destinations

Use existing target resolution contracts for:

- Geographic coordinates.
- Permanent hydrants when supported.
- Incident tactical point objects.
- Other point entities supported by the navigation system.

Do not assume polygon and line objects represent road destinations.

Do not silently use the center of a sector polygon.

Do not create fake coordinates.

### Critical security requirement

The current user-facing navigation workflow uses authenticated human authority.

**Do not impersonate a human commander using a service-role token.**

Introduce a narrowly constrained simulation-only planning path if required.

This path may operate only on:

- An existing authorized SIM task assignment.
- An eligible persisted automation job.
- A protected training scenario.
- A supported navigation action.
- A valid current SIM position.

It must not be capable of preparing arbitrary navigation sessions for real incidents.

Reuse the existing navigation validation and route-commit infrastructure.

Do not create a second independent routing engine.
