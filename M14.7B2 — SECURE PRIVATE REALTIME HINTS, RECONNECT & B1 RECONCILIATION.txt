5. CHANNEL TOPIC AND MESSAGE CONTRACT
-------------------------------------
Preferred logical topic: `incident:<incident-uuid>:org:<acting-organization-uuid>`.
If a more restrictive canonical topic already exists, reuse it and document why.
This is an AUTHORIZATION-SCOPED topic, not a room name chosen from a display label.
Use an exact anchored parser; validate UUIDs/format before casting. Treat malformed/too-long topics as denied.
Never interpret a partial parse, wildcard, null `auth.uid()` or user-supplied organization assertion as authorization.
Do not include actor user ID, unit IDs, task IDs, title, body text, notes, map points, GPS, attachments or raw old/new JSON in the topic/payload.

Event name (suggested): `incident_changed`.
Canonical minimal payload:
  {
    "incident_id": "<uuid>",
    "revision": "<decimal BIGINT string>",
    "timeline_sequence": "<decimal BIGINT string>"
  }
Optionally a non-sensitive protocol version field if needed for backward compatibility.
Do not include role/scopes, raw operation UUID, broadcast timestamps that claim stronger order, or secret scope fingerprints.
Keep payload bounded (for example <=512 bytes) and verify this contract in producer/client code. Use decimal STRINGS for BIGINT across Kotlin/TypeScript/JSON.
Only broadcast when a canonical transaction commits; a rolled-back mutation must not result in a durable broadcast.
Prefer a single canonical server-side producer at the established incident revision/timeline commit boundary. No client-emitted authoritative notifications.
Document that Supabase Broadcast is NOT durable; event loss is expected and safe because B1/foreground polling catches up.

11. BROADCAST RECONNECT, RACES AND RESILIENCE
--------------------------------------------
Use one bounded lifecycle controller per active incident scope; no unbounded subscription pool.
Recommended state machine:
  DISABLED / UNSUPPORTED
  -> CONNECTING -> SUBSCRIBED_UNVERIFIED -> CATCHING_UP -> LIVE
  -> STALE / OFFLINE / RETRY_WAIT -> CONNECTING
  -> ACCESS_LOST -> TERMINATED.
`SUBSCRIBED_UNVERIFIED` is NOT "live". `LIVE` is contingent on a successful authorized read.
Backoff with jitter and cap, e.g. first 1s, 2s, 4s, 8s, max 30s; reset only after stable success. Do not run timers after cleanup. Keep existing bounded safety poll cadence, tune it conservatively to avoid increased load.
Race examples to handle:
  - Event commits between initial read and subscribe.
  - Subscription callback fires after account/org switch.
  - Reconnection occurs after 30-day cursor gap: B1 RESET_REQUIRED must fetch a fresh manifest.
  - Newer revision arrives during older B1 read; schedule a second pass.
  - Server sends two events for same revision/sequence; one reconcile.
  - Timeline sequence advances without aggregate revision, and vice versa.
  - One org loses access while old WebSocket is temporarily still authenticated: metadata-only cached subscription; ALL detail reads deny and client removes scope.
  - JWT rotates while connected; auth propagation re-evaluates read permissions at supported refresh.
  - Device sleeps/backgrounds; no assumed persistent socket.
  - Supabase broadcast partition unavailable; absence of hints does NOT imply absence of changes.
  - Many SIM ticks occur; no unbounded per-tick refresh on all devices.
No infinite retry on permanent auth failure. No event-loop reentry or timer accumulation. When reconnected always catch up from authoritative B1 server state, not from last socket message.
