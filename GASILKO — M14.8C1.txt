A. Enter an incident-scoped Android Map from IncidentScreen, a specific task assignment, or the existing own-unit screen.

3.1 Canonical objects and identifiers

Never duplicate canonical incident/hydrant/task/object rows just to draw them. Prefer a typed read projection/adapters with fields conceptually equivalent to:

  IncidentMapContext(
    incidentId UUID,
    actingOrganizationId UUID,
    actorId from authenticated session (NEVER client authority),
    mode REAL|TRAINING as derived from existing source,
    aggregateRevision decimal string,
    sourceFingerprint opaque string,
    verifiedAt UTC,
    leaseExpiresAt UTC,
    layers ...
  )

  MapFeature(
    kind = TASK_TARGET|INCIDENT_SECTOR|INCIDENT_MAP_OBJECT|
           INCIDENT_LINKED_HYDRANT|REGISTRY_HYDRANT|AUTHORIZED_UNIT,
    canonicalId UUID or stable assignment/target identity,
    incidentId UUID when incident-scoped,
    assignmentId UUID when task-scoped,
    geometry with explicit WGS84 longitude/latitude,
    canonicalLabel or safe display text,
    sourceVersion decimal string where applicable,
    issuedTargetSnapshot boolean,
    visibilityScope from server projection, not a client-supplied grant,
    originProvenance ACTUAL_AUTHORIZED|MANUAL_PLANNING|REFERENCE_ONLY|NONE,
    observedAt UTC when genuine observation exists,
    verifiedAt UTC,
    state/current/stale/unknown fields
  )

These are conceptual field expectations. Adapt actual existing return JSON rather than imposing incompatible new shapes.

3.2 Exact typed task targets (known canonical issue-task shape)

  {kind:"NONE"}
  {kind:"COORDINATE", coordinate:[longitude,latitude]}
  {kind:"HYDRANT", entityId: UUID}
  {kind:"INCIDENT_MAP_OBJECT"|"INCIDENT_SECTOR",
   entityId: UUID, incidentId: UUID}

The issued immutable target snapshot has priority for the task-specific pin/route destination. A later edit to a live hydrant, sector or object must not silently redirect an already-issued task.

If target geometry is not a point (sector polygon, line or area), show geometry and a safe "no canonical point destination" state unless the issued task contains an authoritative point or existing NAV2 contract explicitly defines one. DO NOT invent centroids, nearest edge snap, random points or fallback "arrival" positions. Distinguish live contextual geometry from frozen task target.

3.3 Latitude/longitude

- Explicit names longitude and latitude. WGS84 and correct coordinate order [lon,lat] for GeoJSON and RPCs.
- Validate finite numbers; longitude [-180,180], latitude [-90,90]; reject NaN, swapped/out-of-range values and nonsensical geometry.
- No silently corrected coordinates. Report localized invalid geometry/target state.
- Bound geometries/vertices according to actual server constraints. Respect M14.5D limits if dealing with navigation geometry.

3.4 Hydrants

- Incident-linked hydrants are incident context references, not copies. Preserve original registry UUID and provenance.
- Background registry hydrants remain from the user's existing authorized Room registry/map, with separate legend/style and existing access/lease rules.
- A hydrant linked to multiple incidents remains one canonical hydrant; the per-incident link is a separate relationship.
- Never display an incident link because the hydrant exists in an unrelated org; verify current field incident visibility + registry permissions independently where required.
- Do not claim registry hydrant pressure, availability or flow if those facts are not currently verified. Display appropriate stale/unknown states.

3.5 Units and positions

- Only show units the authenticated actor is currently allowed to see through the field projection, not all incident deployments.
- If no genuine authorized REAL position source exists, show unit as a list/card with "position unavailable", NOT at incident center or imaginary station point.
- NEVER show SIM_AGENT_INTERPOLATED / SIMULATED_POSITION as actual REAL GPS.
- TRAINING may show training-labeled data only if that exact field actor is authorized by an existing source; don't widen simulator-controller private data.
- Device-local location use is not automatic sharing. No persistence, telemetry stream, server upload or hidden route-origin transfer. M14.8C2 is reserved for owner-approved consented REAL unit location sharing.

3.6 Access and projections

Every field map projection must apply:
- auth.uid() from server session;
- ACTIVE profile;
- exact active acting-organization membership;
- current incident participation and unit/crew/effective leader episode;
- data-specific visibility and current incident status;
- no assumed rights from org ADMIN/MANAGER or historical relationship;
- no cross-incident ID guessing, join leakage or broad COP grant.

A responder gets own assignment target and only specifically permitted operational context. An effective own-unit leader may see its own supervised assignments and appropriate team context, but cannot see another unit's private reasons, messages, resource details or instructor hazards. A controller's protected training visibility is a distinct authority, not implied by the TRAINING label.

NEVER ship broad raw private table rows and depend on Android UI filtering. The SQL read must be safe in itself. RLS + properly scoped SECURITY DEFINER read contracts are mandatory where appropriate.
