# CODEX IMPLEMENTATION PROMPT — M14.6B
## Dynamic Incident Events, Scenario Timeline & Instructor Event Scheduling

**Repository:** https://github.com/ficlus/Gasilko

Implement **M14.6B — Dynamic Incident Events & Scenario Timeline**.

Create one focused PR targeting the latest merged `main`. Do not merge.

**Prerequisite:** M14.6A / PR #74 must be merged. Inspect its actual SQL migration and template-definition schema before beginning.

## 1. Goal

Extend the Gasilko training simulator so that an incident evolves over time.

An authorized instructor should be able to:

- Define events while preparing an exercise.
- Schedule events relative to simulation time.
- Trigger events manually during a running exercise.
- Reveal new incident information to the commander.
- Add or reveal simulated hazards on the map.
- Change selected tactical conditions through explicitly supported operations.
- Review past, upcoming and triggered events.
- Pause and resume the scenario without losing scheduling accuracy.
- Replay the same template with the same event definitions in independent sessions.

The commander should experience an evolving operational incident, not a passive map containing static vehicles.

**This milestone is an event orchestration system, not a physical fire-propagation engine.**

Do not implement automatic fire spread, water consumption or resource-effect simulation yet. Those belong to M14.6C and M14.6D.

## 3. Event categories

Introduce an explicit, server-validated event catalog.

For MVP, implement the following categories.

### INCIDENT_REPORT

A new piece of information arrives.

Examples:

- Smoke visible from the second floor.
- Additional callers report trapped persons.
- New witnesses provide information.
- More vehicles may be involved.

Effect:

- Record a simulated incident report.
- Notify authorized commanders.
- Add a timestamped timeline entry.

Do not automatically change physical conditions unless another supported effect is explicitly configured.

### HAZARD_REVEAL

Reveal a previously hidden simulated danger.

Examples:

- Hazardous material discovered.
- Roof-collapse danger identified.
- Electrical hazard reported.
- Dangerous zone identified.

Effect:

- Display an authorized scenario hazard marker or polygon.
- Notify the commander.
- Preserve the distinction between a simulated hazard and a real-world observation.

Use existing tactical geometry validation and bounded object models.

### HAZARD_UPDATE

Modify the state or geometry of a previously revealed simulated hazard where the existing model permits it.

Requirements:

- Version guards.
- Valid geometry.
- Immutable event history.
- No silent overwrite of unrelated tactical objects.

### ACCESS_RESTRICTION

Introduce a simulated access restriction.

Examples:

- Road access unavailable.
- Main entrance blocked.
- Bridge reported unsafe.
- A particular approach becomes prohibited.

MVP behavior:

- Display the restriction on the map.
- Notify the commander.
- Clearly mark it as simulated.

Do not pretend that OSRM knows about a temporary road closure.

Do not automatically modify road-provider geography or silently invalidate unrelated routes.

Only enforce a routing restriction if the existing navigation domain genuinely supports that restriction through validated server logic. Otherwise keep it advisory and document the limitation.

### RESOURCE_REQUEST

Produce a simulated request for additional support.

Examples:

- Additional firefighting units requested.
- Water supply assistance needed.
- Technical rescue resources required.
- Medical support requested.

Effect:

- Create a simulated request/notification.

Do not automatically dispatch real resources or create an authorized operational task.

### COMMUNICATION_EVENT

Simulate a communication event:

- Radio message.
- Delayed report.
- Communication failure notification.
- Restoration of communication.
- Unit reporting an obstacle.

These must remain clearly labeled as simulated.

Do not impersonate human users or fabricate real personnel acknowledgments.

### PHASE_CHANGE

Allow the instructor to mark:

- Situation escalated.
- Situation stabilized.
- New operational phase.
- Additional incident information released.

Do not automatically alter authoritative real-incident lifecycle states.

## 4. Event definition schema

Introduce versioned, declarative event definitions.

A conceptual event:

```json
{
  "id": "event-01",
  "type": "HAZARD_REVEAL",
  "title": "Hazardous material discovered",
  "description": "A chemical container has been identified.",
  "trigger": {
    "mode": "SIMULATION_TIME",
    "offset_seconds": 360
  },
  "visibility": "COMMANDER",
  "effects": [
    {
      "type": "REVEAL_HAZARD",
      "object_local_id": "hazard-01"
    }
  ]
}
```

This is illustrative. Adapt the schema to the actual M14.6A template model.

Required:

- Stable definition-local event ID.
- Explicit supported event type.
- Validated trigger.
- Validated effects.
- Optional map geometry/object references.
- Clear visibility.
- Bounded descriptions.
- Bounded event count.
- Deterministic ordering.
- Schema versioning.
- No executable user-supplied scripts.
- No arbitrary SQL, RPC or Edge Function names.
- No unrestricted JSON command payloads.

### Compatibility with M14.6A

The existing template schema is strict and versioned.

Do not silently add new keys to its schema-v1 definition.

Either introduce an explicitly validated schema-v2 definition or a separate immutable, version-associated event-plan model.

Choose the smallest compatible design.

Existing v1 templates and running scenarios must remain valid.

Published event plans must be immutable.

Starting a training session must capture the exact event-plan version used.

## 5. Event triggers

Support three modes.

### A. Simulation time

Example:

"After 5 minutes of simulated incident time, reveal a hazard."

Time must come from the existing authoritative simulation clock.

Do not calculate event eligibility from a browser timer.

### B. Manual instructor action

The instructor explicitly presses:

**Sproži dogodek / Ereignis auslösen**

Require authorized scope and user confirmation for impactful events.

### C. Simple authoritative conditions

Support only conditions that can be evaluated against existing trusted state.

Examples:

- A specific explicitly referenced SIM unit has reached a confirmed arrival state.
- A specific simulation task assignment has completed.
- A prior scenario event has executed.

Do not infer event conditions from geographic proximity, visual marker position, simulated ETA or guessed task completion.

If reliable condition evaluation requires unsupported infrastructure, defer that condition rather than fabricate it.

## 9. Server-side event lifecycle

Define an authoritative event execution lifecycle.

Suggested states:

```text
PLANNED
   |
   v
ELIGIBLE
   |
   v
CLAIMED
   |
   +---- BLOCKED
   |
   +---- RETRYABLE_FAILURE
   |
   v
EXECUTED
```

Support explicit cancellation or skipping before execution where authorized.

Requirements:

- One logical event executes at most once.
- Unique scenario/event identity.
- Immutable event execution history.
- Stable operation IDs.
- Concurrency-safe claiming.
- Worker leases where appropriate.
- Bound retry policy.
- No automatic replay after ambiguous responses.
- No second execution after browser reload.
- No cross-scenario event execution.
- No old results overwriting newer revisions.

The execution record must contain the actual effect result, not just a success flag.

## 10. Scheduling through existing runner

Reuse the current Supabase scheduling infrastructure.

The project already has:

- `incident-simulation-runner`
- Secret-authenticated execution.
- `gasilko-sim-runner-5s` Cron.
- H1 automatic SIM preparation.
- Existing virtual agent movement ticks.

Do not add a browser scheduler.

Do not create a separate uncontrolled five-second Cron loop.

### Worker behavior

Preserve existing simulation movement ticks and H1 route preparation.

Add bounded event work in a way that does not starve movement ticks or H1 jobs.

Use fair scheduling and bounded processing time.

Events should trigger according to simulation time, within realistic scheduler tolerance.

Do not assume Cron executes at an exact millisecond.

Overlapping invocations must remain safe.

### Paused scenarios

Scheduled simulation-time events must not progress while a scenario is paused.

After resume, continue relative to the authoritative simulation clock.

Finishing the scenario prevents new events from executing.

Do not use wall-clock time as a substitute for simulation time.

### Cron unavailable

When the worker is unavailable, events remain pending.

Show an honest worker-freshness warning.

Do not silently execute pending events through browser refresh.

## 11. Safe event effects

Effects must use a narrowly supported server-side policy registry.

Do not introduce an unrestricted general-purpose executor.

Each supported effect should explicitly define:

- Input schema.
- Authorization.
- Allowed target.
- Incident/scenario scope.
- Validation.
- Idempotency.
- Audit.
- Visibility.
- Cancellation/retry behavior.

### Map effects

Prefer creating/revealing scenario-owned training annotations through the established COP object model or a dedicated read-only simulated hazard projection.

A background worker must not impersonate a human commander to call user-facing operational RPCs.

Where scenario annotations are created automatically, use a narrow protected training-only execution path with proper history.

Do not let scenario events arbitrarily edit genuine operational COP objects.

### Notification effects

Use existing F4 event/notification infrastructure.

Do not create a separate notification transport.

### Resource effects

For this milestone, resource-request events are informational only unless an established explicitly authorized training-only resource workflow already exists.

Do not automatically issue operational tasks or change resource ownership.

- Stable identity must be preserved within each scenario.

- Clock speed must not cause missed events.
- Pause/resume must not double-trigger events.
- Retried effects must not create duplicate map objects.
- Instructor intervention must be recorded.
- Template edits after a scenario starts must have no effect on that scenario.

Prepare clean event records for future M14.7 replay.
