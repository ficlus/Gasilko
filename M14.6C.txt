## 4. Deterministic fire-spread algorithm

For wildfire simulations, implement a bounded geographic grid.

Suggested MVP:

- Local metric simulation grid centered on a configured exercise origin.
- Configurable cell width, with a sensible default around 25–50 meters.
- Bounded simulation radius.
- Maximum permitted cell count.
- Eight-neighbor or another explicitly documented neighborhood model.
- Deterministic simulation step.
- Explicit versioned model parameters.

Convert between geographic coordinates and local metric coordinates using an appropriate existing geospatial method or a validated local projection.

Do not treat longitude/latitude degrees as uniform meters.

### Example cell data

```text
cell_x
cell_y
fuel_factor
moisture_factor
burn_state
intensity
burned_fraction
ignition_step
last_updated_step
```

Recommended burn states:

```text
UNBURNED
HEATING
BURNING
BURNED
NON_COMBUSTIBLE
```

Implement and document the actual supported transitions.

### Spread calculation

The ignition tendency for an adjacent cell may depend on:

- Neighboring burning intensity.
- Neighbor direction.
- Configured wind direction.
- Configured wind speed.
- Fuel factor.
- Moisture factor.
- Cell dimensions.
- Simulation time step.

Example conceptual relationship:

```text
spread_tendency =
    base_spread
    × fuel_factor
    × moisture_modifier
    × wind_direction_modifier
    × neighboring_fire_influence
```

This is a conceptual policy, not a prescribed physical equation.

Design a bounded, deterministic educational model.

If variability is required, use seeded deterministic values derived from scenario identity, model version, cell and simulation step.

**Never use uncontrolled random values that make identical scenario inputs behave differently after retry or worker restart.**

### Model requirements

- Identical initial state + identical parameters + identical elapsed simulation steps produce identical results.
- No double advancement after retry.
- No missing advancement due to a temporary worker delay.
- No fire growth while paused.
- No invalid negative intensity or fuel.
- No propagation outside configured bounds.
- No unlimited memory growth.
- No fabricated terrain or weather measurements.
- Explicit handling of multiple simultaneous ignition points.

## 5. Simulation clock integration

Use the existing authoritative simulation clock.

Fire evolution must be based on simulated time, not browser time.

Choose a fixed simulation step such as 5 or 10 simulated seconds and document it.

### Example

At 10× time speed:

- One real second represents ten simulated seconds.
- Fire simulation advances according to the authoritative simulated timeline.
- Browser refresh frequency does not change the simulation result.

### Mandatory behavior

- PAUSE freezes fire, smoke and hazard progression.
- RESUME continues from the correct simulated state.
- Scenario finish stops further advancement.
- Scenario reset follows an explicit existing-compatible lifecycle.
- Repeated Cron invocations do not advance the same step twice.
- Overlapping worker invocations cannot corrupt the fire field.
- Slower worker execution does not invent future steps or silently skip required evolution.

Track the last committed simulation step durably.

### Backlog control

At accelerated clock speeds, the system may accumulate more pending simulated steps than can be processed in one worker call.

Implement bounded processing per invocation.

Do not block other simulator subsystems for an unbounded time.

Report simulation lag explicitly.

Do not silently jump the fire field ahead without processing intermediate state transitions.

## 6. Smoke simulation

Implement an intentionally simplified smoke model.

Required properties:

- Smoke originates from active configured fire sources.
- Smoke intensity depends on simulated fire intensity.
- Smoke can drift according to configured wind direction and strength.
- Smoke spreads/dilutes over simulated time.
- Smoke gradually dissipates when the source weakens.
- Smoke cannot grow indefinitely without bounds.

### Visualization

Use lightweight semi-transparent coverage or polygons.

Avoid expensive particle systems as the authoritative model.

Do not create one permanent database row per smoke particle.

The map should show:

- Smoke source.
- Approximate plume area.
- Relative smoke concentration.
- Direction of drift where appropriate.

The visualization must be clearly labeled:

**SIM — modeliran dim**

Do not claim the polygon represents an actual measured toxic concentration.

No fabricated real sensor measurements.

Gasilko supports a dynamic, server-authoritative simulated incident environment.

The instructor can prepare a fire scenario, configure ignition and environmental conditions, and let the incident evolve through simulation time.

The commander sees only authorized simulated observations on the Command Map and continues issuing real training commands through the existing RTS task system.

Fire, smoke and hazards evolve deterministically without browser dependence, without compromising real incidents, and without degrading existing unit navigation or map performance.
